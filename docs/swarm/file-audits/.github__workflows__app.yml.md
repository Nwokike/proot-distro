## What it does / how the app uses it

`app.yml` is the CI delivery pipeline (house pattern: GitHub Releases only, never `actions/upload-artifact`, per D-006 at docs/decisions.md:21-22). Four jobs:

- `quality` (ubuntu-latest): checkout, uv, python 3.14, `uv sync --frozen --group dev`, ruff check+format, Flet API guard, a hand-rolled release-identity consistency script, `pytest -q -m "not live"` (app.yml:40-108).
- `prepare-release` (needs quality): creates a `softprops/action-gh-release` placeholder release, always `prerelease: true`, `make_latest: false`, tag `app-${run_number}` (app.yml:110-127).
- `apk` (needs prepare-release): builds the flet-proot payload wheel, decodes `KEYSTORE_BASE64` → `kiri_keystore.jks`, `uv sync`, `flet build apk` split-per-abi, prune check, 16 KB ELF alignment gate, upload APKs (app.yml:129-182).
- `aab` (needs prepare-release): same wheel+keystore, `flet build aab`, merged-manifest SDK/permissions/AdMob guard, app.zip dev-file prune, alignment gate, third-party sources bundle, upload AAB + sources (app.yml:183-302).

Release identity chain: `pyproject.toml` version/build_number → `src/core/constants.py` (APP_VERSION/APP_BUILD_NUMBER) → `version.json` (gitignored feed) → CI identity step at app.yml:59-106. Signing per D-008 (docs/decisions.md:27-28): keystore from secrets, env-only `FLET_ANDROID_SIGNING_*`, no pyproject signing block.

### F1 · P2 · `check_elf_alignment.py` is deleted in the working tree but still referenced by the workflow
- **Where:** `.github/workflows/app.yml:52,53,175,291` (ruff check/format inputs + two alignment-gate invocations); `git status --short` shows ` D check_elf_alignment.py` (deleted in working tree, NOT staged); `git ls-files --stage` confirms it is still tracked in HEAD/index; file absent on disk (`test -f` → ABSENT).
- **What:** The ruff step and both 16 KB alignment gates invoke a script that does not exist on the working tree. CI via `actions/checkout` restores it from HEAD so the pipeline is not broken today, but if the deletion is committed the `quality` job (ruff) and both alignment gates fail. `app.yml:8` also lists it in the `push` `paths:` filter.
- **Evidence:** `git status`/`git ls-files --stage` output above; app.yml:52-53,175,291; `check_elf_alignment.py` content recovered from `git show HEAD:check_elf_alignment.py` (main():63-70 returns non-zero on missing artifact).
- **Fix / opportunity:** either restore `check_elf_alignment.py` to the working tree (do not commit its deletion) or remove the ruff inputs and alignment-gate invocations from app.yml. Keep the gate — it enforces the Play 16 KB requirement (check_elf_alignment.py:84-91, ALIGN_16K=0x4000).
- **Risk if ignored:** committing the deletion breaks `quality` (ruff on missing file) and both Android alignment gates, silently shipping potentially misaligned native libs (Play rejection).

### F2 · P1 · hand-rolled `vt()` comparator blocks releases on cosmetic reformat and crashes on pre-release strings
- **Where:** `.github/workflows/app.yml:85-86` (`def vt(s): return tuple(int(x) for x in s.split("."))`); used at :96 (`elif vt(vj_v) < vt(py)`).
- **What:** `vt()` is a dotted-int tuple comparator, not PEP 440. Python tuple ordering treats a shorter prefix as smaller, so `vt("1.0")=(1,0) < vt("1.0.0")=(1,0,0)` is True but `vt("1.0.0") < vt("1.0")` is False. Consequence: if `pyproject` is `1.0` and `version.json` is `1.0.0` (a purely cosmetic reformat/trailing-zero normalization), `vt(vj_v) < vt(py)` is False → falls to `else` → `version.json … is AHEAD of pyproject` error (app.yml:99), blocking the release on a cosmetic change. Separately, `int(x)` raises `ValueError` on any pre-release-style segment (e.g. `int("0a1")`), which would crash the identity step if such a string ever reached it (all version inputs are currently hard-coded `1.0.0`, so this path is UNVERIFIED in practice).
- **Evidence:** app.yml:85-86,91-99 read directly; deterministic Python tuple semantics (no `.venv` dependency needed). `packaging 26.3` is installed but unused (`.venv/.../packaging/version.py` exists, pyproject has no packaging entry).
- **Fix / opportunity:** replace `vt()` with `packaging.version.Version` (already in `.venv`; adding as direct dependency needs owner sign-off per D-003, docs/decisions.md:13) or at minimum wrap in try/except with a clear error and treat equal-normalized versions as equivalent.
- **Risk if ignored:** a version string like `1.0` vs `1.0.0` (cosmetic reformat) triggers a false "AHEAD" error and blocks the release; a pre-release string crashes CI with an unhandled `ValueError`.

### F3 · P1 · release job is prerelease-always with no finalize step
- **Where:** `.github/workflows/app.yml:115-127` (`prerelease: true` at :124, `make_latest: false` at :125, placeholder body at :120-123).
- **What:** `prepare-release` creates a placeholder prerelease that is never finalized: there is no step to replace the body with release notes, set `prerelease: false`, or set `make_latest: true`. The release stays a draft-prerelease placeholder forever. This matches the drift recorded in docs/reference/app-ffmpeg.md:22 ("No release-notes finalize step — the placeholder release body is never replaced") and is explicitly deferred to M5 there. D-006 (docs/decisions.md:21-22) sanctions prereleases as the delivery vehicle but says nothing about finalization, so the gap is real.
- **Evidence:** app.yml:115-127 (no subsequent step references the tag to edit/replace the release); app-ffmpeg.md:22.
- **Fix / opportunity:** add a `finalize-release` job (needs apk+aab) that edits the release via `softprops/action-gh-release` (or `gh release edit`) with `prerelease: false`, `make_latest: true`, and a body built from the changelog/version.json release_notes. Gate it on a `workflow_dispatch` input or a tag so it only runs for real releases.
- **Risk if ignored:** users/consumers never see a stable/latest release; the placeholder prerelease remains the only artifact, defeating the "deliver via Releases" house pattern.

### F4 · P2 · APK prune verification is blind to nested `app.zip` / `sitepackages.zip`
- **Where:** `.github/workflows/app.yml:163-172` (`ls -lh build/apk/*.apk` + `unzip -l "$artifact" | grep -qE 'pytest/|ruff/|uvicorn/|starlette/|fastapi/|docs/'`).
- **What:** The prune check only lists top-level APK entries. flet packages the Python app + site-packages into a nested `app/app.zip` inside the APK (flet_cli `build_base.py:2836-2841` verifies `app/app.zip`; `SERIOUS_PYTHON_SITE_PACKAGES` at :2975-2995 bundles site-packages). `pytest`/`ruff` (dev group, pyproject.toml:78-84) would live inside `app.zip`/site-packages, **not** at the APK top level, so `unzip -l` on the APK cannot see them and the gate passes even with dev-only code shipping. The task-named `sitepackages.zip` could not be confirmed as an actual flet output name (grep of flet/flet_cli found `site-packages` dirs and `app/app.zip`, no `sitepackages.zip`) — that packaging filename is UNVERIFIED; regardless, the prune gate does not recurse into any nested zip.
- **Evidence:** app.yml:168; flet_cli build_base.py:2836-2841,2975-2995; pyproject.toml:78-84 (dev group includes pytest/ruff); grep of flet_cli for `sitepackages.zip` → none found.
- **Fix / opportunity:** extract `base/assets/app/app.zip` (AAB pattern already does this at app.yml:280-282) or the APK's embedded app zip and run the dev-file grep against its contents too; add `site-packages/**` to the patterns.
- **Risk if ignored:** dev-only/test code (pytest, ruff, dev dependencies) ships inside the APK undetected, bloating the package and expanding the attack surface.

### F5 · P2 · APK/AAB artifact globs can be a no-op literal when nothing is built (alignment gate short-circuit)
- **Where:** `.github/workflows/app.yml:175` (`check_elf_alignment.py build/apk/*.apk`) and :291 (`… build/aab/*.aab`).
- **What:** If a build fails to emit an artifact (or `split_per_abi` output lands elsewhere), bash passes the literal unexpanded glob `build/apk/*.apk` to the script. `check_elf_alignment.py` `main()` (HEAD:63-70) then reports `FAIL: no such artifact(s)` and returns 1 — a hard failure, not a silent pass. So it is safe-failing rather than short-circuiting to success. However, this has not been executed against a real build in this session, and the exact behavior when zero `.apk` match under `split_per_abi=true` (two ABIs configured at pyproject.toml:49) is UNVERIFIED by observation.
- **Evidence:** app.yml:175,291; pyproject.toml:45,49 (`split_per_abi=true`, `target_arch=["arm64-v8a","x86_64"]`); check_elf_alignment.py (HEAD) main():59-70; flet_cli build_base.py:1575-1577 (`split_per_abi`), :1408-1444 (`target_arch`), platform outputs at :194-203 (apk dist=`apk`, outputs=`build/app/outputs/flutter-apk/*`), :915 (`rel_out_dir = build/<dist>` → `build/apk`).
- **Fix / opportunity:** guard with `shopt -s nullglob` or an explicit `ls`/existence check before invoking the gate, and fail fast with a clear message when no artifact exists.
- **Risk if ignored:** a missing-artifact scenario surfaces as an obscure `no such artifact(s)` error rather than a clear build-failure signal; cosmetic, not a silent pass.

### F6 · P2 · `paths:` filter includes `tests/**`, contradicting docs/decisions.md D-015 §7(b)
- **Where:** `.github/workflows/app.yml:10` (`- "tests/**"`); docs/decisions.md:58-7b ("app.yml's `paths:` filter excludes `tests/**`, so a tests-only change needs a `workflow_dispatch`").
- **What:** The current `app.yml` push `paths:` list explicitly includes `tests/**` (line 10), so tests-only changes **do** trigger CI. D-015 §7(b) states the opposite (excludes `tests/**`). One of the two is stale; the workflow file is the operational ground truth. No defect in behavior today, but a documentation/decision drift that can mislead operators about whether a `workflow_dispatch` is required for tests-only changes.
- **Evidence:** app.yml:5-14; docs/decisions.md:58-59 (ruling 7b).
- **Fix / opportunity:** reconcile: either remove `tests/**` from app.yml:10 (matching D-015) and rely on `workflow_dispatch` for tests-only runs, or update D-015 §7(b) to state `tests/**` is included.
- **Risk if ignored:** operators follow D-015 and open a PR with only test changes expecting no CI run, but CI triggers anyway (harmless) — or vice versa, confusion about dispatch requirements.

### F7 · P3 · YAML is valid but step names are unquoted (incl. an unquoted `&`), diverging from D-015.7
- **Where:** `.github/workflows/app.yml` step names (e.g. :163 `Size report & prune check`); docs/decisions.md:58-7a ("an unquoted `": "` inside a YAML step name made GitHub reject the whole workflow file — quote step names").
- **What:** `python3 -c "import yaml; yaml.safe_load(app.yml)"` parses cleanly, so the file is valid YAML today and GitHub has accepted it (workflow commits exist in git history). No step name contains an unquoted `": "` colon-space. The `&` at :163 is space-surrounded, which YAML treats as a plain scalar (verified parse). Per D-015.7 the house rule is to quote step names to guard against future `:`/`&`/special-char additions; they are currently unquoted. Style/compliance only, P3.
- **Evidence:** app.yml:48-296 (all `- name:` entries unquoted); pyyaml parse test OK; `&` present only at :163.
- **Fix / opportunity:** quote all `- name:` strings per D-015.7 (e.g. `- name: "Size report & prune check"`) to future-proof against a regressor adding `": "` to a name.
- **Risk if ignored:** a future contributor adds a step name containing `": "` unquoted and GitHub rejects the entire workflow file with no jobs — the exact landmine D-015.7 records.
