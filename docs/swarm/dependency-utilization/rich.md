## What it does / how the app uses it

`rich` 15.0.0 (MIT, `.venv/Lib/site-packages/rich-15.0.0.dist-info/METADATA`) is a **dev-only, transitive** dependency of this repo. It is required by `flet-cli` (`uv.lock:231`), `flet-desktop` (`uv.lock:245`) and `cookiecutter` (`uv.lock:185`) — all three of which are dev-group-only (`pyproject.toml:78-84`). The app itself never touches it: `grep -rn "import rich\|from rich" src/ tests/` → 0 hits; `src/` contains no `print()` at all; and the packaged app dependency set is `project.dependencies` + `tool.flet.<platform>.dependencies` only (`.venv/Lib/site-packages/flet_cli/commands/build_base.py:2566-2576`), so the dev group is never consulted when the APK's site-packages is built. rich therefore **cannot reach the device**.

Where rich is actually exercised is the **build host**: `flet-cli` renders its console output through it (`flet_cli/commands/flutter_base.py:10-15` imports `Console, Group, Panel, Progress, Confirm, Style, Theme`; the shared console at `:35-44`; `Progress(transient=True)` at `:69`; the emoji swap at `:145-148`; the `Panel`/`Group` error frame at `:510-518`; `update_status` at `:537-548`), `flet-desktop` uses it for the download progress bar (`flet_desktop/__init__.py:20`), and `cookiecutter` uses it for prompts (`cookiecutter/prompt.py:16`).

The three host-side CLI scripts the prompt asks about (`build_flet_proot_wheel.py`, `check_elf_alignment.py`, `generate_third_party_sources.py`) do **not** use rich — they hand-roll console output with builtin `print()`. This audit evaluates whether that is a gap worth closing. **It is not**, and F2 shows the adoption would actively regress CI diagnosis.

## Findings

### F1 · P3 · rich is dev-only and provably cannot ship to Android — no action needed
- **Where:** `pyproject.toml:9-15` (runtime deps), `pyproject.toml:78-84` (dev group), `uv.lock:231` / `:245` / `:185` (rich's three requirers), `uv.lock:747-758` (rich 15.0.0 entry), `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2566-2576` (packaged dep set), `tests/test_imports_vs_deps.py:46-59`, `tests/test_proot_surfaces.py:133-148`
- **What:** The question "is rich dev-only (flet-cli logs)?" — **yes, and it is correctly so.** The runtime closure `flet → httpx/msgpack/oauthlib/repath` has no edge to rich (`uv.lock:193-201`); rich appears in `uv tree` only under `flet-cli (group: dev)` and `flet-desktop (group: dev)` (`docs/swarm/dependency-tree/uv-tree.txt:44,54,58`). No runtime package imports it: `grep -rn "import rich" .venv/Lib/site-packages/{flet,flet_ads,flet_terminal,proot_distro}/` → 0 hits. The APK is therefore free of rich (and of its own deps `markdown-it-py` + `pygments`).
- **Evidence:** `grep -i "^Requires-Dist" .venv/Lib/site-packages/flet-1.0.4.dist-info/METADATA` → httpx/msgpack/oauthlib/repath only; `.venv/Lib/site-packages/flet_cli-1.0.4.dist-info/METADATA` → `Requires-Dist: rich>=13.0.0`; `.venv/Lib/site-packages/flet_desktop-1.0.4.dist-info/METADATA` → `Requires-Dist: rich>=13.0.0`; `.venv/Lib/site-packages/cookiecutter-2.7.1.dist-info/METADATA` → `Requires-Dist: rich`.
- **Fix / opportunity:** None. This is the intended state; recorded so the synthesis does not propose pruning it as "unused".
- **Risk if ignored:** None. (A *real* risk exists only in the other direction — see F2's caveat about adding rich to `project.dependencies`, which would ship ~1 MB of dead weight into the APK.)

### F2 · P3 · Adopting rich in the three host CLIs would **regress** CI readability — recommend against
- **Where:** `build_flet_proot_wheel.py:5` ("Stdlib only"), `:435-443`, `:454-462`, `:493`; `check_elf_alignment.py:31-55`, `:69`; `generate_third_party_sources.py:112`; `.venv/Lib/site-packages/rich/console.py:1038` (`width = width or 80`), `:1041` (`width - self.legacy_windows`), `console.py:931` (`is_terminal`), `console.py:1652` (`print`); `.venv/Lib/site-packages/rich/live.py:244`, `:269`, `:272-276`; `.venv/Lib/site-packages/rich/status.py:41` (`transient=True`); `.venv/Lib/site-packages/rich/table.py:153`, `:364`, `:422`; `pyproject.toml:115-117` (ruff `T201` per-file-ignore for exactly these three files)
- **What:** The host tools *do* hand-roll console output — `build_flet_proot_wheel.py:454` (`print(f"[{pkg}] {deb['file']} ...", end=" ", flush=True)`), `:435-443` (a fixed-width payload listing), `:493` (a `=== flet-proot :: arch :: tag ===` banner); `check_elf_alignment.py:31-55` (`FAIL`/`warn`/`ok` prefixes with manual padding); `generate_third_party_sources.py:112` (one line). Rich has an obvious-looking counterpart for each (`Console.status`, `Table`, `rule`, `Panel`). **Measured against the real CI conditions, every one of those substitutions makes the log worse, not better:**
  1. **Width.** In a non-TTY, `Console.size` falls back to **80 columns** (`console.py:1038`, `:1041`; 79 measured on this Windows host because of `legacy_windows`). The current lines are ~95 characters and plain `print` does not wrap them. `Console().print()` of the exact current line **wraps it onto two lines**, splitting `p_align=0x4000` away from the library name.
  2. **Table truncation.** A `rich.table.Table` with the four columns (`artifact`, `library`, `p_align`, `status`) at the default width **ellipsises the artifact and library names** — `proot-distro-flet-arm64-v8…`, `lib/arm64-v8a/libsqlite3_…`. The full `.so` name is precisely what a Play 16 KB-alignment rejection asks for.
  3. **Silent status.** `console.status(...)` in a pipe prints **nothing**: `Status` builds its `Live` with `transient=True` (`status.py:41`) and `Live.refresh` only prints in a terminal (`live.py:269`) or in the non-transient fallback (`live.py:272-276`). Replacing `build_flet_proot_wheel.py:454` with a status would **delete the `.deb` name from the CI log**.
- **Evidence:** run against the installed rich, output piped (non-TTY):
  ```
  === PLAIN print (current check_elf_alignment.py style) ===
  ok   proot-distro-flet-arm64-v8a.apk: lib/arm64-v8a/libsqlite3_python.so p_align=0x4000
  === RICH Table, default Console (piped, non-TTY) ===
  │ proot-distro-flet-arm64-v8… │ lib/arm64-v8a/libsqlite3_… │ 0x4000  │ ok     │
  === RICH Table, Console(width=120) ===
  │ proot-distro-flet-arm64-v8a.apk │ lib/arm64-v8a/libsqlite3_python.so   │ 0x4000  │ ok     │
  --- A: console.print of the exact current CI line (95 chars) ---
  ok   proot-distro-flet-arm64-v8a.apk: lib/arm64-v8a/libsqlite3_python.so
  p_align=0x4000
  --- B: same, soft_wrap=True ---
  ok   proot-distro-flet-arm64-v8a.apk: lib/arm64-v8a/libsqlite3_python.so p_align=0x4000
  --- C: console.status in a non-TTY pipe ---
  (nothing)
  --- E: is_terminal: False width: 79 color_system: None
  ```
- **Fix / opportunity:** **Do not adopt rich in the host CLIs.** The house has already made this call: `build_flet_proot_wheel.py:5` states "Stdlib only", and `pyproject.toml:115-117` grants exactly these three files a ruff `T201` (print) exemption with the comment "host-side CLIs: progress output and pinned-URL fetches are their job". If a future change *does* want rich's colouring, the only non-regressing form is `Console(soft_wrap=True)` (or an explicit `width=`) — but that buys nothing in CI (colour is off: `color_system: None` in a non-TTY) and would break the file's "Stdlib only" property plus require owner sign-off under **D-003** (`docs/decisions.md:13`: "Dev: flet-cli, flet-desktop, pytest, pytest-timeout, ruff. Any addition needs owner sign-off.").
- **Risk if ignored:** None. The current plain output is already correct for a non-TTY CI log. The risk being avoided is the real one: a `Table` that truncates the library name would turn a one-glance Play diagnosis into a grep.

### F3 · P3 · `--no-rich-output` is correctly enforced in CI — but one rich frame still lands in the log
- **Where:** `.github/workflows/app.yml:31` (`FLET_CLI_NO_RICH_OUTPUT: "1"`), `app.yml:149` / `:203` (`uv sync --frozen --group dev`), `app.yml:159` / `:213` (`flet build apk|aab --yes -v`); `.venv/Lib/site-packages/flet_cli/commands/flutter_base.py:24-31` (env + argv detection), `:35-44` (`force_terminal=False if no_rich_output else None`), `:91-96` (argparse flag), `:122`, `:145-148` (emoji swap), `:504-507` (skip `flutter doctor` on Windows), `:537-548` (`update_status`); `.venv/Lib/site-packages/flet/utils/platform_utils.py:8-20` (`get_bool_env_var`); `.venv/Lib/site-packages/flet_cli/commands/build.py:125` (the success message that becomes a `Panel`)
- **What:** CI sets the **env var**, not the CLI flag — `app.yml:31` sets it workflow-wide, so all four jobs inherit it. `get_bool_env_var` treats `"1"` as true (`platform_utils.py:20`: `v.lower() in ["true", "1", "yes"]`), so the module-level `no_rich_output` is True (`flutter_base.py:29-31`) and the shared console is built with `force_terminal=False` (`flutter_base.py:43`). The CI logs are consequently **clean**: measured on the real run `39415969214` job `apk` (857 lines) — **0 ANSI escape sequences** from rich (the only 15 `^[[36;1m` sequences in the file are the Actions runner's own cyan echo of each `run:` block, not rich), **0 spinner frames**, **0 progress-bar glyphs**, and no `Live` redraw flood. The one residue is a **3-line `Panel` frame** at log lines 610-612 (`╭───…───╮ │ Successfully built your .apk for Android! … │ ╰───…───╯`), produced by `build.py:125` → `flutter_base.py:518` (`self.live.update(Panel(msg, style=error_style), refresh=True)`). The flag suppresses colour and animation but **not** the box-drawing frame.
- **Evidence:** `grep -c ' p_align=' apk.log` → 134; `grep -c $'\u2588\|\u2591\|\u2592\|\u2593' apk.log` → 0; `grep -c "⠋\|⠙\|⠹\|⠸\|⠼\|⠴\|⠦\|⠧\|⠇\|⠏" apk.log` → 0; `grep -o '\^\[\[[0-9;]*m' apk.log | sort | uniq -c` → `15 ^[[36;1m` / `15 ^[[0m`; `grep -n $'\u256d\|\u2570' apk.log` → 3 lines (the success panel).
- **Fix / opportunity:** None in this repo — the residue is owned by upstream `flet-cli` and is 3 readable lines. The repo's own discipline is already correct and is what §9 of the dependency study prescribes ("always pass `--no-rich-output` (or set `FLET_CLI_NO_RICH_OUTPUT=1`) in GitHub Actions"). **Do not** "fix" it by editing the workflow; the current env-var form is strictly better than the flag because it also applies to `flet build`'s per-command argparse path (`flutter_base.py:122`).
- **Risk if ignored:** 3 cosmetic lines per build. Acceptable.

### F4 · P3 · The 16 KB alignment gate prints 134 identical lines with no count — the one real diagnostic gap, and it needs no rich
- **Where:** `check_elf_alignment.py:33-55` (per-`.so` loop), `:68-70` (summary), `:20` (imports `ALIGN_16K, elf_info` from `build_flet_proot_wheel`); `.github/workflows/app.yml:175` (apk gate), `:291` (aab gate); `build_flet_proot_wheel.py:91` (`ALIGN_16K = 0x4000`)
- **What:** The gate is the Play-store-blocking check, and its CI output is **134 near-identical `ok` lines** (67 per APK × 2 APKs) that each repeat the artifact name, e.g. `ok   proot-distro-flet-arm64-v8a.apk: lib/arm64-v8a/libsqlite3_python.so p_align=0x4000`. The final line `OK: all 64-bit libs are 16 KB aligned` (`:69`) says nothing about *how many* were checked. A reader looking for the one misaligned library has to scan 134 lines; a reader looking for "did it even run" sees no count.
- **Evidence:** real CI log `39415969214` job `apk`: `grep -c ' p_align='` → **134**; `grep -c 'arm64-v8a.apk: lib/arm64-v8a/'` → 67; `grep -c 'x86_64.apk: lib/x86_64/'` → 67; `FAIL ` → 0; ` warn ` → 0.
- **Fix / opportunity:** Add the checked-library count to the existing summary line — e.g. count the libraries inspected and print `OK: 134 64-bit libs are 16 KB aligned` (or print the count and the misalignment count). This is a **one-line stdlib change inside `check_artifact`/`main`**, requires **no new dependency**, and does not disturb the existing per-line format (so any existing grep still works). Rich's `Table` is explicitly **not** the fix here — see F2 (it would truncate the library names).
- **Risk if ignored:** Low. A misaligned library is still correctly caught (exit code 1, `:70`); the cost is slower human triage of the one failure line.

## Verified-good list

- **rich is dev-only and cannot ship** (F1) — three requirers, all dev-group; the packaged dep set excludes the dev group (`build_base.py:2566-2576`); zero `import rich` in `src/`, `flet`, `flet_ads`, `flet_terminal`, `proot_distro`.
- **The repo's own guards already cover the invariant**: `tests/test_imports_vs_deps.py:46-59` (every `src/` import must be a declared runtime dep) and `tests/test_proot_surfaces.py:133-148` (`src/` must not import the dev-only build stack) — neither scans the repo-root host scripts, so a future `import rich` there would not be caught by CI (relevant if F2 is ever revisited).

- **`flet build` streams rather than hides its output in CI**: `-v` at `app.yml:159`/`:213` with `capture_output=self.verbose < 1` means the Flutter output is visible, so the no-rich setting costs no information.
- **The study's API claims spot-check clean against the installed 15.0.0**: `Console` `console.py:581` (`__init__` `:619`), `print` `:1652`, `log` `:1947`, `rule` `:1589`, `print_exception` `:1873`, `print_json` `:1758`, `is_terminal` `:931`, `size` `:1005`, `status` `:1157`, `capture` `:1096`, `set_live` `:822`; `Table` `table.py:153` / `grid` `:253` / `add_column` `:364` / `add_row` `:422`; `Progress` `progress.py:1061` / `track` `:1192` / `update` `:1417` / `add_task` `:1600`; `Panel` `panel.py:17`; `Text` `text.py:118`; `Prompt`/`Confirm` `prompt.py:304`/`:340`; `traceback.install` `traceback.py:84`; `RichHandler` `logging.py:24`; `filesize.decimal` `filesize.py:52`; `Live` `live.py:41` / `refresh` `:244`; `Status` `status.py:11`.
