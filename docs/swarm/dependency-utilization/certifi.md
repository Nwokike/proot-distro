## What it does / how the app uses it

**There is a legitimate app use, but it is entirely indirect and it covers only one of the app's two network paths.** The app never calls a certifi API itself.

certifi is a two-function package: `where()` and `contents()` (`.venv/Lib/site-packages/certifi/__init__.py:1-4` — `from .core import contents, where`; `__all__ = ["contents", "where"]`). The app's **only** occurrence of the string `certifi` in `src/` is a third-party-notice name in the licenses screen tuple: `"certifi"` at `src/screens/views.py:37`, consumed by `_py_entries()` at `src/screens/views.py:600-606` to render the MPL-2.0 row. `grep -rn -E "import certifi|certifi\." src/` returns nothing.

The real use is **transitive through httpx**, and it is real: the app's one httpx consumer is the update check, which creates `httpx.AsyncClient(timeout=4.0, follow_redirects=True)` with **no `verify=` argument** (`src/services/update_service.py:73-76`). httpx's default is `verify: ssl.SSLContext | str | bool = True` (`.venv/Lib/site-packages/httpx/_client.py:646`), the transport calls `create_ssl_context(verify=verify, cert=cert, trust_env=trust_env)` (`.venv/Lib/site-packages/httpx/_transports/default.py:153`, `:297`), and `create_ssl_context` with `verify is True` and no `SSL_CERT_FILE`/`SSL_CERT_DIR` in the environment falls through to `ctx = ssl.create_default_context(cafile=certifi.where())` (`.venv/Lib/site-packages/httpx/_config.py:33-40`). **So yes: the app's httpx calls are certifi-anchored, and the Android system CA store is not consulted on that path** — `ssl.create_default_context` with an explicit `cafile` takes the `load_verify_locations(cafile, capath, cadata)` branch and never calls `load_default_certs` (CPython 3.14.7 `ssl.py:716-722`), which is the only place the OS store is read (`ssl.py:528-534`).

**The app's other — and much larger — network path does not use certifi at all.** Every OCI image pull, Docker Hub search, and image download goes through upstream `proot_distro`'s own urllib opener, which builds `urllib.request.HTTPSHandler(context=None)` (`.venv/Lib/site-packages/proot_distro/helpers/download.py:395`, `:401`). With `context=None` the stdlib builds the **platform** context: `urllib/request.py:1360-1362` → `http/client.py:845` → `ssl._create_default_https_context` (`ssl.py:785` is the alias `_create_default_https_context = create_default_context`) → `create_default_context()` with **no cafile** → `load_default_certs()` → `set_default_verify_paths()` (`ssl.py:718-722`, `:528-534`). Upstream never imports certifi: `grep -rn -E "(^|[^a-zA-Z_])certifi([^a-zA-Z_]|$)" .venv/Lib/site-packages/proot_distro/ --include="*.py" | grep -iE "import|certifi\."` → empty.

**Do any paths need custom verify or certificate pinning?** Answers, with evidence below:
- **Update check** — no pinning needed. certifi's CA bundle plus hostname verification is the right control for a public GitHub endpoint; leaf pinning would break on GitHub's certificate rotation. The real risk on that path is elsewhere (redirect downgrade, already filed in the httpx audit as F6).
- **OCI pull** — certificate pinning is **not** the right instrument and is already superseded: content integrity is anchored by **sha256 digests** inside the OCI layer (`.venv/Lib/site-packages/proot_distro/helpers/docker/pull.py:34-39`, `:139`, `:258`, `:267`, `:273`). What the pull path lacks is a **pinned trust store** (F1/F2).
- **Docker Hub search** — metadata only, no digest, no pinning needed.

## Findings

### F1 · P1 · Image pulls trust the device CA store, while the app ships a pinned Mozilla bundle it never uses for them

- **Where:** `src/services/proot_service.py:212-223` (install → upstream), `:263-269` (search → upstream), `:108-114` (`allow_insecure=False` at `:113`); `.venv/Lib/site-packages/proot_distro/helpers/docker/transport.py:162-176` (`_build_opener`), `:176` (`_verified_opener = _build_opener(False)`), `:180-187` (`opener()`), `:190-192` (`auth_opener()`), `:344` (`http_opener().open`); `.venv/Lib/site-packages/proot_distro/helpers/docker/search.py:64`, `:153`; `.venv/Lib/site-packages/proot_distro/helpers/download.py:373-407` (`:395` `context = insecure_ssl_context() if insecure else None`, `:401` `urllib.request.HTTPSHandler(context=context)`); CPython 3.14.7 `urllib/request.py:1357-1365`, `http/client.py:845`, `http/client.py:1514`, `ssl.py:716-722`, `ssl.py:528-534`, `ssl.py:785`; the pinned side: `.venv/Lib/site-packages/httpx/_config.py:33-40`.
- **What:** the app has two network paths with **two different, provably different trust bases**. The update check trusts exactly the 121 CAs in `cacert.pem` and nothing else. The image-pull path trusts whatever OpenSSL's default verify paths provide on the device — the Android/OEM store, user-installed CAs, or nothing at all. Nothing in `src/` bridges them: `grep -rn -E "SSLContext|create_default_context|verify\s*=" src/` → empty, and `src/core/storage_paths.py:36-53` (`env_contract()`) sets no `SSL_CERT_FILE`/`SSL_CERT_DIR`. Upstream offers **no seam** to inject a CA bundle either: `grep -rn -E "SSL_CERT|cafile|capath|ca_bundle|CA_BUNDLE|cert_file|tls_ca" .venv/Lib/site-packages/proot_distro/` → empty; `http_opener()` takes only `insecure` and `redirect` (`download.py:373`), and `transport._build_opener` is private (`transport.py:162`).
- **Evidence:** runtime, this host — the app's *exact* client construction yields certifi and only certifi:
  ```
  certifi.where()  : ...\.venv\Lib\site-packages\certifi\cacert.pem
  bundle bytes     : 240216        certs in bundle : 121
  client ssl ctx   : <ssl.SSLContext ...>   ca_certs count : 121   # httpx.AsyncClient(timeout=4.0, follow_redirects=True)
  platform default ctx CA count      : 49                            # ssl.create_default_context()
  urllib HTTPSHandler(context=None) CA count : 49                    # the proot_distro path
  ```
  121 ≠ 49 on the same interpreter, in the same process: the two paths do not share a trust store. `ssl.create_default_context(cafile=certifi.where())` takes the `load_verify_locations` branch (`ssl.py:716-717`) and skips `load_default_certs` (`ssl.py:718-722`) — that is the proof that **Android system CAs are ignored on the httpx path**.
- **Fix / opportunity:** set `SSL_CERT_FILE` to `certifi.where()` in `env_contract()` (`src/core/storage_paths.py:36-53`). This is public-surface configuration, not a patch of upstream, so it respects the "one upstream importer / no monkeypatch" rule. Runtime-verified that OpenSSL picks the env var up through exactly that call style:
  ```
  baseline default-ctx CA count           : 49
  after os.environ.update(SSL_CERT_FILE=) : 152
  OpenSSL picked up the env var           : True
  httpx ctx CA count with SSL_CERT_FILE   : 121
  ```
  `env_contract()` is applied by `proot_service.bootstrap()` (`src/services/proot_service.py:40`) **before** `importlib.import_module("proot_distro")` (`:47`, `:81-85`), and upstream builds its opener at import time (`transport.py:176`), so the env var is in place before any SSL context exists. The guest container is env-isolated (`env -i K=V …` — `src/services/proot_service.py:315`), so nothing leaks into the Linux container. **Caveat, stated plainly:** `SSL_CERT_FILE` replaces OpenSSL's default *file*, but `set_default_certs()`→`set_default_verify_paths()` still also loads OpenSSL's default *directory*, so on the pull path certifi's 121 are **added** to, not substituted for, that directory's contents (hence 152, not 121, on this host). A hard "bundle only" guarantee on the pull path is **not reachable** without patching upstream, which the architecture forbids — `SSL_CERT_FILE` is the best available unification.
- **Risk if ignored:** image pulls run under a trust store the app neither controls nor can reproduce, while the app's documentation claims the opposite (`docs/reference/dep-httpx-cluster.md:18`: "certifi = build-time-pinned Mozilla bundle, not the Android system trust store — OS-level CA changes are invisible to httpx calls"). That sentence is true for the update check and **false for every image pull** — which is the operation that actually matters for a container engine.

### F2 · P1 · The pull path's trust store is device-dependent, and a trusted-but-unpinned MITM can substitute a tag-pinned image

- **Where:** `src/services/proot_service.py:215-217` ("image is any reference upstream accepts (debian:bookworm, alpine@sha256:…, ./path.tar.gz, https://…)"); `src/screens/views.py:83` ("docker image ref (e.g. debian:bookworm)"); `.venv/Lib/site-packages/proot_distro/helpers/docker/pull.py:34-39`, `:139` (`require_data_digest(body, ref, …)`), `:258`, `:267`, `:273`; `.venv/Lib/site-packages/proot_distro/helpers/download.py:424-438` (`is_cert_verification_error`), `:441-448` (`certificate_error_msg`), `:612-614`; `.venv/Lib/site-packages/proot_distro/helpers/docker/search.py:171-174`; `.venv/Lib/site-packages/proot_distro/commands/install.py:183`, `:188`, `:243`, `:314`, `:321`; `src/services/proot_service.py:113` (`allow_insecure=False`).
- **What:** upstream's digest discipline is sound but it verifies digests **against the digests the registry itself hands out** (`pull.py:34-39`: "Neither a cache file's name nor a registry's word is treated as evidence of content. A reference pinned by digest extends that to the top of the chain"). For a **tag** reference the top of the chain is still registry-supplied, so a party who controls the TLS session controls the manifest, the config blob, and the layers. Because the pull path trusts the device's CA store rather than a pinned bundle (F1), an enterprise/MDM-installed root — or any root the user added — is sufficient to sit in that session. A digest-pinned ref (`alpine@sha256:…`) is immune, because the user supplies the top digest. The app currently offers tag refs as the first-class example in its own UI hint.
- **Evidence:** the trust-store difference is F1's runtime output (121 vs 49 on the same interpreter). The digest chain is `pull.py:34-39` (policy comment), `:139` (`require_data_digest` for the manifest), `:258`/`:267`/`:273` (each fetched document is checked against the digest that asked for it). Upstream's own error text confirms the failure mode it is designed for is "untrusted certificate" (`download.py:441-448`), and it detects that condition precisely (`download.py:424-438`, `search.py:171-174`). The app's own insecure opt-out is correctly closed: `allow_insecure=False` (`src/services/proot_service.py:113`) → `install.py:183,188,243,314,321` → `download.py:395` keeps `context=None` (verifying) rather than `insecure_ssl_context()` (`download.py:410-421`).
- **Fix / opportunity:** the same one-line `SSL_CERT_FILE` change as F1 removes the device CA store from the pull path's *file*-based trust and adds the pinned bundle, so a device-added root is not what authorizes an image. Independently, make the **digest** the app-level anchor: have the install flow resolve the tag once, surface the resolved `sha256:…` in the UI, and let the user install from that digest (the app already accepts `alpine@sha256:…` per `proot_service.py:215-217`). That converts "the registry said so" into "the user pinned it", which is the control that survives a compromised TLS session.
- **Risk if ignored:** on a managed or tampered device, a trusted-but-unpinned root is enough to serve an attacker-chosen image that then runs as the container user on the phone. Digest-pinned users are unaffected; tag-ref users — the default the UI suggests — are not.

### F3 · P2 · certifi's `contents()` — the only seam for a private CA — is entirely unused, and only half the app could use it anyway

- **Where:** `.venv/Lib/site-packages/certifi/core.py:46-47` (`contents()`), `:21-44` (`where()`), `:14` (`sys.version_info >= (3, 11)` branch), `:40-42` (lazy `as_file` + `atexit` cleanup), `:10-11` (`exit_cacert_ctx`); `.venv/Lib/site-packages/httpx/_config.py:45-54` (deprecated `verify=<str>`), `:47-49` (the supported form: `verify=ssl.create_default_context(cafile=...)`), `:56` (an `SSLContext` passes through untouched); `.venv/Lib/site-packages/proot_distro/helpers/download.py:373-407`, `:395`, `:401`.
- **What:** the dependency study's §5.2 names the real-world failure a consumer app must survive: a user-installed enterprise MITM CA is not in the Mozilla bundle, so TLS fails with no settings-screen fix. On the httpx path the app owns the fix — `certifi.contents()` + the private PEM → `ssl.create_default_context(cafile=combined)` → `AsyncClient(verify=ctx)`. On the **pull path the app owns nothing**: `http_opener()` exposes no context parameter (`download.py:373`), `transport._build_opener` is private (`transport.py:162`), and upstream has no CA-related env var or argument anywhere (grep above). So a custom-CA story today can cover the update check and nothing else — a partial remedy that would leave the install path broken on exactly the devices the remedy is for.
- **Evidence:** `contents()` is the second and last public function (`certifi/__init__.py:1-3`); it is not called anywhere in `src/` and not called by any shipped package other than `certifi/__main__.py:3` (the CLI). `certifi.contents()` runtime: length 240216, identical to the on-disk bundle.
- **Fix / opportunity:** if a private-CA story is ever needed, build it once — `certifi.contents()` + private PEM → a single PEM file → point **both** paths at it. httpx: `verify=ssl.create_default_context(cafile=path)` (`httpx/_config.py:56`). urllib/upstream: the only app-side lever is `SSL_CERT_FILE` (F1), because upstream will not take a context. Decide this **before** a first enterprise pilot, not after: a half-fix that only covers the update check is worse than none, because it produces a support ticket with a plausible-looking cause.
- **Risk if ignored:** a managed-device user hits a TLS failure on the update check (visible, has a workaround: use a browser) and a TLS failure on image pull (invisible, has no workaround at all). No private mirror is planned today, so this is preparedness, not a live defect.

### F4 · P3 · certifi has no in-app refresh path; the bundle's freshness is a release ritual, and the exposure is smaller than the study implies

- **Where:** `.venv/Lib/site-packages/certifi/core.py:46-47` (the whole API — there is no update function, no `__version__` other than `__init__.py:4`); `.venv/Lib/site-packages/httpx/_config.py:33-40`; `.venv/Lib/site-packages/proot_distro/helpers/docker/transport.py:176`; `pyproject.toml:9-15`; `uv.lock:44-50` (certifi 2026.7.22), `:298-311` (httpx 0.28.1 → certifi), `:288-296` (httpcore 1.0.9 → certifi).
- **What:** certifi can only change by a dependency bump → lockfile move → CI rebuild → release. The dependency study (§4) frames the emergency-distrust exposure as an app-update-latency problem. In this app that exposure is **narrower than stated**: certifi governs only the update-check TLS session, while the operation that actually moves attacker-controlled bytes (image pulls) is on the device trust store (F1). A CA the Mozilla bundle drops is therefore not the app's urgent problem; a CA the *device* adds is.
- **Evidence:** the entire public surface is `where`/`contents` (`certifi/__init__.py:1-3`); `__version__ = "2026.07.22"` (`certifi/__init__.py:4`); the installed dist-info agrees (`certifi-2026.7.22.dist-info/METADATA:2-3`, `:8` `License: MPL-2.0`, `:12` the MPL-2.0 classifier). The lock pins the wheel hash (`uv.lock:48-50`).
- **Fix / opportunity:** none required. Keep certifi on the normal "bump the version" path and spend the CA-freshness attention on F1 instead, where the trust store is actually device-dependent.
- **Risk if ignored:** low, and smaller than the study's framing suggests.

## Missed capabilities (dependency audits only)

- **Unify the two trust bases with `SSL_CERT_FILE`** · API: OpenSSL's `set_default_verify_paths()` honors `SSL_CERT_FILE` (proven at runtime: default-ctx CA count 49 → 152 after `os.environ.update({"SSL_CERT_FILE": certifi.where()})`); httpx honors it too via `trust_env` (`httpx/_config.py:34-35`) and lands on the same 121-CA store · Integration: `src/core/storage_paths.py:36-53` `env_contract()` — one added key; it is applied before `import proot_distro` (`src/services/proot_service.py:40`, `:47`, `:81-85`), i.e. before upstream builds its opener (`transport.py:176`) · Value: closes F1/F2 with zero upstream changes and one line · Cost: S.
- **`certifi.contents()` as the private-CA building block** · API: `certifi/core.py:46-47` (returns the bundle as one ASCII str; 240216 chars here) · Integration: `ssl.create_default_context(cafile=<combined pem>)` passed as `verify=` to `httpx.AsyncClient` (`httpx/_config.py:47-49`, `:56` passthrough) · Value: the only supported way to add an enterprise CA to the update check without disabling verification (`verify=False` at `_config.py:41-44` must never ship) · Cost: S — but it covers only the httpx half (F3).
- **`certifi.where()` as the canonical bundle path** · API: `certifi/core.py:21-44`; returns the real filesystem path and is cached in `_CACERT_PATH` after a one-time `as_file` extraction (`core.py:40-42`) · Integration: any future `verify=ssl.create_default_context(cafile=certifi.where())` · Value: the bundle is already in the APK; pointing at it costs nothing · Cost: trivial.
- **Deliberately *not* recommended: certificate pinning.** The right pinning instrument for image pulls already exists and is content-addressed — sha256 digests (`proot_distro/helpers/docker/pull.py:34-39`, `:139`, `:258`, `:267`, `:273`). Leaf-certificate pinning on `raw.githubusercontent.com` would break on GitHub's certificate rotation and buy nothing the CA bundle does not already give. The gap is a pinned **trust store** (F1) and a user-visible **digest** for tag refs (F2) — not a pinned certificate.
- **`certifi` CLI (`python -m certifi`, `certifi/__main__.py:1-12`)** — a debugging aid for printing the bundle path on a device (`python -m certifi` prints `where()`, `-c/--contents` prints the PEM). Value: confirming on-device which bundle is in force when F1/F2 are diagnosed. Cost: zero (the module already ships).

## Verified-good list

- **Installed version is 2026.7.22 and the lock agrees.** `certifi/__init__.py:4` → `__version__ = "2026.07.22"`; `certifi-2026.7.22.dist-info/METADATA:2-3` → `Name: certifi` / `Version: 2026.7.22`; `uv.lock:44-50` pins the same version with a wheel hash. The study's version claim is confirmed, not drifted.
- **The study's API description matches the installed source exactly.** `where()` at `core.py:21-44`, `contents()` at `:46-47`, `__all__ = ["contents", "where"]` at `__init__.py:3`, `exit_cacert_ctx` at `core.py:10-11`, the py≥3.11 branch at `:14`/`:16` (our floor is Python 3.14.7, so the legacy `importlib.resources.path` branch at `:49-83` is dead code here), the `atexit` registration at `:42`.
- **The app's httpx calls are genuinely certifi-anchored.** `httpx.AsyncClient(timeout=4.0, follow_redirects=True)` with no `verify` (`src/services/update_service.py:75`) → `verify=True` default (`httpx/_client.py:646`) → `create_ssl_context(verify=True, …)` (`httpx/_transports/default.py:153`) → `ssl.create_default_context(cafile=certifi.where())` (`httpx/_config.py:33-40`). Runtime: that exact client object's SSL context holds **121** CAs, i.e. precisely the `cacert.pem` bundle (240216 bytes, 121 `BEGIN CERTIFICATE` blocks) and not the platform's 49.
- **Android system CAs are ignored on the httpx path — proven, not inferred.** `ssl.create_default_context(cafile=…)` takes the `load_verify_locations` branch and skips `load_default_certs` (CPython 3.14.7 `ssl.py:716-722`); `load_default_certs` (`ssl.py:528-534`) is the only place the OS store is read. So an OS-level CA change is invisible to the update check, exactly as `docs/reference/dep-httpx-cluster.md:18` states.
- **`certifi` is packaged for Android and works from the packaged zip.** Flet's own build notes say so: "Android (serious_python native-mmap packaging): pure Python ships in stored zips read via zipimport… The default set is empty: the common offenders read their data via importlib.resources, which is zip-safe (e.g. `certifi.where()` works from the zip — `importlib.resources.as_file()` extracts cacert.pem to a temp file on demand)" (`.venv/Lib/site-packages/flet_cli/commands/build_base.py:72-82`; `ANDROID_DEFAULT_EXTRACT_PACKAGES: list[str] = []` at `:82`). The lazy-extraction mechanism is the one certifi implements (`certifi/core.py:40-42`: `as_file(files("certifi").joinpath("cacert.pem"))`, `_CACERT_CTX.__enter__()`, `atexit.register(exit_cacert_ctx)`). A second Flet source confirms certifi is expected on device: "the embedded Python can't import its dependencies (e.g. ModuleNotFoundError: certifi)" (`.venv/Lib/site-packages/flet_cli/commands/test.py:53-59`).
- **The app declares no custom trust configuration, so nothing silently overrides certifi.** `grep -rn -E "SSLContext|create_default_context|verify\s*=" src/` → empty; no `verify=False` anywhere in `src/`; `SSL_CERT_FILE`/`SSL_CERT_DIR` are unset in the audit environment (runtime check: both `False`).
- **The app's insecure opt-out is correctly closed.** `allow_insecure=False` (`src/services/proot_service.py:113`) flows to `install.py:183,188,243,314,321` and to `download.py:395` (`context = insecure_ssl_context() if insecure else None` → `context=None`, i.e. the verifying handler), so `insecure_ssl_context()` (`download.py:410-421`, `check_hostname=False`, `verify_mode=CERT_NONE`) is never constructed by this app.
- **Certifi has exactly two runtime consumers in the shipped tree.** `httpx/_config.py:31` and `httpcore/_ssl.py:3` (`default_ssl_context()` → `context.load_verify_locations(certifi.where())`). `requests/certs.py:15` also uses `certifi.where()`, but `requests` is dev-only — it arrives via `cookiecutter ← flet-cli` (`uv.lock:173-186`, dev group) and is absent from the runtime tree (`docs/swarm/dependency-tree/uv-tree.txt`). The APK's runtime tree carries certifi through httpx/httpcore only.
- **The update-check path fails closed on TLS errors.** `except Exception` (`src/services/update_service.py:100-102`) catches `httpx.ConnectError`/`ssl.SSLCertVerificationError` and returns `None` — no downgrade, no retry-without-verify, no `verify=False` fallback.
- **The app ships certifi's license.** `pyproject.toml:60-63` removes only `oauthlib/**`; certifi's `cacert.pem` and `py.typed` are pure-Python package data and are packaged. `_TEXT_FILES` maps `MPL-2.0.txt` → "MPL-2.0" (`src/screens/views.py:50`), matching `METADATA:8`/`METADATA:12`.
- **No other network path in the app touches TLS.** `flet-ads` is a Dart extension (`grep` over `.venv/Lib/site-packages/flet_ads/*.py` finds no `httpx`/`urllib`/`ssl`/`certifi`); `launch_url` hands the URL to the OS browser (`src/core/shared_services.py:58-66`); the update dialog only launches URLs, it downloads nothing in-app (`src/components/update_dialog.py:23-26`, `:126-141`; the module docstring at `src/services/update_service.py:1-7` says "Delivery is browser-based: the dialog opens the release page; nothing is downloaded in-app"). `build_flet_proot_wheel.py:197-198` uses `urllib.request.urlopen` but is a host-side CI tool, not app code.

## Unverified

- **What the Android runtime's OpenSSL default verify paths contain.** Flet 1.0.4 builds Android on serious_python (`.venv/Lib/site-packages/flet_cli/commands/build_base.py:72`); whether that CPython ships a CA bundle at OpenSSL's compiled-in default file/dir, and whether Android's `/system/etc/security/cacerts` is in that path, is **UNVERIFIED** — no device run and no APK artifact was available in this audit. This is the single fact that decides whether F2 is *exploitable* (device store populated → a trusted root can MITM a tag-pinned pull) or merely *unreproducible* (device store empty → pulls fail closed with `CERTIFICATE_VERIFY_FAILED`). The code path in F1/F2 is proven; the device outcome is not. A one-line on-device probe settles it: print `ssl.create_default_context().get_ca_certs()` length and `certifi.where()` from the packaged app, and compare against 121.
- **Whether a device-installed enterprise/MDM root is actually in the pull path's trust store.** The mechanism is proven (F1); the presence of such a root on a given device is device state, not repo state — UNVERIFIED.
- **The exact `SSL_CERT_FILE` effect on Android.** The env var is honored by OpenSSL's `set_default_verify_paths()` (runtime-verified on Windows/OpenSSL 3.5.7), but the resulting store on Android is `SSL_CERT_FILE`'s 121 CAs **plus** whatever OpenSSL's default *dir* holds there — the size of that contribution is UNVERIFIED on device.
- **`SSL_CERT_DIR` is a trap and is not a usable alternative.** Runtime-verified: pointing it at the certifi directory changed the default context's CA count not at all (49 → 49), because OpenSSL's directory mode expects hashed per-certificate files and `certifi/` ships a single `cacert.pem`. Only `SSL_CERT_FILE` works with certifi's layout.
- **The pull path's error surface if TLS fails on device.** Upstream's message is precise (`download.py:441-448`), but `proot_service._run_command` (`src/services/proot_service.py:88-95`) nests `redirect_stderr` and loses the inner capture — already filed as F5 in the proot-distro utilization audit, not re-opened here. Whether a TLS failure would actually reach the user as a readable message is therefore UNVERIFIED.
- **On-device timing/latency of the certifi extraction** (`as_file` → temp file → `atexit` cleanup, `certifi/core.py:40-42`, `:11`) and whether the zipimport path in the packaged APK resolves `files("certifi")` identically to a filesystem install — UNVERIFIED; the Flet build comment (`build_base.py:79-80`) asserts it works, but asserts are not a device run.
- **Whether the Flet OAuth path could ever become a certifi consumer.** It is dormant (no `page.login` in `src/`; `oauthlib` is stripped by `pyproject.toml:60-63`), and flet imports httpx only lazily (`flet/auth/authorization_service.py:119,207,248`, `flet/auth/providers/github_oauth_provider.py:43,76`). If a login flow is ever added, that path would also be certifi-anchored — UNVERIFIED as a plan, not as a code path.
