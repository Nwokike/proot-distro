### F1 · P2 · The app has **no** syntax-highlighting surface: pygments has nothing to serve, and the study's "Track A — already working" is vacuous for this repo

- **Where:** `docs/dependency-studies/pygments.md:134-143` (Track A), `:145-160` (Track B), `:158-160` (the recommendation); `src/screens/views.py:609-694` (the only text-heavy screen), `src/screens/terminal_view.py:69-78`, `src/components/update_dialog.py:67-72,88-93`; `src/core/changelog.py:5-13`; `src/core/proot_probe.py:109-113`; `src/app_controller.py:173-195`.
- **What:** the study's Track A asserts that "**Every** `Syntax(...)` block in our dev-script output, **every** fenced code block in `rich.Markdown` build reports, and **every** `traceback.install()` frame is pygments-highlighted across 602 languages" and calls this "free, via rich". In this repository **none of those artifacts exist**:
  - there is no `tools/` directory and no dev script of any kind (the only host-side Python is `build_flet_proot_wheel.py` at the repo root);
  - `grep -rn "rich.Syntax\|from rich import\|import rich\|traceback.install\|rich.Markdown\|Console(" --include=*.py --include=*.yml --include=*.yaml --include=*.toml .` (excluding `.venv/`) → **no output**. ### F2 · P2 · pygments is dev-only and correctly so — two independent chains, no runtime path, and the house import guard would block an adoption today

- **Where:** `pyproject.toml:9-15` (runtime deps), `:52` (`tool.flet.android.dependencies`), `:63` (`cleanup.package_files = ["oauthlib/**"]`), `:77-84` (dev group); `docs/decisions.md:12` (D-003); `.venv/Lib/site-packages/flet-1.0.4.dist-info/METADATA:12-18`; `.venv/Lib/site-packages/httpx-0.28.1.dist-info/METADATA:27-30,36`; `.venv/Lib/site-packages/rich-15.0.0.dist-info/METADATA:29`; `.venv/Lib/site-packages/pytest-9.1.1.dist-info/METADATA:38`; `.venv/Lib/site-packages/flet_cli-1.0.4.dist-info/METADATA:21`; `.venv/Lib/site-packages/flet_desktop-1.0.4.dist-info/METADATA:13`; `.venv/Lib/site-packages/cookiecutter-2.7.1.dist-info/METADATA:37`; `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2566-2606`; `tests/test_imports_vs_deps.py:1-8,17-35,46-59`.
- **What:** the runtime dependency set is five strings (`pyproject.toml:9-15`) plus the Android native wheel (`pyproject.toml:52`). `flet` pulls `oauthlib`, `httpx`, `repath`, `msgpack`, `typing-extensions` — **no `rich`** (`flet-1.0.4.dist-info/METADATA:12-18`), so `rich` → `pygments` never enters the Android resolve. `httpx`'s `pygments` is an extra (`:36`), so it is not a hard dep either. `pygments` is reachable only through `rich` (under `flet-cli`/`flet-desktop`/`cookiecutter`) and `pytest` — every one of them in the dev group (`pyproject.toml:77-84`), and therefore outside D-003's runtime set.
  The house guard enforces this independently: `tests/test_imports_vs_deps.py:46-59` walks every `src/**/*.py`, resolves each top-level import to its provider distribution, and fails the build if the provider is not in `[project].dependencies` (plus the `tool.flet.<platform>.dependencies` tables, `:17-35`). `pygments`' provider is `pygments`, which is in neither table — so `import pygments` anywhere in `src/` **fails CI today, by design**. The guard's own docstring states the reason (`:1-8`): *"`flet build` resolves ONLY the project dependencies; a desktop-only import that isn't declared crashes the packaged app on Android."*
- **Evidence:** the chain diagram in §"What it does" above; `docs/swarm/dependency-tree/uv-tree-inverted.txt:81-83`; live `grep -rn "pygments" .venv/Lib/site-packages/*.dist-info/METADATA` → exactly four hits (`httpx` extra, `pytest`, `pygments` itself, `rich`).
- **Fix / opportunity:** none in the app — this is the correct state. Record it in the study so the next reader does not re-open it: "pygments is dev-only via `rich` and `pytest`; it is absent from the APK; `tests/test_imports_vs_deps.py` forbids importing it from `src/`."
- **Risk if ignored:** an adoption attempt (`import pygments` in `src/`) fails the `quality` CI job with an opaque "imports without a declared dependency" message. If the failure were "fixed" by adding `pygments` to `pyproject.toml` without noticing D-003 (`docs/decisions.md:12`: *"Any addition needs owner sign-off"*), the app would silently grow by the F3 amount and the frozen-dependency policy would be broken without a decision record.

### F3 · P2 · If pygments were adopted, it would cost ~3.2 MiB of APK for a capability Flet already ships natively in Dart

- **Where:** `docs/dependency-studies/pygments.md:149-155` (the study's own "the Android-shipping question is REAL"); `pyproject.toml:9-15,52`; `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2741-2745` (`--compile-packages` default **True**, `compile.packages` default True); `.venv/Lib/site-packages/flet/controls/core/markdown.py:955-960,308,679`; `.venv/Lib/site-packages/pygments/lexers/__init__.py:17,43-48,110-132`.
- **What:** the study flags the size but does not measure it. Measured on the installed package (`.venv/Lib/site-packages/pygments/`):
  | measure | bytes | size |
  |---|---|---|
  | `.py` source, whole package (343 files) | 4 577 209 | **4.37 MiB** |
  | `.py` source, `lexers/` only (89 % of the package) | 4 086 391 | **3.90 MiB** |
  | `.py` source, `formatters/` + `styles/` | 276 517 | 0.26 MiB |
  | fully compiled `.pyc` (all 343 modules, `compileall` forced) | 4 393 103 | **4.19 MiB** |
  | zipped compiled package (APK assets are zip-compressed) | 3 350 809 | **3.20 MiB** |
  | `lexers/_mapping.py` (the name→module table) | 71 218 | 0.07 MiB |

  `flet build apk` compiles packages by default (`flet_cli/commands/build_base.py:2741-2745` — `compile.packages` defaults to `True`), so the shipped form is the `.pyc` set; inside the APK's zip that is **≈ 3.2 MiB**, on top of a Python runtime and a Flutter engine.
  Against that cost, the value is zero, because **the capability already exists natively**: Flet's `ft.Markdown` highlights fenced code blocks in Dart with 89 built-in themes and a default of `MarkdownCodeTheme.GITHUB` (`.venv/Lib/site-packages/flet/controls/core/markdown.py:955-960`, `:308`, `:484`), and the app's only two `ft.Markdown` call sites (`src/components/update_dialog.py:67`, `:88`) already use it. Shipping a pure-Python lexer engine to re-derive what `flutter_markdown_plus` renders natively would add 3.2 MiB, a `Token → ft.TextSpan` mapper, and a permanent Android resolve obligation.
  The study's option (b) — *"strip to ~10 needed lexers via `[tool.flet.cleanup]` globs"* — is **not** safe as written, and the study's own caveat understates it. `pygments/lexers/_mapping.py:1-2` is auto-generated (`"DO NOT EDIT BY HAND; run tox -e mapfiles` instead"`) and is a **data-only** dict of `class name → (module, name, aliases, filenames, mimetypes)`. Deleting lexer *modules* without regenerating it leaves `import pygments.lexers` working (`:17` imports only the data), but `get_lexer_by_name` (`:110-132`) will then hit `_load_lexers(module_name)` → `__import__(module_name, None, None, ['__all__'])` (`:45`) and raise `ModuleNotFoundError` for any stripped lexer — while `get_all_lexers()` (`:51`) still advertises all 602. A stripped build would report lexers it cannot load.
- **Evidence:** the size table above (measured with `find … -printf "%s"` and a forced `compileall` + `zipfile` round-trip); `.venv/Lib/site-packages/flet/controls/core/markdown.py:955-960`; `flet_cli/commands/build_base.py:2741-2745`; `pygments/lexers/__init__.py:43-48,110-132`.
- **Fix / opportunity:** **decline Track B** and record the measurement so the M4 discussion does not re-litigate it. If a highlighting surface is ever wanted, the integration point is `ft.Markdown(code_theme=…)` (already available, zero cost) for markdown, or `ft.TextSpan` (`.venv/Lib/site-packages/flet/controls/core/text_span.py:14`) for arbitrary text — not pygments.
- **Risk if ignored:** the study's *"as an M4 plan-mode proposal with an APK-size measurement"* (`docs/dependency-studies/pygments.md:158-160`) is an open invitation to spend a milestone on a 3.2 MiB package that duplicates a native control. The ~30 MB rootfs figure the study cites (`:152`) does not appear anywhere in `docs/` — it is a recollection, not a recorded budget, so the cost side of that trade was never actually anchored.

### F5 · P3 · The one genuinely usable pygments capability is host-side only, and the only host-side consumer that exists does not use it

- **Where:** `.venv/Lib/site-packages/pygments/__init__.py:35,52,77`; `.venv/Lib/site-packages/pygments/lexers/__init__.py:110,212,261,304`; `.venv/Lib/site-packages/pygments/formatters/__init__.py:70`; `.venv/Lib/site-packages/pygments/styles/__init__.py:24`; `.venv/Lib/site-packages/rich/syntax.py:24-28,141-154`.
- **What:** pygments is fully available **in the dev venv at zero marginal cost** (already installed, already a transitive dev dep, already on the CI runner through the dev group). Its usable value is therefore in host-side tooling, not on-device:
  - `pygments.highlight(code, lexer, formatter)` (`.venv/Lib/site-packages/pygments/__init__.py:77`) / `pygments.lex(code, lexer)` (`:35`) / `get_lexer_by_name` (`.venv/Lib/site-packages/pygments/lexers/__init__.py:110`) / `get_lexer_for_filename` (`:212`) / `guess_lexer_for_filename` (`:261`) / `get_style_by_name` (`.venv/Lib/site-packages/pygments/styles/__init__.py:24`) — a host-side renderer that can turn any text into a terminal-coloured or HTML block with no new dependency.
  - `rich.Syntax` is the natural wrapper and it is already installed: `.venv/Lib/site-packages/rich/syntax.py:24-28` (the pygments imports), `:141-154` (`PygmentsSyntaxTheme`, falling back to `"default"` for an unknown theme name at `:148-150`). Rich consumes the token stream and converts each `(ttype, word)` pair into its own `Style` objects — pygments' **formatters are never involved** in rich's terminal rendering (they matter only for `HtmlFormatter`).
  - But the repo has **no host-side script that renders anything**: no `tools/` directory, and the only root-level Python is `build_flet_proot_wheel.py` (the native-wheel builder, whose job is progress output and pinned-URL fetches — `pyproject.toml:112-113` documents it as a "host-side CLI"). Nothing in it or in `.github/workflows/app.yml` uses rich or pygments.
- **Evidence:** the grep outputs in F1; `rich/syntax.py:24-28,141-154`; live `pygments.highlight('x = 1\n', get_lexer_by_name('python'), get_formatter_by_name('terminal256'))` → `'x \x1b[38;5;241m=\x1b[39m \x1b[38;5;241m1\x1b[39m\n'` (the study's `format()`-return-value question, now resolved).
- **Fix / opportunity:** none required. If the owner ever wants a *release-notes preview* in CI (render the `version.json` notes the way the app will show them), `rich.Syntax`/`rich.Markdown` in a one-off CI step is the zero-cost route — but the app already renders that content with `ft.Markdown`, so the preview would be a convenience, not a fix.
