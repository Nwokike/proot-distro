## What it does / how the app uses it

**Plainly: markupsafe is dormant in this project. It is a dev-group, build-host-only transitive dependency. The app never imports it, the APK never contains it, and nothing the app or the host scripts render is HTML — so there is nothing for it to escape.**

- **Chain (verified, dev-only).** `markupsafe 3.0.4` ← `jinja2 3.1.6` (`Requires-Dist: MarkupSafe>=2.0`, `.venv/Lib/site-packages/jinja2-3.1.6.dist-info/METADATA:18`) ← `cookiecutter 2.7.1` (`Requires-Dist: Jinja2<4.0.0,>=2.7`, `.venv/Lib/site-packages/cookiecutter-2.7.1.dist-info/METADATA:31`) ← `flet-cli 1.0.4` (`Requires-Dist: cookiecutter>=2.6.0`, `.venv/Lib/site-packages/flet_cli-1.0.4.dist-info/METADATA:18`) ← `proot-distro-flet` **dev group** (`pyproject.toml:77-84`; `docs/swarm/dependency-tree/uv-tree.txt:23,30-35`: `flet-cli v1.0.4 (group: dev)` → `cookiecutter v2.7.1` → `jinja2 v3.1.6` → `markupsafe v3.0.4`).
- **The app never imports it.** `grep -rniE "html|markupsafe|jinja" src/ --include="*.py"` → no output (exit 1). No `src/` file references jinja2, markupsafe, or HTML.
- **The APK never contains it.** The Android payload's pip set is built from `[project] dependencies` + `tool.flet.<platform>.dependencies` only — `flet_cli/commands/build_base.py:2566-2576` (`get_project_dependencies(self.get_pyproject("project.dependencies"))`, then `tool.flet.android.dependencies`), each emitted as `-r <requirement>` at `:2605-2606`. `[dependency-groups] dev` is never consulted by the build. No runtime package drags jinja2 in (`.venv/Lib/site-packages/flet-1.0.4.dist-info/METADATA:12-18`, `flet_ads-1.0.4.dist-info/METADATA:14`, `flet_terminal-0.4.0.dist-info/METADATA:23`, `proot_distro-5.10.0.dist-info/METADATA:13` — all `Requires-Dist` lines are flet/httpx/msgpack/oauthlib/repath/typing-extensions only).
- **The build host does touch the chain once, indirectly.** `flet build` renders the upstream Flutter build template through cookiecutter → jinja2 → markupsafe: `flet_cli/commands/build_base.py:1893-1905` (`from cookiecutter.main import cookiecutter` … `cookiecutter(template=template_url, …)` inside `create_flutter_project`), and `flet_cli/commands/create.py:90,134`.
- **Even there, markupsafe's *escaping* is never exercised.** cookiecutter's environment is `StrictEnvironment` (`.venv/Lib/site-packages/cookiecutter/environment.py:59-72`), which passes only `undefined=StrictUndefined` — `autoescape` keeps jinja2's default `False` (`.venv/Lib/site-packages/jinja2/environment.py:312`). markupsafe is therefore an **import-time** dependency of jinja2 (`.venv/Lib/site-packages/jinja2/filters.py:13-15`), not an exercised one; `do_forceescape` (`:139-144`) is opt-in per template.
- **No HTML anywhere in the product.** The app renders plain text (`ft.Text`, `.venv/Lib/site-packages/flet/controls/core/text.py:221-235` — `value: str`, no `inner_html`/HTML field anywhere in flet 1.0.4) and Markdown (`ft.Markdown`, `src/components/update_dialog.py:66-74,87-95` — rendered by the Flutter/Dart side, not by a Python HTML template). The host scripts emit Markdown/plain text only: `build_flet_proot_wheel.py:337-357` (THIRD-PARTY.md), `:399-412` (METADATA), `:413-418` (WHEEL), `:424-429` (RECORD) — no `.html` file is produced anywhere in the repo (`grep -rniE "\bhtml\b" --include=*.py --include=*.yml --include=*.yaml --include=*.toml .` excluding `.venv/.git/docs` → exit 1).

## Findings

### F1 · P2 · The study's "Our-project utilization" section documents an HTML-rendering app that does not exist — and would mislead the next agent into corrupting plain-text UI

- **Where:** `docs/dependency-studies/markupsafe.md:37-42` (the "Our-project utilization (M3/M4 defense in depth)" section) and `:44-48` ("Better than Termux's proot-distro?"). App-side truth: `src/screens/views.py:609-694` (`licenses_view`), `src/components/update_dialog.py:55-74,87-95`, `src/core/changelog.py:5-18`.
- **What:** the study asserts *"Any HTML we render — error dialogs with guest output, report pages, log viewers — goes through Jinja2 `{{ }}` or explicit `escape()`"*. In this codebase there is **no HTML rendering at all**: no `jinja2`/`markupsafe` import in `src/`, no `.html` file generated or served, no "report page" or "log viewer" feature (`grep -rniE "html|markupsafe|jinja" src/ --include="*.py"` → no output). The license texts are rendered through `ft.Text` (`src/screens/views.py:628-633`); the changelog and the GitHub release notes through `ft.Markdown` (`src/components/update_dialog.py:66-74,87-95`). The parenthetical claim that the app would be a *"security-hygiene win … a class of display-spoofing bugs Termux output views do not systematically guard against"* describes a defense that does not exist and would not work as written: **`markupsafe.escape()` in a plain-text Flutter widget double-encodes** — `escape('<b>')` → `'&lt;b&gt;'` (verified above), so the user would literally see `&lt;b&gt;` in the license dialog instead of `<b>`. The correct hygiene for this UI is plain-text rendering plus a URL allowlist, not HTML entity escaping.
- **Evidence:** `grep -rniE "html|markupsafe|jinja" src/ --include="*.py"` → no output (exit 1); `grep -rniE "\bhtml\b" --include=*.py --include=*.yml --include=*.yaml --include=*.toml .` (excluding `.venv/.git/docs`) → no output; `.venv/Lib/site-packages/flet/controls/core/text.py:235` `value: str = ""` (no HTML field; `inner_html` does not exist in flet 1.0.4 — the only `Markup` hit in the flet package is the iOS share-sheet action `MARKUP_AS_PDF`, `.venv/Lib/site-packages/flet/controls/services/share.py:84`).
- **Fix / opportunity:** correct `docs/dependency-studies/markupsafe.md:37-42` to say what is true — the app renders plain text and Markdown only, so HTML escaping is **not applicable**; the display-spoofing defenses it actually has are (a) plain-text rendering of every guest string and (b) the `https` + host allowlist on every launched link (`src/services/update_service.py:26-37`, used by `src/components/update_dialog.py:23-26` and `src/core/shared_services.py:58-66`). Keep the "never `Markup(untrusted)`" rule — it is sound advice for the *build-host* templates, just not for this UI. This is a docs-only edit; no app code changes.
- **Risk if ignored:** a future agent trusts the study, adds `markupsafe` to `[project] dependencies` (a D-003 violation, `docs/decisions.md:12`) or calls `escape()` on strings bound to `ft.Text`, and ships either a dependency-addition violation or visibly mangled license/terminal text in the About dialog. The synthesis will re-open this file unless it is corrected.

### F2 · P2 · The dev-only import guard omits `markupsafe` — the one package in this chain whose absence from the APK would crash the app on device

- **Where:** `tests/test_proot_surfaces.py:133-148` (`test_dev_only_packages_are_not_imported_from_src`, docstring at `:134`, set literal at `:135-145`, helper `_imports_of` at `:23-31`); the dev group at `pyproject.toml:77-84`.
- **What:** the guard's stated purpose is *"The build-host tree must never reach the app (licensing A4)"*, and its set contains `"jinja2"` (`:143`) and `"cookiecutter"` (`:137`) — but **not `"markupsafe"`**, and not the rest of the cookiecutter stack (`arrow`, `slugify`, `yaml`, `click`, `rich`, `markdown_it`, `mdurl`, `pygments`, `chardet`…). `markupsafe` is the one member of that family that a developer would plausibly import *directly* to "escape a guest filename" — exactly the use the study advertises at `docs/dependency-studies/markupsafe.md:37-42`. If `src/` ever did `from markupsafe import escape`, the APK would not contain the package (F1 chain: no runtime dependency pulls it), so the import would raise `ModuleNotFoundError` **on device only** — the desktop `flet run` and the whole pytest suite would stay green because the host venv has markupsafe installed.
- **Evidence:** set contents at `tests/test_proot_surfaces.py:135-145` = `{"chardet", "cookiecutter", "pytest", "ruff", "flet_cli", "flet_desktop", "binaryornot", "jinja2", "requests"}` — no `markupsafe`; `markupsafe` is installed only in the dev tree (`docs/swarm/dependency-tree/uv-tree.txt:23,35`, `group: dev`); the APK pip set excludes it (`flet_cli/commands/build_base.py:2566-2576`).
- **Fix / opportunity:** add `"markupsafe"` to that set literal (one line, `tests/test_proot_surfaces.py:136-146`). The guard then fails any `src/` import of the package with a message naming the dev-only offender, exactly as it already does for `jinja2`.
- **Risk if ignored:** a one-line "let's escape this guest string" in `src/` produces a device-only `ModuleNotFoundError` at import time (or, if the import is lazy, a crash on the code path that uses it) that no host-side test can catch. Low probability, high blast radius, trivially closed by one list entry.

### F3 · P3 · `build_flet_proot_wheel.py` must stay stdlib-only, and its one `escape`-looking call is `re.escape`, not markupsafe

- **Where:** `build_flet_proot_wheel.py:5` (*"One self-contained file: the sha256 pins and the ELF/alignment checks live below. Bumping a source = editing `_PINNED_SOURCES` (one commit). **Stdlib only.**"*); `build_flet_proot_wheel.py:259` (`re.fullmatch(rf"{re.escape(stem)}(\.so(\.[0-9]+)*)?", …)`); `build_flet_proot_wheel.py:337-357` (`_third_party_md` — a Markdown table built by f-string interpolation of pinned lock values); `build_flet_proot_wheel.py:330-334` (`_license_text` → `LICENSES/`, `LICENSE_DIR` at `:24`).
- **What:** two audit traps for the synthesis. (1) The `escape` at `:259` is **stdlib `re.escape`** (regex metacharacter escaping for a filename glob) — it has nothing to do with `markupsafe.escape`, and a report that mis-binds it would produce a false "markupsafe is used here" claim. (2) The builder is executed on a bare host (CI, and it must run before the app exists), so it may not import anything outside the stdlib; `markupsafe` is *not* guaranteed to be installed next to it. `_third_party_md` interpolates only pinned, repo-controlled values (package names, versions, upstream URLs, `arch` from an `argparse` choice list at `:472-475`) into Markdown — there is no untrusted input and no HTML sink, so no escaping is required or wanted.
- **Evidence:** `build_flet_proot_wheel.py:1-21` — imports are `argparse, base64, hashlib, io, re, struct, sys, tarfile, urllib.error, urllib.request, zipfile, pathlib` only.
- **Fix / opportunity:** none required. Record the reading so the synthesis does not open a false positive; if the builder ever needs to emit HTML (it does not), that would be the moment `markupsafe` becomes relevant — and then it would have to be a vendored/pinned decision, not an import.
- **Risk if ignored:** a synthesis-level false positive ("markupsafe is used in the wheel builder") would send a fixer to "add markupsafe to the builder's imports", breaking the stdlib-only property the file documents at `:5`.

## Missed capabilities (dependency audits only)

**None. There is no capability of markupsafe this project should adopt.**

- `escape` / `escape_silent` / `Markup` / `EscapeFormatter` exist to make **HTML** safe. This app produces **no HTML** (F1 evidence) and cannot consume markupsafe at runtime (it is not in the APK, and D-003 freezes the dependency set — `docs/decisions.md:12`). Adopting it would require a D-003 change for zero benefit.
- `Markup.striptags` / `Markup.unescape` (`:188-238`) are HTML-tag tools with no analogue in a Flutter text UI.
- The one thing markupsafe is genuinely good for here is already handled by a *different, correct* mechanism: the URL allowlist for anything that can launch a browser (`src/services/update_service.py:26-37` → `is_allowed_launch_url`, `https` scheme + host-suffix match against `_ALLOWED_HOSTS`), plus `ft.Markdown`'s Dart-side rendering for the release notes.
- If a future feature ever needs to emit an HTML page (e.g. a shareable "session report"), the correct decision is a *runtime* dependency decision (D-003 sign-off + Android wheel availability), not a silent `import markupsafe` inside `src/`.

## Verified-good list

- **The app does not import markupsafe, jinja2, or cookiecutter** — enforced by a real test, `tests/test_proot_surfaces.py:133-148` (the set is incomplete, see F2, but the rule itself is sound and the code complies).
- **markupsafe never reaches the APK**: the build's requirement list comes only from `[project] dependencies` + `tool.flet.<platform>.dependencies` (`flet_cli/commands/build_base.py:2566-2576`, `:2605-2606`); the dev group is not part of it. This matches the house reference `docs/reference/dep-cookiecutter-stack.md:3` ("Build-host only; none ship to Android").
- **The app's own third-party inventories correctly omit markupsafe/jinja2** — `_PY_DISTS` (`src/screens/views.py:26-42`) lists only the shipped runtime dists, and the generated `THIRD-PARTY-SOURCES.md` "Python Dependencies" table (git HEAD, read via `git show HEAD:THIRD-PARTY-SOURCES.md`) lists the same runtime set. Compliance-wise the omission is correct: a package that is not shipped needs no in-app license entry.
- **`licenses_view()` renders license text as plain text** (`src/screens/views.py:625-634`), reads files with an explicit UTF-8 decode and a 6000-char cap, and degrades to `"(text missing)"` when a file is absent — no HTML sink, no injection surface.
- **The changelog is plain text** (`src/core/changelog.py:5-18`, `notes_for` at `:16-18`), and release notes are length-capped and type-checked before use (`src/services/update_service.py:40-41` `_safe_text`, `:44-47` `_safe_url`).
- **Every externally launched URL is allowlisted** (scheme `https` + host suffix, `src/services/update_service.py:26-37`; the Markdown link handler goes through it, `src/components/update_dialog.py:23-26,71,92`) — the correct defense for remote content in a Markdown view, and the reason no HTML escaping is needed anywhere.
- **`ft.Text` has no HTML mode in Flet 1.0.4** (`.venv/Lib/site-packages/flet/controls/core/text.py:221-235`); no `inner_html`-style control exists in the package. Escaping guest strings before binding them to `ft.Text` would corrupt the display, so *not* escaping them is the correct behavior here.
- **The builder is stdlib-only** (`build_flet_proot_wheel.py:1-21`) and its outputs (`.md`, `METADATA`, `WHEEL`, `RECORD`, the zip) contain no HTML (`:337-357`, `:399-429`).
- **The installed markupsafe API matches the study** — every entry of `docs/dependency-studies/markupsafe.md:9-19` re-verified against `.venv/Lib/site-packages/markupsafe/__init__.py` (table above), and the C speedups are active on this host (`_speedups.cp314-win_amd64.pyd`).

## Unverified

- **Whether the upstream flet build template contains `.html` files that jinja2 renders with `autoescape=False`.** The template zip is fetched at build time and is not cached on this host (`~/.flet/cache/` holds only `python-build/manifest-20260921.json`; `flet_cli/utils/template_cache.py:21-29`), so its contents could not be inspected.
