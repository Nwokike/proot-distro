## What it does / how the app uses it

`flet-platform-assets 1.0.4` is a **build-host-only** renderer: it turns one source image into every platform's icon set and splash bitmaps, and the *output* ships in the app bundle while the package itself never reaches the APK (`uv.lock:228` — it is a dependency of `flet-cli`, which is a dev-group dependency at `pyproject.toml:78-84`; `uv.lock:253-258` — its only runtime dep is `pillow 12.3.0`). It is pure: `render_icons()`/`render_splash()` do images in → images out and never touch disk (`__init__.py:1-17`); `write()` is the only mutator (`_write.py:13-57`); diagnostics are data in `RenderResult.warnings`, never log output (`_models.py:130-162`).

The app uses it through `flet-cli`, which calls `customize_icons()` and `customize_splash_images()` on every build (`flet_cli/commands/build.py:115-116`). The source is discovered **by convention, not by config**: `self.assets_path = <app.path>/assets` (`build_base.py:2092`) → `icon_<platform>.*` first, then the generic `icon.*` (`build_base.py:2100-2108`), and the splash falls back `splash_<platform> → splash → icon` (`build_base.py:2379-2384`). `pyproject.toml:28` (`icon = "src/assets/icon.png"`) is **not read by anything** (see the flet-cli report F5; re-verified here) — the file happens to be at the conventional path, so it works by accident of layout.

The app has exactly one piece of artwork, `src/assets/icon.png` (1024×1024, palette PNG with transparency). It is a **wide wordmark lockup** — `{ } _` braces, the Tux penguin, and the words "Proot Distro" — in the SVG's *light* palette (slate `#2e343a` on transparent). `src/assets/icon.svg` is the same artwork with a `prefers-color-scheme: dark` variant; it is the **in-app** brand mark (`src/components/brand_hero.py:17-29`, `src/screens/onboarding_view.py:11,77`) and can never reach the build pipeline.

CI builds **Android only** (`apk` at `.github/workflows/app.yml:159`, `aab` at `:213`); `ICON_PLATFORMS`/`SPLASH_PLATFORMS` (`build_base.py:93-102`, `:120-126`) map `apk`/`aab` → `android`. So the iOS/macOS/Windows/Linux renders are latent, never produced by this repo.

I rendered every platform's output in isolation (the package is pure, so this is the real output) into a temp dir and measured the pixels. **All 9 render passes produced ZERO warnings** — the package is not complaining; the *inputs and configuration* are wrong.

## Findings

### F1 · P1 · The Android splash artwork is dark-on-dark and effectively invisible

- **Where:** `pyproject.toml:39-41` (`[tool.flet.splash] color = "#121218"`, `dark_color = "#121218"`); `src/assets/` (no `splash*.png` — only `icon.png`/`icon.svg`); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2379-2384` (splash falls through to `icon`, `derived = True`), `:2387-2393` (`SplashOptions(color=splash["color"], …)`), `:2427-2439` (load + `square`), `:2441-2445` (`render_splash(...)` then `write(..., declared_only=False)`); `.venv/Lib/site-packages/flet_platform_assets/_splash.py:126-128` (`_scaled`), `:145-152` (`drawable-{d}/splash.png` + `android12splash.png`), `:49-51` ("Android now uses `@color/flet_splash_background` instead").
- **What:** the splash has no artwork of its own, so the pipeline falls back to the app icon — a **slate `#2E353B`** wordmark on transparency — and composites it over the **`#121218`** background colour. Slate on `#121218` is a **1.48:1** contrast ratio: the launch screen is a black rectangle. The same is true of the Android 12 splash icon (`android12splash.png`, `drawable-xxxhdpi` = 1152×1152) and of the iOS `LaunchImage*.png` set (`_splash.py:228-247`).
- **Evidence:** measured from the generated files (my isolated render, temp dir, `.venv/Scripts/python.exe`):
  ```
  splash.png composited on #121218 — top colours: (18,18,24) 987108  (46,53,59) 1895 …
  dominant art colour: (18, 18, 24)      -> contrast vs #121218: 1.0
  contrast pure slate #2e343a vs #121218: 1.48
  contrast #2e343a vs white:              12.59
  contrast #f4f4f8 vs #121218:            17.01
  ```
  Visual proof (generated `drawable-xxxhdpi/splash.png` over `#121218`): the wordmark is present but effectively black-on-black.
- **Fix / opportunity:** give the splash its own artwork instead of inheriting the launcher icon. Add `src/assets/splash.png` — a raster of the brand in a **light** tone (`#f4f4f8`, 17:1 against `#121218`) — which the pipeline will pick up through the documented `splash_<platform> → splash → icon` chain (`build_base.py:2379-2384`) and frame with the `"splash"` rule (`_splash.py:108-111`, `FRAMING["splash"] = 0.60` at `_icons.py:192`). Because `color == dark_color == "#121218"`, a single `splash.png` covers both modes: the dark pass reuses the light artwork (`_splash.py:166-167`, `:246`) and the Android `-night-` duplicates are simply not emitted (`:156-157`). No new dependency, no code change.
- **Risk if ignored:** the app's *only* brand moment before the terminal prompt — the cold-start launch screen — is a black rectangle on every device, and the "branded first run" claim in `docs/dependency-studies/flet-platform-assets.md:422-424` does not hold.

### F2 · P1 · The launcher icon is a wide wordmark and is unreadable at every launcher size

- **Where:** `src/assets/icon.png`; `.venv/Lib/site-packages/flet_platform_assets/_icons.py:53-59` (mipmap 48/72/96/144/192), `:61-67` (adaptive 108/162/216/324/432), `:51` (`ADAPTIVE_SAFE_FRACTION = 72/108`), `:177-193` (`FRAMING`), `:241-242` (`derived` → `_frame(source, platform)`), `:332-347` (`_plain`).
- **What:** the source is a **1.75:1 letterbox inside a 1024² canvas** — the opaque artwork's alpha bounding box is `(53, 256, 969, 779)`, i.e. 89.6 % of the width but only 51 % of the height, vertically centred. The package dutifully fits that into every square target, so each output is a *small wide wordmark floating in a large empty square*. At `mipmap-mdpi` (48 px) the text is ~4 px tall and unreadable; the adaptive layer shrinks it further to 56.7 % radial (`FRAMING["android"]`, `_icons.py:180`), so the launcher's guaranteed 72/108 circle shows a wordmark occupying about 30 % of the icon.
- **Evidence:** `alpha bbox (l,t,r,b): (53, 256, 969, 779) of 1024x1024`; `alpha_extent: 0.896484375`, `radial_extent: 1.0277951825786085`; the generated 48 px `mipmap-mdpi/ic_launcher.png` renders as illegible mush, and `ic_launcher_foreground.png` (432 px) inside a circular mask shows a small wordmark.
- **Fix / opportunity:** use the **per-platform source** feature that is currently unused. `build_base.py:2103-2105` resolves `icon_<platform>.*` *before* the generic `icon.*`, and an `icon_<platform>.png` is treated as a finished composition and is **never reframed** (`derived=False` → `_icons.py:252`, `:222-226`). Add `src/assets/icon_android.png`: a 1024² **square** mark (the penguin alone, or the mark inside the 72/108 safe circle on transparency) — legible at 48 px, correctly masked by the launcher, and it leaves the iOS/macOS/web sets untouched. Cost: one PNG, zero code.
- **Risk if ignored:** the app is unidentifiable on the home screen; the Play listing thumbnail and the taskbar icon are both mush. This is the single largest gap between what the package can do and what the app currently gets from it.

### F3 · P2 · The Android adaptive icon gets a white background resource in a dark app

- **Where:** `pyproject.toml:43-52` (`[tool.flet.android]` — no `adaptive_icon_background`); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:1645-1653` (`self.options.android_adaptive_icon_background or get_pyproject("tool.flet.android.adaptive_icon_background") or self.icon_background_value("android") or "#ffffff"`), `:2194-2196` (`icon_background_value`), `.venv/Lib/site-packages/flet_platform_assets/_icons.py:61-67` (the foreground layers).
- **What:** the adaptive background is a **colour resource, not pixels** — the package only produces the foreground layers (`drawable-*/ic_launcher_foreground.png`). With nothing configured, the chain falls through to the literal `"#ffffff"`. So the app's adaptive launcher icon is a **white** rounded square carrying the dark wordmark, while the splash behind it is `#121218` and the app itself is dark-themed (`src/core/theme.py:17`). The only light surface in the product.
- **Evidence:** resolution walk of `build_base.py:1645-1653` with the current `pyproject.toml` — CLI flag `None`, `tool.flet.android.adaptive_icon_background` absent, `tool.flet.android.icon_background` absent, `tool.flet.icon_background` absent → `"#ffffff"`. Rendered composite of `ic_launcher_foreground.png` over white inside a circular mask: white disc, dark wordmark.
- **Fix / opportunity:** `[tool.flet.android] adaptive_icon_background = "#121218"` — one line, `build_base.py:1647`. **It must land together with the artwork change in F6**: the current slate wordmark would then be dark-on-dark in the adaptive icon too.
- **Risk if ignored:** a glaring white icon tile on a dark home screen, inconsistent with the launch screen and the app's own palette; on Pixel-style launchers it reads as a third-party app.

### F4 · P2 · `icon_background` is unset, so iOS / macOS / web icons are flattened onto pure white

- **Where:** `pyproject.toml` (no `icon_background` at any level); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2194-2196` (`icon_background_value`: `tool.flet.<platform>.icon_background` → `tool.flet.icon_background`), `:2198-2231` (`_resolve_icon_background` → `(255,255,255)` when unset, `:2218-2220`); `.venv/Lib/site-packages/flet_platform_assets/_models.py:83` (`IconOptions.background = WHITE`), `_icons.py:109-114` (iOS targets are `opaque=True`), `:140-159` (web maskables + apple-touch are `opaque=True`).
- **What:** the flatten colour is what the user actually sees on Apple platforms, and it is hardcoded to white because the app never sets it. The iOS 1024 marketing icon — the App Store listing image — is a white square; the macOS tile is white; the two web maskables and the apple-touch icon are white. The app's own dark background is `#121218` (`src/core/theme.py:17`).
- **Evidence:** the generated `Icon-App-1024x1024@1x.png` corner pixel is `(255, 255, 255)`, mode `RGB`; `IconOptions.background` defaults to `WHITE` (`_models.py:83`).
- **Fix / opportunity:** `icon_background = "#121218"` under `[tool.flet]` (global) or `[tool.flet.ios]`/`[tool.flet.macos]` (per-platform, `build_base.py:2194-2196`). **Same sequencing caveat as F3** — the artwork must become light-on-dark first (F6), otherwise the iOS icon becomes a dark square with a dark wordmark.
- **Risk if ignored:** the iOS home-screen icon and the App Store listing image are white, in a product whose entire surface area is near-black. (Latent: CI builds Android only, so this bites the moment an iOS target exists.)

### F5 · P2 · The splash is dark in *both* system modes although the app ships a real light theme

- **Where:** `pyproject.toml:39-41`; `.venv/Lib/site-packages/flet_cli/commands/build_base.py:1748-1758` (`color()` resolution → `splash.color` / `splash.dark_color`); `src/core/theme.py:10` (`LIGHT_BG = "#F4F4F8"`), `:17` (`DARK_BG = "#121218"`), `src/core/state.py:30` (`theme_mode = "system"`), `src/core/theme.py:43-72` (system-resolved light/dark).
- **What:** the app follows the system brightness and has a polished light palette, but the native launch screen is `#121218` unconditionally — a dark flash before a light UI on light-mode devices. The Android 12 splash is likewise dark in both modes (the `-night-` duplicates are simply not emitted when there is no dark artwork — `_splash.py:156-161`).
- **Evidence:** `pyproject.toml:40-41` `color = "#121218"` / `dark_color = "#121218"`; `src/core/theme.py:10,17`; `src/core/state.py:30` `theme_mode: str = "system"`.
- **Fix / opportunity:** `color = "#F4F4F8"` (the app's own `LIGHT_BG`) and `dark_color = "#121218"`, then supply **two** rasters: `src/assets/splash.png` (dark artwork for the light background) and `src/assets/splash_dark.png` (light artwork for the dark background). The two-artwork chain already exists — `resolve(f"splash_{platform}", "splash")` for light and `resolve(f"splash_dark_{platform}", "splash_dark")` for dark (`build_base.py:2379-2385`); note the dark pass has **no** fallback to the icon, so without `splash_dark.png` the night variant reuses the light art.
- **Risk if ignored:** a black-to-white flash on every cold start in light system mode, and the launch screen contradicts the theme the user chose.
- **Intent UNVERIFIED:** no entry in `docs/decisions.md` records whether the always-dark splash was deliberate (brand) or accidental (copy-paste of `dark_color`).

### F6 · P2 · Neither the PNG nor the SVG's dark variant is legible on `#121218` — the artwork itself must change, and the config lines must land with it

- **Where:** `src/assets/icon.png` (opaque artwork is `#2E353B`); `src/assets/icon.svg:8-13` (the palette block); `pyproject.toml:40-41` (`#121218`).
- **What:** there is no ready-made "light on dark" raster in the repo, and the obvious candidate — the SVG's own dark-mode palette — is **also unusable on `#121218`**: the SVG paints the *wordmark* light (`path.slate { fill: #f4f4f8 }`) but paints the **penguin in `#121218`**, which is *exactly* the splash background. Rasterising the dark variant would make the penguin vanish and leave only the braces and the wordmark. The light variant (what the PNG is) makes *everything* vanish.
- **Evidence:** `src/assets/icon.svg` style block:
  ```
  path.slate { fill: #2e343a; stroke: #2e343a; }
  path.mark  { fill: #ffffff; stroke: #ffffff; }
  @media (prefers-color-scheme: dark) {
    path.slate { fill: #f4f4f8; }
    path.mark  { fill: #121218; stroke: #121218; }
  }
  ```
  `#121218` (penguin, dark mode) == `pyproject.toml:40` (splash colour) → invisible. PNG opaque-pixel histogram is 100 % slate (`(46,53,59,254)` 5282, `(45,52,58,254)` 4383, … ; 9,275 opaque near-white pixels = the penguin's `fill-rule="evenodd"` outline strokes).
- **Fix / opportunity:** author one light-on-transparent mark for build use (slate `#f4f4f8` wordmark **and** a white/`#121218`-contrasting penguin — e.g. the penguin in white and the wordmark in `#f4f4f8`), export it as `src/assets/icon_android.png` (square, for the launcher) and `src/assets/splash.png` (for the launch screen), and export a *dark-on-transparent* variant for the light-mode surfaces if the light splash of F5 is adopted. **Sequencing matters:** adding `icon_background`/`adaptive_icon_background` (F3, F4) *before* the new art lands makes iOS, macOS, web and Android **worse** (dark art on a dark background). Land the art first, the config in the same commit.
- **Risk if ignored:** every "just set the colour" fix in F3/F4 makes the product less legible, and the team will conclude the package is at fault.

### F7 · P3 · `icon.svg` is inert in the build path; the PNG is a light-palette-only copy with no sync step

- **Where:** `src/assets/icon.svg` (42,905 bytes), `src/assets/icon.png` (99,177 bytes); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:3536-3542` (`.svg` is filtered out of every candidate list), `:3548-3559` (`.png` outranks everything), `:3566-3581` (an SVG-only directory logs a warning and falls back to the default icon); `.venv/Lib/site-packages/flet_platform_assets/_source.py:44-50` (Pillow-only loader).
- **What:** the vector master can never reach the renderer — `PIL.Image.open` cannot decode it (`UnidentifiedImageError: cannot identify image file 'src/assets/icon.svg'`), and flet-cli drops it before that. The PNG is a faithful raster of the SVG's **light** variant (SVG path extents `x [56.5, 970.5] y [258.9, 777.1]` vs PNG alpha bbox `x [53, 969] y [256, 779]`, i.e. the same geometry within rasterisation tolerance; slate `#2E353B` ≈ the SVG's `#2e343a`, ±1 from palette quantisation) but carries **none** of the SVG's `prefers-color-scheme: dark` variant. Nothing in the repo regenerates one from the other.
- **Evidence:** `Image.open('src/assets/icon.svg')` → `UnidentifiedImageError`; `build_base.py:3539` `ext == ".svg"` in `_incompatible`; the two extent measurements above.
- **Fix / opportunity:** keep `icon.svg` as the runtime source of truth (`src/components/brand_hero.py:17-29` reads it directly), and generate the build rasters **from** it — add a one-line documented export step (or a CI job) that rasterises the SVG into `src/assets/icon.png` / `icon_android.png` / `splash.png` so the vector master and the shipped pixels cannot drift. That is also where the light/dark palette decision (F6) belongs: one place, two exports.
- **Risk if ignored:** the in-app brand (SVG, tinted white in dark mode — `brand_hero.py:41`) and the shipped brand (PNG, slate) are *different artworks* in colour; a future edit to the SVG silently does not reach the launcher.

### F8 · P3 · `splash.icon_background` is unset, so the Android 12 splash icon canvas stays at 288 dp instead of the spec'd 240 dp

- **Where:** `pyproject.toml:39-41` (no `icon_background` / `icon_dark_background` / `icon_fit`); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2387-2393` (`icon_background=self.splash_setting("icon_background")`, `icon_dark_background=…`, `icon_fit=… or "contain"`), `:1695-1721` (`splash_setting`, platform-over-global, with the legacy aliases `icon_bgcolor`/`android_12_fit` at `:114-118`); `.venv/Lib/site-packages/flet_platform_assets/_splash.py:40-43` (`ANDROID_12_CANVAS_DP = 288`, `ANDROID_12_CANVAS_DP_WITH_BACKGROUND = 240`), `:195` (`dp = …WITH_BACKGROUND if background else …CANVAS_DP`), `:209` (`place(..., bg=parse_hex_color(background))`), `:203-207` (fit-to-circle).
- **What:** with `icon_background` unset the Android 12 splash icon is drawn on a 288 dp canvas and the platform's 240 dp variant (the one with an icon background) is never used; the icon circle is transparent and floats on the window background. The knob also *shrinks* the canvas to the platform-specified 240 dp and fills the visible circle with the colour — exactly what a dark splash needs.
- **Evidence:** `dp = ANDROID_12_CANVAS_DP_WITH_BACKGROUND if background else ANDROID_12_CANVAS_DP` (`_splash.py:195`); the rendered `drawable-xxxhdpi/android12splash.png` is 1152×1152 = 288 dp × 4, not 960×960.
- **Fix / opportunity:** `[tool.flet.splash] icon_background = "#121218"` (and `icon_dark_background = "#121218"` for symmetry) — one line each, `build_base.py:2390-2391`. The Android 12 icon then gets the spec'd 240 dp canvas with a brand-coloured circle.
- **Risk if ignored:** the Android 12 launch icon is drawn at a non-spec size and has no icon background of its own; a minor platform-compliance nit.

### F9 · P3 · The iOS and desktop renders are correct but never exercised; three platform knobs stay unused

- **Where:** `.github/workflows/app.yml:159,213` (only `flet build apk` / `flet build aab`); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:93-102` (`ICON_PLATFORMS`), `:120-126` (`SPLASH_PLATFORMS` — macOS/Windows/Linux have **no** splash); `pyproject.toml` (no `macos.icon_style`, no `web.pwa_theme_color`).
- **What:** I rendered every platform in isolation. The iOS set is 15 files, all `RGB` (alpha stripped, App Store requirement met — `_icons.py:109-114`); macOS gets 7 files with Apple's squircle+shadow grid applied (correct: `looks_pre_shaped(source)` → `False` for a wordmark, so `"auto"` composes the grid — `_icons.py:367-393`, verified visually); Windows gets a 4-entry `.ico` (16/32/48/256 — `_icons.py:71`); Linux gets the full 8-size hicolor tree plus `linux/app_icon.png` (`_icons.py:436-459`). The web set is favicon + 192 + 512 + 2 opaque maskables + an opaque apple-touch. All **structurally correct** — but never produced by this repo, and none of the three platform-specific knobs is set.
- **Evidence:** isolated render output — `ios 15 assets (all RGB)`, `macos 7 assets`, `windows ico sizes=[16, 32, 48, 256]`, `linux 9 assets` (8 hicolor + `linux/app_icon.png`), `web 6 assets` (2 RGB opaque + 4 RGBA). `build_base.py:2113` `macos_style = get_pyproject("tool.flet.macos.icon_style") or "auto"`; `build_base.py:1551-1554` `pwa_theme_color` → `None`.
- **Fix / opportunity:** no action while Android is the only target. When a desktop/iOS target is added: set `tool.flet.macos.icon_style` explicitly (keep `"auto"` — it is already correct for a wordmark) and `tool.flet.web.pwa_theme_color`; and re-run this audit's render script, because the wordmark legibility problem (F2) will reproduce on every square platform.
- **Risk if ignored:** low today; the moment a second platform is added, the same unreadable wordmark lands on iOS, macOS, Windows and Linux simultaneously.

## Verified-good list

- **No low-resolution asset anywhere.** The source is 1024×1024 and the largest target per platform is 1024 (iOS/macOS), 512 (web), 432 (Android adaptive), 256 (Windows) — `_warn_low_resolution` (`_icons.py:273-300`) never fires. Measured: `android max 432`, `ios max 1024`, `macos max 1024`, `windows max 256`, `web max 512`, all vs source 1024 → `OK`. The 2048 source cap (`_source.py:11-17`, `:66-75`) is not engaged.
- **Zero diagnostics from the whole pipeline.** 6 icon platforms + 3 splash platforms → `TOTAL WARNINGS: 0`. The source is square, high-resolution and already framed within tolerance, so `FRAMING_TOLERANCE` (`_icons.py:199`) skips every resample. The package is not flagging anything; the *configuration* is the problem.
- **The palette-mode PNG is handled correctly.** `src/assets/icon.png` is mode `P` with a `transparency` chunk; `load_source` converts it to RGBA (`_source.py:63-64`) and the alpha survives: `alpha min/max (0, 254)`, corner alpha 0 on all four corners, 9,275 opaque near-white pixels preserved. No alpha loss, no black-corner artefact.
- **iOS icons are alpha-free.** All 15 `Icon-App-*.png` come out `RGB` (flattened onto `options.background`) — the App Store's "no alpha channel" rule is met (`_icons.py:109-114`). The 1024 marketing icon is a true 1024×1024.
- **Web maskables and apple-touch are opaque.** `Icon-maskable-{192,512}.png` and `apple-touch-icon-192.png` come out `RGB` (`_icons.py:140-159`) — the "black corners on some Android launchers" failure mode is avoided.
- **macOS grid is applied, and correctly so.** `looks_pre_shaped(source)` → `False` (the wordmark is not a filled near-square tile), so `"auto"` composes Apple's squircle + shadow (`_icons.py:367-393`); the resulting `app_icon_1024.png` is a proper macOS tile. `tool.flet.macos.icon_style` is correctly left unset.
- **Android adaptive layers are created even though the template ships none.** `ICONS_CREATED_FRESH` contains `"android"` (`build_base.py:109`) → `declared_only=False` at `:2171` → all 5 `drawable-*/ic_launcher_foreground.png` (108/162/216/324/432) are written, not merely overwritten.
- **`icon.svg` next to `icon.png` does not confuse the lookup.** `.svg` is filtered (`build_base.py:3536-3542`) and `.png` wins deterministically via `ext_priority` (`:3548-3564`) — no warning, no ambiguity.
- **Stale launch-screen resources are removed.** The legacy flutter_native_splash `background.png` / `launch_background.xml` set is listed stale (`_splash.py:52-64`) and deleted by `write` (`_write.py:38-41`), so an old generator's files cannot keep being served.
- **Rebuilds are free.** The hash stamp covers the generator version, the template digest, the source mtime and the resolved options (`build_base.py:2088-2132`), so an unchanged asset set costs nothing.
- **The PWA background follows the splash colour.** `pwa_background_color` falls through to `splash["color"]` (`build_base.py:1542-1550`) → `#121218`, so an installed PWA does not flash white in front of a coloured splash.
- **The package is build-host-only and adds no runtime weight.** `uv.lock:228` places it under `flet-cli`; `uv.lock:253-258` shows `pillow` as its only dependency; `pyproject.toml:9-15` (runtime deps) contains neither. Confirmed by import inspection: the package imports only stdlib (`math`, `_imaging.py:18`) + Pillow + its own modules — no `flet`, no `flet-cli`.
- **The `tool.flet.icon` key is inert** (`pyproject.toml:28`) — re-verified here: `grep -rn "tool\.flet\.icon\b" flet_cli/ flet/` → no hits. The icon is found by convention at `src/assets/icon.png` (`build_base.py:2092`). The file is in the right place, so the outcome is correct by accident. (Same finding as the flet-cli report F5; listed so the synthesis does not count it twice.)

## Unverified

- **The exact Android launch-screen composition** (which drawable is layered over which colour resource, and with what gravity) lives in the pinned cookiecutter template. That template is **not** installed in `.venv` and **not** cached on this host (`~/.flet/cache` contains only `python-build/manifest-20260921.json`). The claims that `adaptive_icon_background` becomes the `ic_launcher_background` resource and that Android uses `@color/flet_splash_background` are cross-referenced from `docs/dependency-studies/flet-platform-assets.md:324` and `docs/swarm/dependency-utilization/flet-cli.md:131` (which downloaded it), **not** re-verified here.
- **Whether a real `flet build apk` reproduces my isolated render byte-for-byte.** The package is pure and the pipeline is hash-stamped, so the images must match — but no `build/` directory exists in the repo and Flutter/Android SDK are not provisioned on this host, so no end-to-end build was run. Every asset in this report was produced by calling the installed `flet_platform_assets` directly with the options that `build_base.py` resolves for `config_platform = "android"` (`build_base.py:194-211`).
- **Whether the always-dark splash is intentional.** No entry in `docs/decisions.md` covers the splash or the brand palette.
- **Whether an iOS/macOS/Windows/Linux target is planned.** CI builds Android only, so F4 and F9 are latent rather than live.
- **The Flutter-side boot screen.** `pyproject.toml:33-37` selects the built-in `"flet"` boot screen with a `startup_message`; its `bgcolor_light`/`bgcolor_dark` defaults live in the Dart client inside the same unavailable template, so the flash between the native launch screen and the boot screen is **not** verifiable here. The boot screen's own background is not part of flet-platform-assets' scope and is not audited.
- **The exact rasterisation of `icon.svg` to `icon.png`.** The two agree geometrically to within ~3 px and in palette to ±1 per channel, which is strong evidence they are the same artwork, but no SVG rasteriser is available on this host to prove a byte-level match.
- **Contrast ratios are WCAG-style relative-luminance ratios** computed from the measured sRGB pixels; they are a proxy for perceived legibility, not a platform guideline. The 1.48:1 and 17.01:1 figures are for the brand slate and the light slate against the `#121218` splash.
