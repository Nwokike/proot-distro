## What it does / how the app uses it

**It does not.** `python-dateutil` 2.9.0.post0 is installed in `.venv` and the app never touches it — not directly, not transitively, not even indirectly through a date-formatting call.

- **No app importer.** `grep -rn "dateutil" src/ tests/` → **0 hits**. `grep -rnE "^\s*(import|from)\s+(datetime|dateutil|tzdata|arrow|zoneinfo|pytz)" --include="*.py" src/` → **0 hits**. The only clock import in the whole app is `import time` at `src/services/ad_service.py:7`, used for a monotonic ad throttle (`:171`, `:179`).
- **No venv importer other than arrow.** `grep -rln "dateutil" .venv/Lib/site-packages/ --include="*.py" | grep -v "site-packages/dateutil/"` → exactly two files, both arrow: `.venv/Lib/site-packages/arrow/arrow.py:33-34` and `.venv/Lib/site-packages/arrow/util.py:6`.

- **Proven not in the shipped closure.** Walking `Requires-Dist` from the five runtime deps (`pyproject.toml:9-15`) yields exactly: `anyio, certifi, exceptiongroup, flet, flet-ads, flet-terminal, h11, httpcore, httpx, idna, msgpack, oauthlib, proot-distro, repath, six, typing-extensions`. `arrow` → **False**, `python-dateutil` → **False**, `tzdata` → **False**.

## Findings

### F1 · P1 · python-dateutil is 100% dev-only and 100% dormant — and an `import dateutil` in `src/` is a device-only crash
- **Where:** `pyproject.toml:9-15` (runtime deps = `flet`, `flet-ads`, `httpx`, `flet-terminal`, `proot-distro`), `pyproject.toml:77-84` (`flet-cli` in the dev group); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2566-2569` (only `project.dependencies` is read), `:2572-2575` (`tool.flet.<platform>.dependencies` appended), `:2606` (`package_args.extend(["-r", toml_dep])`); `.venv/Lib/site-packages/arrow/arrow.py:33-34`, `.venv/Lib/site-packages/arrow/util.py:6` (the only two importers in the venv); `docs/swarm/dependency-tree/uv-tree-inverted.txt:88-90`; `docs/decisions.md:12-13` (D-003: the runtime set is frozen, "Any addition needs owner sign-off").
- **What:** the host venv contains dateutil, so a desktop `flet run`, `pytest` and `ruff` all resolve `import dateutil` happily. The packaged app does not: `flet build` pip-installs exactly the PEP 621 `project.dependencies` into the device's site-packages, and dateutil is only reachable through `flet-cli → cookiecutter → arrow`, all of which are dev-group. So `import dateutil` in `src/` = `ModuleNotFoundError` on every Android device at startup, invisible to the entire host test loop.
- **Evidence:** the closure walk above (`arrow`/`python-dateutil`/`tzdata` → **False**). `arrow-1.4.0.dist-info/METADATA:25` `Requires-Dist: python-dateutil>=2.7.0`; `cookiecutter-2.7.1.dist-info/METADATA:36` `Requires-Dist: arrow`; `flet_cli-1.0.4.dist-info/METADATA:18` `Requires-Dist: cookiecutter>=2.6.0`. `ls requirements.txt` → "No such file or directory" (so the `requirements.txt` branch at `build_base.py:2608` is not taken either). Runtime proof of the only importer set: `grep -rln "dateutil" .venv/Lib/site-packages/ --include="*.py" | grep -v "site-packages/dateutil/"` → `arrow/arrow.py`, `arrow/util.py`.
- **Fix / opportunity:** none needed in code — the correct state today is **zero** dateutil usage, and it should stay that way. If a future feature genuinely needs a date library, that is a **D-003 dependency-set decision** (an `arrow` or `python-dateutil` entry in `project.dependencies` + a lock bump + owner sign-off), not a code change. Do not add `import dateutil` to `src/` on the strength of the host venv.
- **Risk if ignored:** the app fails to launch on the only shipping platform, with a stack trace no CI job can reproduce.

The study currently points at the wrong gaps.

### F3 · P2 · `dateutil.parser` is not even *loaded* by the arrow chain — the capability the study leads with has zero execution path in the entire stack
- **Where:** `.venv/Lib/site-packages/arrow/arrow.py:33-34` (`from dateutil import tz as dateutil_tz` / `from dateutil.relativedelta import relativedelta`) and `.venv/Lib/site-packages/arrow/util.py:6` (`from dateutil.rrule import WEEKLY, rrule`); the *only* consumers are `arrow/arrow.py:717`, `:720` (`span`), `:928`, `:934` (`is_ambiguous`/`is_imaginary`), `:1049-1053` (`shift`), `:1218-1220` (`__sub__`), and `arrow/util.py:50` (`next_weekday`); the cookiecutter side is `.venv/Lib/site-packages/cookiecutter/extensions.py:12` (`import arrow`), `:128` (`arrow.now(timezone)`), `:134` (`d.shift(**shift_params)`), `:144` (`arrow.now(timezone).strftime(datetime_format)`).
- **What:** the study's headline claim — *"every `{% now %}` render and every `Arrow.shift/to` call runs on dateutil's parser and tz machinery"* (`docs/dependency-studies/python-dateutil.md:40-42`) — is false on two counts. (a) `dateutil.parser` is **never imported** by arrow: `arrow.now(tz)` goes through stdlib `zoneinfo.ZoneInfo` (`arrow/factory.py:333-335` → `arrow/parser.py:928-936`), and `strftime` is pure stdlib, so the `{% now %}` path touches **zero** dateutil code. (b) The only dateutil code that *can* execute is `relativedelta`, via `arrow.Arrow.shift()` — which the `{% now %}` tag reaches **only** when the template supplies a shift offset (`extensions.py:134` `d.shift(**shift_params)`), and `Arrow.span()` (`:717`, `:720`) — which cookiecutter never calls. `rrule` is imported by `arrow/util.py:6` but `next_weekday()` (`:50`) is not called by the `{% now %}` path either.
- **Evidence:** runtime module-diff on the installed package — `import arrow` then diffing `sys.modules`:
  ```
  dateutil modules loaded by "import arrow":
     dateutil, dateutil._common, dateutil._version, dateutil.relativedelta,
     dateutil.rrule, dateutil.tz, dateutil.tz._common, dateutil.tz._factories,
     dateutil.tz.tz, dateutil.tz.win
  dateutil.parser loaded?           False
  dateutil.parser._parser loaded?   False
  dateutil.parser.isoparser loaded? False
  dateutil.easter loaded?           False
  six loaded?                       True
  ```
  And the fuzzy-parser capability the study headlines does work, it is simply never reached: `dateutil.parser.parse("Oct 16 2026 10am")` → `2026-10-16 10:00:00`; `dateutil.parser.isoparse("Oct 16 2026 10am")` → `ValueError: invalid literal for int() with base 10: b'Oct '`.
- **Fix / opportunity:** correct `docs/dependency-studies/python-dateutil.md:38-42` to say exactly which dateutil submodules arrow imports and which it does not. This matters because `dateutil.parser` is the *only* part of the package that would be genuinely hard to replace with the stdlib (fuzzy free-form parsing) — and it is the part that is **never loaded**. If a future date feature needs fuzzy parsing, the stdlib cannot do it, and then (and only then) a `python-dateutil` entry in `project.dependencies` is justified. Until then the honest statement is: **of the five dateutil submodules, the app uses none, and the arrow chain loads three of them at import time but executes one.**
- **Risk if ignored:** a future "parse the guest's `apt` log" feature gets built on `parser.parse` — a module that is not even in the shipped bundle — and crashes on device only.

### F4 · P2 · Every date surface the app *does* have has a stdlib or upstream answer; dateutil buys nothing
- **Where:** session age — `src/services/proot_service.py:406` (`"start_time": record.get("start_time")`), `.venv/Lib/site-packages/proot_distro/session.py:154` (`"start_time": time.time()`), `:320-323` (validated: not a bool, numeric, finite), `:332` (coerced to `float`), dropped at `src/app_controller.py:390-392`; image age — `src/services/proot_service.py:284-289` vs `.venv/Lib/site-packages/proot_distro/helpers/docker/cache.py:712-713` (`"created": _text(image_config.get("created"))`, `"cached_at": st.st_mtime`) and `.venv/Lib/site-packages/proot_distro/commands/list.py:228-248` (`_created_epoch`, RFC 3339 regex at `:49-52`), `:252-269` (`_fmt_age`, a 6-threshold "N units ago" formatter) and `:44` (`_IMAGE_HEADERS` includes `"CREATED"`); backup name — `src/app_controller.py:346-348` (`file_name=f"{container}.tar.gz"`) vs `.venv/Lib/site-packages/proot_distro/commands/backup.py:476-478` (hard refusal to overwrite an existing file).
- **What:** there are exactly **three** places where a date is genuinely wanted, and in all three the non-dateutil answer is at least as good:
  1. **Image age** — the only *parsing* job in the app is RFC 3339 → datetime. Python 3.14's `datetime.fromisoformat` parses RFC 3339 natively, including `Z` and fractional seconds, so `dateutil.parser.isoparse` (`dateutil/parser/isoparser.py:416`) buys nothing here. Proven at runtime: `datetime.fromisoformat("2026-10-16T12:00:00.123456789+00:00")` → `2026-10-16 12:00:00.123456+00:00`; `"...Z"` → `...+00:00`; `"...+02:00"` → `...+02:00`. And upstream already ships a complete relative-age formatter (`list.py:252-269`) that the app could reuse instead of re-deriving thresholds.
  2. **Session age** — `start_time` is already a validated epoch float; `datetime.fromtimestamp(ts, tz=timezone.utc).astimezone()` renders it tz-aware (ruff DTZ stays green — `ruff check src/ --select DTZ` → `All checks passed!`).
  3. **Backup file name** — a stamp is `datetime.now().astimezone().strftime("%Y%m%d-%H%M%S")`; pure stdlib, one call, no parsing involved.
  There is **no** recurrence job (no scheduled task, no rotation, no retention window, no expiry) → `rrule` has **no applicable surface at all**; and **no** timezone job (no user tz preference, no cross-zone display) → `relativedelta` and `dateutil.tz` have no applicable surface either.
- **Evidence:** the greps in F2 (no `datetime`/`dateutil`/`zoneinfo`/`arrow` import in `src/`; no schedule/retention/expiry concept) and the runtime `fromisoformat` results above. `ruff check src/ --select DTZ` → `All checks passed!`; `ruff check src/` → `All checks passed!` — so the codebase is already clean for a first date feature, provided the first one uses tz-aware values.
- **Fix / opportunity:** when the timestamp gaps are closed (they are real gaps — the arrow audit's F3/F4/F7), use the **stdlib**: `datetime.fromisoformat` for the RFC 3339 `created` field, `datetime.fromtimestamp` for `start_time`, `strftime` for the backup name, and reuse upstream's `_fmt_age` thresholds (`proot_distro/commands/list.py:252-269`) rather than re-deriving them. `dateutil` should not be added for this. Per D-003 (`docs/decisions.md:12-13`) nothing needs to change in `pyproject.toml`.
- **Risk if ignored:** the temptation to reach for `python-dateutil` "since it is already installed" — which is exactly the trap F1 describes: installed on the host, absent on the device.

### F5 · P2 · `changelog.notes_for()` falls back to the **oldest** entry, not the newest as its docstring promises
- **Where:** `src/core/changelog.py:16-18` —
  ```python
  def notes_for(version: str) -> str:
      """The changelog entry for a version, falling back to the newest one."""
      return CHANGELOG.get(version) or next(iter(CHANGELOG.values()), "")
  ```
  `CHANGELOG` is a `dict[str, str]` at `src/core/changelog.py:5-13` (currently one entry, `"1.0.0"`), and dicts preserve insertion order, so `next(iter(CHANGELOG.values()))` is the **first-inserted** entry. The single caller is `src/components/update_dialog.py:89` (`notes_for(APP_VERSION)`), rendered inside the "You're up to date" dialog (`:83-100`). The only test is `tests/test_version_sync.py:29-31` (`assert APP_VERSION in CHANGELOG; assert notes_for(APP_VERSION)`) — it never exercises the fallback branch.
- **What:** the docstring and the implementation disagree. Today the dict has one entry, so "first-inserted" and "newest" coincide and nothing is visibly wrong. The moment a second release is added — and the natural way to add it is to append `"1.0.1": ...` after the existing key — the fallback silently returns the **1.0.0** notes for any unknown version, i.e. the *oldest* changelog, not the newest. The dialog would show a stale "What's New" to a user whose build number does not match any entry.
- **Evidence:** reproduced against a copy of the dict (the source file was not modified):
  ```
  single entry, unknown version -> 'notes-1.0.0'
  two entries (appended), unknown version -> 'notes-1.0.0'     # <-- 'notes-1.0.1' expected
  docstring says: falling back to the NEWEST one
  ```
  `src/core/changelog.py:18` is the only place the fallback is computed; `grep -rn "changelog\|notes_for" src/` → `src/components/update_dialog.py:15,89` and `src/core/changelog.py:16,17` only.
- **Fix / opportunity:** make the fallback match the docstring — e.g. `next(reversed(CHANGELOG.values()), "")` (dict views are reversible in Python 3.8+), or state the invariant in the docstring and add a test that inserts a second entry and asserts the *newest* is returned. This is a one-line change in the app's own file; it needs no dependency.
- **Risk if ignored:** a user on a build whose version has no changelog entry sees the *oldest* release's "What's New" — misleading, and invisible until the second release ships. Low blast radius, but it is a genuine, provable defect in one of the audited files.

### F6 · P3 · `dateutil.tz.gettz()` is the one capability that is genuinely dateutil-only on Android: it carries its own tz database
- **Where:** `.venv/Lib/site-packages/dateutil/tz/tz.py:1654-1655` (the `gettz` fallback: `from dateutil.zoneinfo import get_zonefile_instance` / `tz = get_zonefile_instance().get(name)`), `:1679` (`gettz = __get_gettz()`), `:1470` (`def __get_gettz()`); `.venv/Lib/site-packages/dateutil/zoneinfo/__init__.py:80` (`get_zonefile_instance`), `:30` (`class ZoneInfoFile`), `:54` (`def get`); the payload `.venv/Lib/site-packages/dateutil/zoneinfo/dateutil-zoneinfo.tar.gz` (156 400 bytes, shipped in the wheel); stdlib `zoneinfo/_common.py:4-29` (`load_tzdata` reads the **`tzdata` package**, raising `ZoneInfoNotFoundError` when it is absent).
- **What:** on a phone there is no OS zoneinfo tree, so stdlib `zoneinfo.ZoneInfo("Europe/Lisbon")` needs the `tzdata` **package** — which is dev-group-only here. `dateutil.tz.gettz()` needs no such package: it falls back to the tz database dateutil **ships inside its own wheel** (598 zones, verified at runtime). This is the sharpest technical difference between dateutil and the stdlib here, and it is the one capability the app could not get from `datetime` alone without adding a *second* dependency. It is also the one place where the sibling arrow report's reasoning needs a dateutil-specific correction: arrow's named-zone path (`arrow/parser.py:928-936` → stdlib `ZoneInfo`) **does** need `tzdata`; dateutil's `gettz` does not.
- **Evidence:** runtime on this host, where `zoneinfo.TZPATH` is `()` and dateutil's own `TZPATHS` has **no** existing directory: `dateutil.tz.gettz('Africa/Lagos')` → `tzfile('Africa/Bangui')`, `utcoffset(2026-10-16)` → `1:00:00`; `gettz('America/New_York')` → `tzfile('America/New_York')`, offset `-1 day, 20:00:00`; `gettz('Asia/Tokyo')` → `tzfile('Japan')`, offset `9:00:00`. `get_zonefile_instance()` reports **598** zones and `'Africa/Lagos' in zi.zones` → `True`. DST correctness: `tz.datetime_exists(datetime(2026,3,8,2,30, tzinfo=gettz('America/New_York')))` → `False` (`tz/tz.py:1683`).
- **Fix / opportunity:** **none today.** The app has no timezone preference, no cross-zone display, and device-local display needs no tz database at all (`arrow.now()` uses the device's local offset, `arrow/arrow.py:195-198`). Record this as the *reason* to reconsider dateutil if a user-facing "timezone" preference is ever specced — and at that point `gettz` is a stronger argument than `arrow` alone, because it removes the `tzdata` sub-dependency. If the app only ever shows device-local times, the stdlib is sufficient and D-003 says don't add anything.
- **Risk if ignored:** low. The real risk is the *opposite* one: adding `arrow` for named zones (per the arrow audit's F6) and shipping `tzdata` to the device for a feature that does not exist.

### F7 · P3 · The `six` / `python-dateutil` pair is split across the ship boundary — `six` ships, `python-dateutil` does not
- **Where:** `.venv/Lib/site-packages/flet-1.0.4.dist-info/METADATA:16` (`Requires-Dist: repath>=0.9.0`) → `.venv/Lib/site-packages/repath-0.9.0.dist-info/METADATA:20` (`Requires-Dist: six (>=1.9.0)`); the importer is `.venv/Lib/site-packages/repath.py` (`grep -rln "import six\|from six" .venv/Lib/site-packages/ --include="*.py"` → `repath.py` + the eight `dateutil/*` files); dateutil's own use of six is `dateutil/rrule.py:18,20`, `dateutil/relativedelta.py:8`, `dateutil/parser/_parser.py:42-43`, `dateutil/parser/isoparser.py:17,29,35`, `dateutil/tz/tz.py:19-21`, `dateutil/tz/_common.py:1`, `dateutil/tz/_factories.py:5`, `dateutil/tz/win.py:13-14`. `docs/swarm/dependency-tree/uv-tree-inverted.txt:88-91` shows six's two parents: `python-dateutil` **and** `repath`.
- **What:** the two packages look like a pair in the lockfile but are not the same tier. **`six` ships to the device** (through `flet → repath → six`, both in the runtime closure); **`python-dateutil` does not** (its only path is the dev group). The practical consequence: a developer who sees `six` in the device's site-packages and `python-dateutil` next to it in the host venv can easily assume both are available. The repo's own `docs/dependency-studies/six.md:40-42` already gets this right for `six` ("dateutil is NOT in our dependency closure … on OUR path the reverse-dependency set is exactly `{repath}`") — the dateutil study never says the same about itself.
- **Evidence:** the runtime-closure walk in F1 lists `six` → **True**, `python-dateutil` → **False**. `python_dateutil-2.9.0.post0.dist-info/METADATA` → `Requires-Dist: six >=1.5`.
- **Fix / opportunity:** no code change. Add one line to `docs/dependency-studies/python-dateutil.md` stating the tier explicitly: *"python-dateutil is build-host-only (via `arrow` ← `cookiecutter` ← `flet-cli`, dev group); its sibling `six` **does** ship, via `flet → repath → six`."* The same paragraph should note that `dateutil` is the one package in the closure that would be **imported** by nothing on the device — so a stray `import dateutil` fails at app start, not at feature use.
- **Risk if ignored:** low individually; it is a navigation hazard for the next engineer who greps the venv instead of the shipped set.
