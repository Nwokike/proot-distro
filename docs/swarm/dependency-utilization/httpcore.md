# httpcore 1.0.9 utilization — audit

**Verdict:** MIXED
**Confidence:** high
**Scope:** `docs/dependency-studies/httpcore.md`; `docs/reference/dep-httpx-cluster.md`; `src/services/update_service.py`; `src/app_controller.py`; `src/components/update_dialog.py`; `src/screens/views.py`; `src/core/constants.py`; `src/main.py`; `pyproject.toml`; `uv.lock`; `tests/test_imports_vs_deps.py`; `.venv/Lib/site-packages/httpcore/`; `.venv/Lib/site-packages/httpx/_transports/default.py`; `.venv/Lib/site-packages/httpx/_client.py`; `.venv/Lib/site-packages/httpx/_config.py`; `.venv/Lib/site-packages/httpx/_types.py`; `.venv/Lib/site-packages/flet/auth/`; `.venv/Lib/site-packages/proot_distro/helpers/download.py`; `.venv/Lib/site-packages/proot_distro/helpers/docker/` · **Date:** 2026-10-20

## What it does / how the app uses it

httpcore 1.0.9 is a **pure-Python HTTP/1.1 + HTTP/2 engine and connection-pool implementation** that sits *under* httpx. It owns the socket layer: TCP connect, TLS, the h11 state machine, keep-alive connection reuse, proxy tunnelling, and the per-phase timeout semantics. The app never imports it.

The **only** runtime path to httpcore in this app is indirect and single-threaded:

```
src/app_controller.py:88        page.run_task(self._check_for_updates)
  → src/app_controller.py:309-317  _check_for_updates() → services.update_service.check_for_update()
    → src/services/update_service.py:73   import httpx            (function-local import)
    → src/services/update_service.py:75   httpx.AsyncClient(timeout=4.0, follow_redirects=True)
      → httpx/_transports/default.py:300-311   httpcore.AsyncConnectionPool(...)
        → httpcore/_async/connection.py:69    AsyncHTTPConnection.handle_async_request
          → httpcore/_async/http11.py:65      AsyncHTTP11Connection  (h11 state machine)
            → httpcore/_backends/anyio.py:98  AnyIOBackend.connect_tcp  (anyio → socket)
```

`grep -rn "httpcore" src/` returns exactly **one** hit: `src/screens/views.py:34`, the string `"httpcore"` in the `_PY_DISTS` license-display tuple — a name in the licenses screen, not an import. There is no `import httpcore` anywhere in `src/`.

**Verdict on direct reach: the app does NOT reach httpcore directly — correct, and enforced.** `tests/test_imports_vs_deps.py:46-59` fails the build for any `src/` import whose top-level module is not in `[project].dependencies` (`pyproject.toml:9-15` declares `httpx`, not `httpcore`). I proved this by temporarily adding `import httpcore` to a probe file under `src/`: the test failed with `imports without a declared dependency: src\_tmp_guard_probe.py: httpcore`. (Probe deleted; no code was modified.) So httpcore stays a transitive dependency of httpx, which is the architecture the house rules require (D-001-style one-importer discipline; D-003 freezes the dependency set).

**Is it dormant?** Partly, and it is more dormant than the app's own traffic warrants. The *async* half of httpcore is genuinely live: the update check runs at every app start and the request really does traverse `AsyncConnectionPool → AsyncHTTPConnection → AsyncHTTP11Connection → AnyIOBackend`. The *sync* half (`httpcore/_sync/`, 95,631 bytes of `.py`) is unreachable — verified: `httpcore._sync.connection_pool` is imported as a side effect of `httpcore/__init__.py:39-47` but no code path calls it. The HTTP/2 and SOCKS branches are **structurally dead**: `h2` and `socksio` are not installed (live check: `ModuleNotFoundError: No module named 'h2'` / `'socksio'`), so `httpcore/_async/__init__.py:7-28` substitutes stubs that raise `RuntimeError` on construction, and `httpx.AsyncClient(http2=True)` / `proxy="socks5://..."` raise `ImportError` at the httpx layer before httpcore is even consulted.

## Findings

### F1 · P2 · httpcore's connect-retry and pooling machinery is entirely unused; the update check pays a fresh TLS handshake every run and gives up on the first failure

- **Where:** `src/services/update_service.py:75` (`httpx.AsyncClient(timeout=4.0, follow_redirects=True)`); `.venv/Lib/site-packages/httpx/_transports/default.py:291` (`retries: int = 0`) and `:309` (`retries=retries`); `.venv/Lib/site-packages/httpcore/_async/connection.py:19` (`RETRIES_BACKOFF_FACTOR = 0.5`), `:25` (`exponential_backoff`), `:110-111` (`retries_left = self._retries`), `:159-165` (the retry loop); `.venv/Lib/site-packages/httpcore/_async/connection_pool.py:52-54` (`max_connections=10`, `max_keepalive_connections=None`).
- **What:** httpx's default `AsyncHTTPTransport` is constructed with `retries=0`, which httpx forwards verbatim to `httpcore.AsyncConnectionPool(retries=0)` (`_transports/default.py:309`). httpcore's exponential-backoff connect-retry therefore never runs. The app also builds a *fresh* `AsyncClient` per call, so the pool is created and destroyed around a single request: httpcore's keep-alive machinery (`AsyncHTTP11Connection._response_closed` returning the connection to IDLE at `_async/http11.py:238-248`; pool expiry at `_async/connection_pool.py:284-299`) has nothing to reuse. The `max_connections=100` / `max_keepalive_connections=20` / `keepalive_expiry=5.0` that httpx actually passes (verified live from `client._transport._pool`) are irrelevant to a one-shot client.
- **Evidence:** live run against a local socket server that accepts then closes: `retries=0 -> ConnectError attempts: 1 elapsed 0.16s`; `retries=2 -> ConnectError attempts: 3 elapsed 0.56s` (the extra attempts are httpcore's `exponential_backoff`, `_async/connection.py:25-35`). Live TCP-connection count against a keep-alive server: one client issuing two requests opened **1** connection; two clients issuing one request each opened **3** connections — i.e. the current per-call client pattern forfeits reuse entirely.
- **Fix / opportunity:** (a) `httpx.AsyncClient(timeout=..., follow_redirects=True, transport=httpx.AsyncHTTPTransport(retries=2))` turns on httpcore's connect-retry with no new dependency. (b) Hoist one long-lived `AsyncClient` (or accept an injected `client:` parameter) so the pool survives across the startup check and the manual re-check, giving keep-alive reuse.
- **Risk if ignored:** on a flaky mobile network, one TCP/TLS blip silently kills the update check for the whole session, and every check pays a full TLS handshake to `raw.githubusercontent.com` (battery/radio cost). The failure is invisible: `update_service.py:100-102` logs at `logger.debug` while the root logger is at `INFO` (`src/main.py:12-14`).
- **Caveat on (a):** passing a custom `transport=` **disables httpx's automatic environment-proxy mounting** (`httpx/_client.py:1399-1400`: `allow_env_proxies = trust_env and transport is None`). Verified live: with `HTTPS_PROXY` set, the default client mounts an `https://` proxy transport whose pool is `httpcore.AsyncHTTPProxy`, while a client built with `transport=httpx.AsyncHTTPTransport(retries=2)` mounts **nothing**. On a device with a corporate proxy, use `mounts=` explicitly or accept the trade.

### F2 · P2 · httpcore's read timeout is per-socket-read, not a total deadline — a trickling server can hold the check open indefinitely

- **Where:** `src/services/update_service.py:75` (`timeout=4.0` → `Timeout(connect=read=write=pool=4.0)`, verified live); `.venv/Lib/site-packages/httpcore/_async/http11.py:199-203` (`_receive_response_body` reads `timeouts.get("read")` and passes it to *each* `_receive_event` call) and `:209-219` (each `_receive_event` does one `self._network_stream.read(self.READ_NUM_BYTES, timeout=timeout)`); `.venv/Lib/site-packages/httpcore/_backends/anyio.py:25-37` (`anyio.fail_after(timeout)` wraps a *single* `receive()`).
- **What:** httpcore applies `Timeout.read` **per read event** (64 KiB chunks, `READ_NUM_BYTES = 64 * 1024` at `_async/http11.py:44`), never as a wall-clock budget for the response. A server that sends one byte every 0.4 s never has a single read exceed 4 s, so the request never times out. Each redirect hop also gets a fresh budget (`httpx/_client.py:1679-1711`).
- **Evidence:** live drip server (headers + `ab`, then one byte every 0.5 s, 20 bytes total) under `httpx.AsyncClient(timeout=4.0)`: **`completed 20 elapsed 9.2s`** — 2.3× the nominal 4 s budget, no exception raised. A 0.4 s drip under `timeout=1.0` completed in 1.8 s. A truncated body raised `httpx.RemoteProtocolError: peer closed connection without sending complete message body (received 9 bytes, expected 100)`.
- **Fix / opportunity:** wrap the request in `async with asyncio.timeout(15):` (or a `asyncio.timeout` around the whole `check_for_update` body) to impose a total deadline that httpcore's per-phase timeouts cannot express. Keep the per-phase timeouts for fast failure on connect.
- **Risk if ignored:** a slow-drip endpoint keeps the background task and its socket alive for the session; the task's `Future` is discarded (`app_controller.py:88`) and `page.on_close` (`main.py:24-31`) never cancels it, so the leak is unbounded. The UI itself is not blocked (the check runs via `page.run_task`).
- **Note:** the httpx-layer audit (`docs/swarm/dependency-utilization/httpx.md`, F7) flags the same class of problem from the httpx side; this finding pins the exact httpcore mechanism and the measured behaviour.

### F3 · P3 · httpcore's byte-level `Trace` hook is a free, unused diagnostic channel for the check that currently fails silently

- **Where:** `.venv/Lib/site-packages/httpcore/_trace.py:11` (`class Trace`), `:21-22` (`self.trace_extension = ... request.extensions.get("trace")`), `:30-37` (sync callback), `:69-78` (async callback); the httpcore call sites are `.venv/Lib/site-packages/httpcore/_async/connection.py:123` (`connect_tcp`), `:155` (`start_tls`), `:164` (`retry`) and `.venv/Lib/site-packages/httpcore/_async/http11.py:83` (`send_request_headers`), `:87` (`send_request_body`), `:97` (`receive_response_headers`), `:333` (`receive_response_body`), `:134`/`:347` (`response_closed`). httpx forwards the extension unchanged: `.venv/Lib/site-packages/httpx/_client.py:1761` (`extensions: RequestExtensions | None` on `get`) → `httpx/_transports/default.py:391` (`extensions=request.extensions` into `httpcore.Request`).
- **What:** the app passes no `extensions=` to `client.get` (`update_service.py:76`), so httpcore's tracing is off and the only diagnostic left is `logger.debug("Update check failed (expected if offline): %s", exc)` at `update_service.py:101` — invisible at the app's `INFO` root level (`main.py:12-14`). httpcore's `Trace` is reachable *through httpx's public API* without the app importing httpcore, so this does not violate the "don't reach httpcore directly" rule or the import guard.
- **Evidence:** live run of `client.get(url, extensions={"trace": cb})` against a local server produced exactly the httpcore event stream: `connection.connect_tcp.started` / `.complete`, `http11.send_request_headers.started` / `.complete`, `http11.send_request_body.started` / `.complete`, `http11.receive_response_headers.started` / `.complete`, `http11.receive_response_body.started` / `.complete`, `http11.response_closed.started` / `.complete`.
- **Fix / opportunity:** pass `extensions={"trace": cb}` on the update request, where `cb` logs phase name + timing at `INFO`/`WARNING` (or records a per-phase breakdown) so a failed check says *which* phase failed (connect / TLS / headers / body) instead of nothing. Note the async contract: the callback must be a coroutine function — a plain `def` raises `TypeError: If you're using an asynchronous interface, the callback of the 'trace' extension should be an asynchronous function rather than a normal function` (verified live; source `_trace.py:72-78`).
- **Risk if ignored:** "the check silently did nothing" stays undiagnosable in release builds. Cheap, dependency-free fix; the same channel will serve the M3 OCI download work.

### F4 · P3 · The whole async pool is configured at httpx's stock defaults, which are wrong for a mobile radio

- **Where:** `src/services/update_service.py:75` (no `limits=`, no `timeout` phases, no `http2=`, no `proxy=`); `.venv/Lib/site-packages/httpx/_config.py:247` (`DEFAULT_LIMITS = Limits(max_connections=100, max_keepalive_connections=20)`), `:178` (`keepalive_expiry: float | None = 5.0`), `:246` (`DEFAULT_TIMEOUT_CONFIG = Timeout(timeout=5.0)`); `.venv/Lib/site-packages/httpx/_transports/default.py:302-304` (the three values httpx hands to `httpcore.AsyncConnectionPool`).
- **What:** the live pool config is `max_connections=100, max_keepalive_connections=20, keepalive_expiry=5.0` — httpx's desktop defaults, not a deliberate mobile choice. `keepalive_expiry=5.0` is short: an idle connection is dropped after 5 s, so a background check separated from a foreground one by more than 5 s pays a new handshake anyway. And `max_connections=100` describes a concurrency the app never has (it issues exactly one request). These are not bugs at today's scale; they are the *absence* of a decision, and they are the knobs httpcore exposes for a future multi-connection OCI download.
- **Evidence:** live introspection of `httpx.AsyncClient(timeout=4.0, follow_redirects=True)._transport._pool` → `pool._max_connections=100`, `pool._max_keepalive_connections=20`, `pool._keepalive_expiry=5.0`, `pool._http1=True`, `pool._http2=False`, `pool._retries=0`, `pool._network_backend=AutoBackend`.
- **Fix / opportunity:** when the client is hoisted to app scope (F1), pass an explicit `httpx.Limits(max_connections=4, max_keepalive_connections=2, keepalive_expiry=60.0)` and `httpx.Timeout(10.0, connect=5.0)`. These are the same four parameters httpcore's `AsyncConnectionPool.__init__` takes (`_async/connection_pool.py:48-62`), so no httpcore import is needed.
- **Risk if ignored:** low today (one request). It becomes a real radio/battery cost the moment the M3 download path issues concurrent requests — and it will be tuned by accident, at httpx's desktop defaults, rather than by choice.

### F5 · P3 · httpcore's proxy support is unreachable: the app has no proxy configuration at all

- **Where:** `grep -rn "proxy\|PROXY" src/` → **no hits** (no proxy setting, no proxy UI, no `proxy=` argument). httpx's only proxy entry points are the constructor argument (`httpx/_client.py:1364`), `mounts=` (`:1365`), and environment variables via `trust_env` + `get_environment_proxies()` (`httpx/_client.py:1399-1400`, `httpx/_utils.py:30-46`).
- **What:** httpcore ships a complete authenticated-proxy stack — `AsyncHTTPProxy` with `proxy_auth` / `proxy_headers` (`.venv/Lib/site-packages/httpcore/_async/http_proxy.py:54`, `:59-76`), `AsyncTunnelHTTPConnection` for CONNECT tunnelling (`:233`, `:265`), and `AsyncSOCKSProxy` — and httpx wires all of it (`_transports/default.py:313-354`). The app uses none of it. On Android there are no `HTTP_PROXY` environment variables either, so even httpx's env-based auto-mount is inert on device (verified: `getproxies_environment()` reads only `*_proxy` env vars; `getproxies_registry()` is Windows-registry-only and returns `{}` elsewhere, so the desktop path also differs from the device path).
- **Evidence:** live check with `HTTPS_PROXY` set — the default client mounted an `https://` transport whose pool was `httpcore.AsyncHTTPProxy`; with a custom transport it mounted nothing (see F1 caveat). No proxy entry exists in `src/`.
- **Fix / opportunity:** if a proxy setting is ever wanted in Settings, httpcore/httpx already provide it end-to-end (`httpx.AsyncClient(proxy="http://user:pass@host:port")` → `httpcore.AsyncHTTPProxy` with `proxy_auth` and CONNECT tunnelling for https). Cost is a Settings field plus a stored value; no new dependency, and SOCKS stays out of scope (`socksio` is not installed and D-003 forbids adding it).
- **Risk if ignored:** enterprise/campus users behind an authenticating proxy cannot check for updates. Note this is a *feature gap*, not a defect — no proxy is the current, defensible default.

### F6 · P3 · The future OCI download path does not run through httpcore at all — the capability the study advertises is not reachable from this app's architecture

- **Where:** the app's install path is `src/services/proot_service.py:212-223` → `proot_distro.commands.install.command_install` → `.venv/Lib/site-packages/proot_distro/commands/install.py:320` (`pull_image`) → `.venv/Lib/site-packages/proot_distro/helpers/docker/pull.py:435` → `.venv/Lib/site-packages/proot_distro/helpers/docker/layers.py:44` (`download_blob`) → `.venv/Lib/site-packages/proot_distro/helpers/docker/transport.py:344` (`with http_opener().open(req, timeout=timeout) as resp`). `http_opener()` is a **urllib** opener (`.venv/Lib/site-packages/proot_distro/helpers/download.py:373-407`), built from `urllib.request.ProxyHandler`/`HTTPHandler`/`HTTPSHandler`.
- **What:** the OCI download — the one place httpcore's pooling, streaming and backpressure would genuinely pay off — is executed entirely by upstream `proot-distro` over stdlib `urllib`. httpcore/httpx is nowhere in that path. Upstream's own urllib layer already does the things the study attributed to httpcore: a 120 s per-step socket timeout (`download.py:108`), a shared retry policy with 5 attempts and a 5 s delay (`download.py:512-536`), a redirect policy that refuses HTTPS→HTTP downgrade (`download.py:292`, `transport.py:138-159`), streaming to disk in 64 KiB chunks with a SHA-256 digest check (`layers.py:76-116`), and a size-bounded metadata path (`transport.py:93`, `MAX_METADATA_BYTES = 16 MiB`).
- **Evidence:** the file/line chain above; `grep -rln "httpx\|httpcore" .venv/Lib/site-packages/proot_distro/` → no matches. `proot_service.py` imports only `proot_distro.*`.
- **Fix / opportunity:** **none, and deliberately so.** D-001 forbids forking or vendoring upstream, and upstream offers no injection seam for the transport (`transport.py:176-192` builds a module-level `_verified_opener`; there is no pluggable opener parameter). Re-implementing the registry client in the app to route it through httpcore would duplicate upstream's digest-verifying, retrying, redirect-hardening downloader for no user-visible gain — and would break the one-importer-per-service rule the house standards impose. The correct reading of `docs/dependency-studies/httpcore.md` §14-§15 for this app is: **httpcore's download advantages are upstream's business, not ours.**
- **Risk if ignored:** the risk is planning risk, not a defect — a future milestone that "moves OCI downloads onto httpcore/httpx for pooling and streaming" would be re-implementing upstream and is out of bounds. If the app ever needs a *supplementary* download of its own (e.g. fetching a release asset the feed points at), that new downloader is the one place httpcore's `AsyncConnectionPool` + `stream()` + `Trace` would be the right tool — and it would be a genuinely new module, not a modification of upstream's.

## Missed capabilities (dependency audits only)

- **`Trace` request extension** · API: `httpcore/_trace.py:11-107`, activated by `request.extensions["trace"]`; reachable from httpx via `client.get(url, extensions={"trace": cb})` (`httpx/_client.py:1761` → `httpx/_transports/default.py:391`) · Integration point: `src/services/update_service.py:76` — add `extensions=` to the request, log the phase stream · Value: turns F2's silent failure into a per-phase diagnosis (connect / TLS / headers / body) at zero dependency cost; the async callback contract must be honoured (`_trace.py:72-78`) · Cost: ~10 lines, no new package.
- **Connect-level retry with exponential backoff** · API: `httpcore.AsyncConnectionPool(retries=…)` (`_async/connection_pool.py:57`) → `AsyncHTTPConnection._connect` retry loop (`_async/connection.py:110-111`, `:159-165`, `RETRIES_BACKOFF_FACTOR = 0.5` at `:19`) · Integration point: `httpx.AsyncHTTPTransport(retries=2)` passed as `transport=` at `update_service.py:75` · Value: survives transient mobile-network connect failures; measured 1 attempt → 3 attempts · Cost: one keyword argument, but it disables httpx's env-proxy auto-mount (`httpx/_client.py:1399-1400`) — pair it with explicit `mounts=` or accept the trade on a proxy-less device.
- **Real connection pooling / keep-alive** · API: `AsyncConnectionPool(max_connections, max_keepalive_connections, keepalive_expiry)` (`_async/connection_pool.py:48-62`), surfaced as `httpx.Limits` (`httpx/_config.py:159-198`) · Integration point: one app-scoped `AsyncClient` owned by `AppController` and closed from `page.on_close` (`src/main.py:24-31`) · Value: one TLS handshake instead of two across the startup + manual checks; the seam also unlocks `httpx.MockTransport` for offline tests · Cost: a lifecycle change; beware module-level globals across Flet sessions.
- **Per-phase `Timeout` + an overall deadline** · API: `httpx.Timeout(connect=, read=, write=, pool=)` (`httpx/_config.py:72-88`, `:246`); httpcore's per-event semantics at `_async/http11.py:199-203` and `_backends/anyio.py:33` · Integration point: `update_service.py:75` (phase split) plus an `asyncio.timeout(...)` wrapper for the total deadline httpcore cannot express · Value: fail fast on an unreachable host, tolerate a slow cellular read, and bound the pathological case (F2) · Cost: ~5 lines.
- **Streaming with a hard byte cap** · API: `AsyncClient.stream()` (`httpx/_client.py:1543`), `Response.aiter_bytes()` (`httpx/_models.py:982`), `Response.num_bytes_downloaded` (`httpx/_models.py:856`); below it, httpcore's `PoolByteStream` (`_async/connection_pool.py:389-420`) and `HTTP11ConnectionByteStream` (`_async/http11.py:324-342`) · Integration point: `update_service.py:76` — stream and abort past ~1 MiB before parsing · Value: bounds memory against a hostile/incorrect feed; the repo's `version.json` is ~0.5 KB, so 1 MiB is ample headroom · Cost: ~10 lines. This is the httpcore-native version of the httpx-layer finding F3 there.
- **`MockBackend` / `AsyncMockBackend` for socket-free tests** · API: `httpcore/_backends/mock.py:58` and `:119`, exported at `httpcore/__init__.py:18` · Integration point: only reachable if the app ever drives httpcore directly — it does not, and should not (the import guard at `tests/test_imports_vs_deps.py:46-59` would fail the build) · Value: n/a today; `httpx.MockTransport` (`httpx/_transports/mock.py:15-29`) is the correct seam at the httpx layer and is already recommended by the httpx-layer audit · Cost: prefer MockTransport; do not add an httpcore import.
- **Authenticated HTTP proxy** · API: `httpcore.AsyncHTTPProxy(proxy_url, proxy_auth, proxy_headers, proxy_ssl_context)` (`_async/http_proxy.py:54`, `:59-76`) with CONNECT tunnelling at `:233`/`:265`; SOCKS is unavailable (`socksio` not installed) · Integration point: a future Settings field, passed as `httpx.AsyncClient(proxy=...)` · Value: enterprise/campus users behind an authenticating proxy can check for updates · Cost: a UI field + persisted value; no new dependency; SOCKS explicitly out of scope under D-003.
- **HTTP/2** · API: `httpcore.AsyncHTTP2Connection` (`_async/http2.py:42`) — **not usable**: `h2` is not installed, so httpx raises `ImportError` (`_client.py:1390-1397`) before httpcore is reached, and httpcore's own stub raises `RuntimeError` (`_async/__init__.py:11-16`) · Value: would let the OCI registry multiplex streams — but that traffic is upstream's urllib path (F6), and D-003 freezes the dependency set, so `h2` cannot be added · Cost: **not actionable.** Recorded so no milestone plans around it.

## Verified-good list

- The app **never imports httpcore directly** — the correct architecture. `grep -rn "httpcore" src/` → one hit, `src/screens/views.py:34`, a string in the license-display tuple `_PY_DISTS`, not an import. The build enforces it: `tests/test_imports_vs_deps.py:46-59` fails on any undeclared `src/` import; a temporary probe importing httpcore under `src/` did fail the test (probe removed; no code changed).
- httpcore is **not an orphan**: it is exercised on every app start. `src/app_controller.py:88` schedules the check, `src/app_controller.py:309-317` runs it, `src/services/update_service.py:73-80` performs it, and the request genuinely traverses `httpcore.AsyncConnectionPool → AsyncHTTPConnection → AsyncHTTP11Connection → AnyIOBackend` (`httpx/_transports/default.py:300-311`; `httpcore/_async/connection.py:69`; `httpcore/_async/http11.py:65`; `httpcore/_backends/anyio.py:98`).
- Installed version is **1.0.9** as the study claims: `httpcore/__init__.py:134` (`__version__ = "1.0.9"`), `httpcore-1.0.9.dist-info/METADATA` (`Version: 1.0.9`, `License-Expression: BSD-3-Clause`), `uv.lock:286-296`. No drift. The package is pure-Python and ships `py.typed`.
- The httpx→httpcore chain the study describes is accurate for the installed tree: `httpx/_transports/default.py:300-311` builds `httpcore.AsyncConnectionPool`; `:313-330` builds `httpcore.AsyncHTTPProxy`; `:340-354` builds `httpcore.AsyncSOCKSProxy`; `:381-392` converts the request and forwards `extensions`; exception mapping is total for the 14 mapped classes (`httpx/_transports/default.py:74-92`) and every mapped httpcore exception has an httpx twin (checked programmatically: no orphans).
- The optional-dependency degradation the study describes is real and matches this venv: `h2` and `socksio` are absent; `httpcore/_async/__init__.py:7-28` and `httpcore/_sync/__init__.py:7-28` substitute `RuntimeError`-raising stubs; `httpx.AsyncClient(http2=True)` and `proxy="socks5://..."` raise `ImportError` at the httpx layer. `httpx.AsyncClient(proxy="socks5://127.0.0.1:1080")` → `ImportError: Using SOCKS proxy, but the 'socksio' package is not installed.` (live).
- The async backend really is the anyio/asyncio one: `httpcore/_backends/auto.py:9-20` (`AutoBackend._init_backend` → `AnyIOBackend` unless trio), and `sniffio` is **not** installed, so `current_async_library()` falls back to `"asyncio"` (`httpcore/_synchronization.py:22-30`). The trio branch is therefore doubly unreachable.
- The single-client-per-check pattern does **not** leak connections: `async with httpx.AsyncClient(...)` closes the transport and its mounts (`httpx/_client.py:2008-2019` → `httpx/_transports/default.py:365-372` → `httpcore.AsyncConnectionPool.__aexit__` → `aclose()` at `_async/connection_pool.py:347-353`). Live check: pool size after close is 0.
- Cancellation is not swallowed: `except Exception` (`update_service.py:100`) excludes `asyncio.CancelledError` (a `BaseException`), so teardown cancellation propagates correctly.
- The `httpx` import in `update_service.py:73` is function-local, so a missing or broken httpx degrades to "no update notice" rather than breaking app import.
- The `httpcore` entry in the licenses screen (`src/screens/views.py:34`) resolves correctly: `importlib_metadata.metadata("httpcore")` yields `Version: 1.0.9` and `License-Expression: BSD-3-Clause` (`httpcore-1.0.9.dist-info/METADATA`), matching the study's licence claim.
- The study's §12/§14 guidance ("stay on httpx; reach for httpcore only for downloads/tests") is confirmed as the right call for this app: the httpx layer already exposes everything the app needs (timeouts, limits, transports, mounts, extensions, mock transport), and httpcore adds nothing the app can use without violating the "no direct httpcore import" guard.
- Pruning is *not* a viable size lever, so no one should attempt it: deleting `httpcore/_sync/` breaks `import httpcore` outright (`httpcore/__init__.py:39-47` imports from `._sync`; `httpcore/_api.py:7` imports `._sync.connection_pool`) — verified live in a scratch copy (`ModuleNotFoundError: No module named 'httpcore._sync'`). Deleting only the four `http2.py` / `socks_proxy.py` files *is* import-safe (the `try/except ImportError` stubs absorb it — verified live), but that saves ~75 KB of source in a pure-Python tree, is not what `flet cleanup package_files` is for (it deletes whole distributions such as `oauthlib/**`, `pyproject.toml:62-63`), and would need a rebuilt APK to validate. Not recommended; recorded to close the question.
