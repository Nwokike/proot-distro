## What it does / how the app uses it

**It does not — tzdata is dormant in this project, and it is dev-only.**

`tzdata` 2026.5 (IANA 2026e) is a **data-only** package: `.venv/Lib/site-packages/tzdata/__init__.py` is 6 lines and holds two constants — `__version__ = "2026.5"` (`:3`) and `IANA_VERSION = "2026e"` (`:6`). The payload is 627 files / 513 763 bytes (excluding `__pycache__`): 625 under `tzdata/zoneinfo/` — of which **598** are the `zic`-compiled TZif zone binaries at `tzdata/zoneinfo/<Region>/<City>` (one per entry of the 598-line index, all present, zero dangling), plus 21 region `__init__.py` packages and the auxiliary tables `zone.tab`, `zone1970.tab`, `zonenow.tab`, `iso3166.tab`, `tzdata.zi`, `leapseconds` — and a 9 102-byte flat index `tzdata/zones` (598 lines). There is no code API beyond the two constants; the entire interface is "be importable so stdlib `zoneinfo` can find data" (`.venv/Lib/site-packages/tzdata-2026.5.dist-info/METADATA:25-28` states exactly this intent).

**It is dev-only, reached only through the arrow chain.** `arrow` 1.4.0 requires it (`arrow-1.4.0.dist-info/METADATA:27` → `Requires-Dist: tzdata;python_version>='3.9'`); `arrow` is required by `cookiecutter` (`uv.lock:178`); `cookiecutter` is required by `flet-cli` (`uv.lock:226`); `flet-cli` is in the **dev** group only (`pyproject.toml:77-84`, `uv.lock:594-601`); the inverted tree shows the same (`docs/swarm/dependency-tree/uv-tree-inverted.txt:111-112` → `tzdata v2026.5 └── arrow v1.4.0 (*)`, and `:88-91` → `six → python-dateutil → arrow → cookiecutter → flet-cli → proot-distro-flet v1.0.0 (group: dev)`). The repo's own reference doc already says so: "Build-host only; none ship to Android" (`docs/reference/dep-cookiecutter-stack.md:3`).

**I proved the runtime closure excludes it by walking the installed METADATA graph**, not by reading the lockfile:

```
runtime roots: flet, flet-ads, httpx, flet-terminal, proot-distro (+ flet-proot)
flet -> httpx, msgpack, oauthlib, repath, typing-extensions
repath -> six
closure = {anyio, certifi, exceptiongroup, flet, flet_ads, flet_proot, flet_terminal,
           h11, httpcore, httpx, idna, msgpack, oauthlib, proot_distro, repath, six,
           typing_extensions}
tzdata in closure? False   arrow in closure? False   python-dateutil in closure? False
```

**The app needs no IANA zone at all.** Greps over `src/`: `import arrow|from arrow` → **0**; `^\s*(import|from)\s+(datetime|zoneinfo|tzdata|dateutil|pytz)` → **0**; `strftime|strptime|isoformat|humanize` → **0**; `ZoneInfo(` → **0**; `^import time` → **1** (`src/services/ad_service.py:7`, used only for a `time.monotonic()` ad throttle at `:171,179`). There is no timestamp to render anywhere in the UI.

**Does the app need IANA zones for timestamps, container times, or scheduling?** Audited all three:
- **Timestamps** — `src/core/changelog.py:5-13` is a `version → bullet-list` map with no date key; `notes_for()` (`:16-18`) returns a string. `src/services/update_service.py:84-99` maps eight feed fields (`version`, `build_number`, `type`, `title`, `release_notes`, `mandatory`, `github_url`, `playstore_url`) — **none is a date** — and `version.json:1-11` has no date field either. The app renders no timestamp of any kind.
- **Container times** — `src/services/proot_service.py:184-203` (`_container_rows`) builds rows of `name`/`image`/`arch`/`size_bytes` only; `:272-291` (`cached_images`) builds `identifier`/`arch`/`size_bytes` only. Upstream *does* carry the time data: `proot_distro/commands/list.py:44` has a `CREATED` column, `:222-225` `_fmt_created`, `:228-248` `_created_epoch` (parses the RFC 3339 `created` field with `_TIMESTAMP_RE` at `:49-52`, falls back to `cached_at` at `:248`), `:262-269` `_fmt_age`; the record's `created`/`cached_at` are set at `proot_distro/helpers/docker/cache.py:712-713`. The app's own dicts at `proot_service.py:196-201` and `:285-288` ignore both. The rendered row is `image · size · arch` (`src/screens/views.py:278-284`).
- **Scheduling** — no scheduler, no cron, no retention window, no expiry. `grep -rniE "schedul|cron|retention|expiry|ttl|prune|rotat"` over `src/` → only the 30-second ad throttle (`src/services/ad_service.py:32,172,174,176`). The prior study's claim that tzdata "makes every `ZoneInfo`/arrow timestamp in install history, session logs, and reports deterministic across devices" (`docs/dependency-studies/tzdata.md:36-38`) describes surfaces that do not exist — the same defect the sibling arrow report already recorded (`docs/swarm/dependency-utilization/arrow.md:17-22`).

## Findings

### F1 · P1 · HALLUCINATION in the prior study: tzdata is not bundled to the device, and the surfaces it is credited with do not exist
- **Where:** the claim is `docs/dependency-studies/tzdata.md:34-40` ("Our-project utilization (M4/M5) … bundling tzdata (via the arrow chain) makes every `ZoneInfo`/arrow timestamp in install history, session logs, and reports deterministic across devices"). Contradicted by `pyproject.toml:9-15` (runtime set) and `:77-84` (dev set), `uv.lock:594-601`, `docs/swarm/dependency-tree/uv-tree-inverted.txt:111-112`, `docs/reference/dep-cookiecutter-stack.md:3`, and by the app itself: `src/core/changelog.py:5-13`, `src/services/update_service.py:84-99`, `src/services/proot_service.py:196-201` and `:285-288`, `src/screens/views.py:278-284`.
- **What:** the study's central utilization claim has two independent false halves. (a) *Nothing is bundled*: the arrow chain is build-host-only, so `tzdata` never enters the APK — the study asserts a benefit the shipped artifact does not have. (b) *There is no install history, no session log, and no report* to make deterministic. The only session time in the app is an epoch float that is collected and dropped (`src/services/proot_service.py:406` copies upstream's `start_time`; `src/app_controller.py:391` renders only `pid · container · kind`).
- **Evidence:** runtime closure walk over the installed METADATA files (output quoted above) → `tzdata in closure? False`. `build_base.py:2566-2576` derives the app's site-packages from `project.dependencies` + `tool.flet.<platform>.dependencies` only — `grep -rn "dependency-groups\|dev-dependencies" .venv/Lib/site-packages/flet_cli/ --include="*.py"` → **no hits**, so the dev group is never consulted by the packaging path. `ls requirements.txt` → no such file, and `build_base.py:2608-2619` only falls back to `requirements.txt` when the TOML list is empty. On the app side: `grep -rnE "^\s*(import|from)\s+(datetime|zoneinfo|tzdata|dateutil|pytz)" --include="*.py" src/` → **0**; `grep -rn "strftime|strptime|isoformat|humanize" --include="*.py" src/` → **0**; `grep -rn "^import time" --include="*.py" src/` → `src/services/ad_service.py:7` only.
- **Fix / opportunity:** correct `docs/dependency-studies/tzdata.md:34-46` to state the truth: tzdata is a **build-host-only transitive** of `flet-cli → cookiecutter → arrow`; the app itself never touches `datetime`/`zoneinfo`/`arrow`; the device has no IANA database and the app does not need one. Then re-derive "Better than Termux's proot-distro?" (`:42-46`) from the actual feature set.
- **Risk if ignored:** an engineer trusts the study, believes the device already has an IANA database, and adds `from zoneinfo import ZoneInfo` in `src/` believing it will resolve — it will raise `ZoneInfoNotFoundError` on device (F4) while passing every host-side check, because the host venv has tzdata installed (F5).

### F2 · P1 · tzdata is not in the shipped dependency set: an `import tzdata` in `src/` is a device-only crash
- **Where:** `pyproject.toml:9-15` (runtime deps: `flet`, `flet-ads`, `httpx`, `flet-terminal`, `proot-distro`), `pyproject.toml:43-52` (`[tool.flet.android] dependencies = ["flet-proot==5.1.107.98"]`), `pyproject.toml:77-84` (`flet-cli` is dev-only); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2566-2576` (the app's site-packages is derived from `project.dependencies` + `tool.flet.<platform>.dependencies`), `:2605-2606` (each becomes a pip `-r` arg), `:2621-2625` (`SERIOUS_PYTHON_SITE_PACKAGES`); `.venv/Lib/site-packages/flet_cli/utils/project_dependencies.py:110-133`; `docs/decisions.md:12-13` (D-003: runtime set frozen, "Any addition needs owner sign-off").
- **What:** `flet build` asks `serious_python` to pip-install exactly the PEP 621 `project.dependencies` into the app's site-packages. The dev group is never consulted, so `flet-cli → cookiecutter → arrow → tzdata` never reaches the device. The host venv has tzdata, so `pytest`/ruff/`flet run` on desktop all pass; only the packaged app breaks.
- **Evidence:** `build_base.py:2566-2570` → `get_project_dependencies(self.get_pyproject("project.dependencies"))`; `:2572-2576` adds `tool.flet.{config_platform}.dependencies`; `:2605-2606` `for toml_dep in toml_dependencies: package_args.extend(["-r", toml_dep])`; `:2608-2619` the `requirements.txt` branch is only reached when `len(toml_dependencies) == 0` and no `requirements.txt` exists in the repo. `grep -rn "dependency-groups\|dev-dependencies" .venv/Lib/site-packages/flet_cli/ --include="*.py"` → **no hits**.
- **Fix / opportunity:** treat "add tzdata" as a **dependency-set decision**, not a code change: it needs owner sign-off under D-003, a `tzdata` entry in `project.dependencies`, and a lock bump. Until then the app must not import `tzdata` — and per F4 it would not help even if it did, because the failure it is meant to prevent is a *named-zone* lookup, and named zones are the one thing the app must avoid on device.
- **Risk if ignored:** a single `import tzdata` at module scope in `src/` is a `ModuleNotFoundError` on every Android device at startup — the app fails to launch. Nothing in the host test loop catches it, because the host venv has tzdata installed.

### F3 · P2 · The app's own timestamps — the one thing tzdata would serve — are not in the runtime set, so the study's "reliability edge" is unavailable exactly where it was claimed
- **Where:** the study's claim is `docs/dependency-studies/tzdata.md:42-46` ("correct local-time display and DST handling without depending on the OEM's system tz data"). App side: `src/services/proot_service.py:406` (`"start_time": record.get("start_time")`), `src/app_controller.py:390-392` (the rendered line), `src/services/proot_service.py:285-288` (cached-image row, drops `created`/`cached_at`), `src/screens/views.py:278-284` (row text). Upstream: `.venv/Lib/site-packages/proot_distro/session.py:154` (`"start_time": time.time()`), `.venv/Lib/site-packages/proot_distro/commands/list.py:222-269` (`_fmt_created`/`_created_epoch`/`_fmt_age`), `.venv/Lib/site-packages/proot_distro/helpers/docker/cache.py:712-713` (`"created"`, `"cached_at": st.st_mtime`).
- **What:** upstream already computes exactly the time data a user would want ("installed 3 weeks ago"), and the app throws it away — but the fix does **not** need an IANA database. Upstream's own formatter is timezone-free: `_created_epoch` (`list.py:228-248`) parses the RFC 3339 `created` string with a regex and converts it with `calendar.timegm` (`:239-241`), then subtracts the parsed numeric offset (`:242-244`) — pure UTC arithmetic, no `ZoneInfo`, no DST table. `_fmt_age` (`:262-269`) is a six-threshold second counter over `_AGE_UNITS` (`:252-259`). The same holds for the session age: `start_time` is an epoch float (`session.py:154`), so "5 minutes ago" is a subtraction. Any of these can be rendered device-locally with the stdlib alone.
- **Evidence:** `list.py:235` `match = _TIMESTAMP_RE.match(image.get("created") or "")`; `:239-241` `epoch = calendar.timegm(tuple(int(g) for g in match.groups()[:6]) + (0, 0, 0))`; `:243-244` `offset = int(off_h) * 3600 + int(off_m) * 60` / `epoch += -offset if sign == "+" else offset`; `:248` `return float(image.get("cached_at") or 0.0)`; `:262-269` `_fmt_age` returns e.g. `"3 weeks ago"`. `calendar.timegm` is documented/observed to be UTC-only: `calendar.timegm((2026,7,15,12,0,0,0,0,0))` → `1784116800` == `2026-07-15 12:00:00+00:00`. `cache.py:713` `"cached_at": st.st_mtime` is a POSIX epoch float. `app_controller.py:391` → `f"pid {row.get('pid')} · {row.get('container')} · {row.get('kind')}" for row in rows` — `start_time` is not in the f-string.
- **Fix / opportunity:** the correct, dependency-free path is: carry the already-present fields (`start_time` at `proot_service.py:406`; `created`/`cached_at` at `:284-289`) and render with a **relative** formatter (elapsed seconds → "5 minutes ago") or with `datetime.fromtimestamp(ts, tz=timezone.utc).astimezone()` for an absolute local time. Relative ages need no zone database at all; absolute local times need only the **device's own** offset, which the platform provides without any IANA file (see F4). A named zone ("Europe/Lisbon") is the only thing that would need `tzdata` — and the app has no user timezone preference to honor.
- **Risk if ignored:** users cannot tell a fresh install from a stale one, cannot age their cache, and cannot see how long a session has been running — while the data is already collected and paid for. This is a UX gap with a zero-dependency fix.

### F4 · P2 · Android's bundled CPython has no POSIX zoneinfo tree: a *named* zone would need the `tzdata` package, and named zones are therefore off-limits on device
- **Where:** stdlib `zoneinfo/_tzpath.py:27-31` (TZPATH comes from `PYTHONTZPATH` or `sysconfig.get_config_var("TZPATH")`), `:78-86` (`find_tzfile` searches only `TZPATH`); `zoneinfo/_zoneinfo.py:65-74` (`_new_instance`: no file found → `_common.load_tzdata(key)` at `:74`); `zoneinfo/_common.py:4-29` (`load_tzdata` reads the **`tzdata` package** via `importlib.resources` — `:7` builds the package name, `:11` opens the resource, `:16-29` turns every failure into `ZoneInfoNotFoundError`); `zoneinfo/__init__.py:13-19` (the C `_zoneinfo` accelerator, or the pure-Python `_zoneinfo.py` fallback — both are stdlib, so `import zoneinfo` always works, only the *data* is missing). Build side: upstream `flet-dev/python-build` `android/build.sh` (cross-build; no `--with-tzpath`), upstream CPython `Android/android.py` `configure-build` (`:262-277` — the configure argument list contains **no** `--with-tzpath`), upstream `flet-dev/python-build` `android/python-android-dart.exclude` (the Android distro excludes `lib/python*/site-packages` and `share` — no zoneinfo tree is shipped), and CPython's own `configure.ac:4347` (`TZPATH="/usr/share/zoneinfo:/usr/lib/zoneinfo:/usr/share/lib/zoneinfo:/etc/zoneinfo"` — Linux paths that do not exist on Android).
- **What:** the CPython that serious_python ships for Android has the `zoneinfo` **module** (stdlib) but no IANA **data** anywhere reachable: none of the four Linux TZPATH roots exist on Android, and Android's own tz data is not a POSIX tree. AOSP's bionic keeps the device's zone rules in a single proprietary concatenated blob at `/apex/com.android.tzdata/etc/tz/tzdata` (`bionic` `libc/tzcode/bionic.cpp:248`) with a fallback at `/system/usr/share/zoneinfo/tzdata` (`:252`) — a container format that is explicitly undocumented and not a directory of per-city TZif files, so `zoneinfo`'s `find_tzfile` cannot read it. The upstream CPython issue states the same conclusion from the platform side: "None of the well-known paths exist on Android… the best approach on Android is currently the same as on Windows – use the tzdata package from PyPI" (python/cpython#127801; the Android team confirmed there is "one single file which has all TZif files concatenated + some indexing" and that "Its format is not documented"). **Therefore: on Android, `ZoneInfo("Europe/Lisbon")` only works if `tzdata` is shipped — and per F2 it is not.**
- **Evidence:** AOSP `bionic` `libc/tzcode/bionic.cpp:237-254` (`__bionic_open_tzdata` → the two hardcoded blob paths) and `:113-125` (the blob's header/index format — a single file with an index, not per-zone files); `bionic` `libc/tzcode/localtime.c:437-440` (bionic's *C* `localtime` reads that same blob via `__bionic_open_tzdata`). CPython `configure.ac:4347` (default TZPATH). CPython `Android/android.py:262-277` (no `--with-tzpath`; `grep -c -i "tzpath|zoneinfo|tzdata"` → **0**). `flet-dev/python-build` `android/python-android-dart.exclude` (excludes `lib/python*/site-packages`; ships no zoneinfo). Runtime proof of the fallback: with the `tzdata` package import blocked, `zoneinfo.ZoneInfo("Africa/Lagos")` → `ZoneInfoNotFoundError: 'No time zone found with key Africa/Lagos'`, and `zoneinfo.ZoneInfo("Europe/Lisbon")` → the same, while `datetime.now().astimezone()` → `2026-10-22 11:39:57.019622+01:00` and `time.localtime()` → a correct local `struct_time` — i.e. **the device's own offset still works without any IANA database**, because it comes from the platform libc, not from Python's `zoneinfo`.
- **Fix / opportunity:** write the constraint into the house convention before the first timestamp lands, and make it a *rule* rather than a hope: **on device, use the platform's local offset (`datetime.now().astimezone()`, `time.localtime()`) or UTC (`datetime.timezone.utc`) — never a named IANA zone.** `ZoneInfo("Area/City")` is the one API that is unavailable on Android without adding `tzdata` to the runtime set (a D-003 decision, and a real cost: 348 KB wheel / 514 KB installed / 627 files for a database the app does not otherwise need). If a *named* zone ever becomes a product requirement, the decision to add `tzdata` to `project.dependencies` must be made explicitly, with the F2 device-crash risk understood.
- **Risk if ignored:** a developer writes `ZoneInfo("Europe/Lisbon")` (or `arrow.now("Europe/Lisbon")`) because it works on the host and in CI; on every Android device it raises `ZoneInfoNotFoundError` at runtime — a crash or a broken screen that no host-side test can reproduce (F5).

### F5 · P2 · The host venv's tzdata masks the device's missing IANA database: every local check passes for code that cannot work on device
- **Where:** `.venv/Lib/site-packages/tzdata/` is installed (dev group), while the device gets only the runtime closure. `zoneinfo/_tzpath.py:27-31` (TZPATH resolution), `zoneinfo/_common.py:4-29` (the `tzdata` fallback), `zoneinfo/_tzpath.py:118-...` `available_timezones()` (reads `resources.files("tzdata").joinpath("zones")` when the package is importable), `pyproject.toml:99-105` (ruff `DTZ` selected, no `DTZ` ignore — the datetime gate is armed), `tests/test_imports_vs_deps.py:46-59` (the import guard), `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2566-2576` (what actually ships).
- **What:** the host is Windows with `zoneinfo.TZPATH == ()` — i.e. **no OS zoneinfo database at all** — and every named-zone lookup succeeds *only* because the dev-group `tzdata` package is installed. The consequences are asymmetric and both point the wrong way: (a) `ZoneInfo("Europe/Lisbon")` works on the developer machine and in CI, and fails on the device; (b) `zoneinfo.available_timezones()` returns 598 zones on the host and would return an empty set on the device. The ruff `DTZ` gate cannot catch either, because it only rejects *naive* datetimes — it says nothing about whether the zone data exists. The house import guard does not catch it either: `zoneinfo` is a stdlib module (`'zoneinfo' in sys.stdlib_module_names` → `True`), so `from zoneinfo import ZoneInfo` in `src/` passes `tests/test_imports_vs_deps.py:54` (`if mod in local or mod in sys.stdlib_module_names: continue`) even though the *data* it needs does not ship.
- **Evidence:** `zoneinfo.TZPATH` on this host → `()`; `sysconfig.get_config_var("TZPATH")` → `''`; `PYTHONTZPATH` env → `None`. `zoneinfo.ZoneInfo("Africa/Lagos")` resolves and `importlib.resources.files("tzdata.zoneinfo.Africa").joinpath("Lagos")` → `...\.venv\Lib\site-packages\tzdata\zoneinfo\Africa\Lagos` (i.e. the package, not the OS). `zoneinfo.available_timezones()` → **598** (exactly the 598 lines of `tzdata/zones`). Instrumented proof that the package is the source: monkeypatching `zoneinfo._common.load_tzdata` records the call → `load_tzdata called with: ['Africa/Lagos']`. Negative proof: blocking only the `tzdata` import (stdlib `zoneinfo` untouched) → `ZoneInfoNotFoundError` for both `Africa/Lagos` and `Europe/Lisbon`, while `datetime.now().astimezone()` and `time.localtime()` keep working. `ruff check src/ --select DTZ` → `All checks passed!` — but the app has no datetime at all, so the gate is currently vacuous. `zoneinfo in sys.stdlib_module_names` → `True`; `tzdata in sys.stdlib_module_names` → `False`; `metadata.packages_distributions().get('zoneinfo')` → `None`.
- **Fix / opportunity:** add a one-line house rule next to the existing ones — *device code may use `datetime` + `timezone.utc` + `.astimezone()`, but not `ZoneInfo(<named zone>)`* — and, if a timestamp feature lands, add a test that asserts the code path never calls `ZoneInfo` with a named key (a one-line AST/grep assertion, cheap). Alternatively, decide now (D-003) whether `tzdata` joins the runtime set, so the constraint is a documented capability rather than a trap; note the cost is 348 KB of wheel for a database the app does not otherwise need.
- **Risk if ignored:** the most likely shape of the eventual bug — a `ZoneInfo(...)` or `arrow.now("Europe/Lisbon")` that is green on the host, green in CI, and red on every device — ships without a single failing local signal.

### F6 · P3 · The only consumer of `{% now %}` in the entire build chain does not use it: arrow's tzdata path is not even exercised at build time
- **Where:** `.venv/Lib/site-packages/cookiecutter/extensions.py:12` (`import arrow`), `:110-144` (`TimeExtension`, `tags = {'now'}` at `:113`, `arrow.now(timezone)` at `:128` and `:144`); `.venv/Lib/site-packages/cookiecutter/environment.py:30-40` (`default_extensions` includes `'cookiecutter.extensions.TimeExtension'`); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:1893-1905` (the `cookiecutter(...)` call), `:67-70` (`DEFAULT_TEMPLATE_URL` = `flet-build-template.zip`); upstream `flet-dev/flet` v1.0.4 `sdk/python/templates/**`; upstream `flet-dev/flet` v1.0.4 `flet-build-template.zip`.
- **What:** `TimeExtension` is registered in every cookiecutter environment, so `arrow` (and therefore `tzdata` as a declared dependency) is *installed* on the build host — but the tag is never *used*. Not one file in flet 1.0.4's own templates and not one file in the shipped `flet-build-template.zip` contains `{% now %}`. So the "arrow chain" that carries tzdata is an install-time dependency with no runtime exercise at all: the build host pulls ~350 KB of IANA database and never reads a byte of it.
- **Evidence:** `grep -rn "{% now" flet-1.0.4/sdk/python/templates/` (after extracting the upstream v1.0.4 source tarball) → **no matches**; scanning all 272 entries of the downloaded `flet-build-template.zip` for the bytes `{% now` → **no matches**; a Jinja-expression scan of the same zip for `{…now…}` → **0 hits**; `cookiecutter/environment.py:34` shows the extension is registered by default. ## Missed capabilities (dependency audits only)

tzdata is a **data package with no code API** (`.venv/Lib/site-packages/tzdata/__init__.py` is 6 lines: `__version__` at `:3`, `IANA_VERSION` at `:6`), so "missed capabilities" here means *unclaimed data*, not unclaimed functions. Every item below is blocked by F2 (tzdata is not in the shipped set) and D-003 (`docs/decisions.md:12-13`, additions need owner sign-off) — so the honest framing is "what tzdata would buy, and what it costs", not "import this".

- **The IANA database itself** (598 zones, `tzdata/zones`; 627 files / 513 763 bytes installed; 348 KB wheel per `uv.lock:818`) · `tzdata/zoneinfo/<Region>/<City>` consumed via `zoneinfo` · integration point: only a **named**-zone feature (a user "display timezone" preference) · value: correct DST/rule handling for a zone the user names · cost: a D-003 dependency-set change (runtime + 348 KB) **and** it buys nothing for the device's own offset, which the platform already provides (F4).
- **`tzdata.zones` (598-line flat index)** · `zoneinfo/_tzpath.py` `available_timezones()` reads it via `importlib.resources` when the package is importable (verified: 598 zones returned on the host) · integration point: a timezone picker for a user preference · value: a searchable zone list without a second source of truth · cost: the same runtime dependency; value today: **zero** — the app has no timezone preference to pick from.
- **`tzdata.__version__` / `tzdata.IANA_VERSION`** · `tzdata/__init__.py:3` and `:6` (`"2026.5"` / `"2026e"`) · integration point: a diagnostics/About line ("IANA rules 2026e") · value: tells a user which IANA release their device-local DST rules came from · cost: trivial, but only meaningful if tzdata ships at all; and note the *device's* rules come from the OEM's APEX, not from this package, so the line would describe the app's database, not the device's zone rules — a possible source of confusion.
- **Where the stdlib is strictly better (do not replace)** · `time.monotonic()` at `src/services/ad_service.py:171,179` · a monotonic interval is immune to wall-clock adjustment and DST; `datetime`/arrow would be strictly worse here · keep it.
- **Where upstream is strictly better (do not re-implement)** · `proot_distro/commands/list.py:262-269` `_fmt_age` (six thresholds + pluralization + "just now") and `:222-225` `_fmt_created` · integration point: `src/services/proot_service.py:285-288` + `src/screens/views.py:278-284` · value: upstream already solved relative-time rendering from UTC-only arithmetic, with **no** IANA database (F3) — the app should carry the fields and reuse the shape, not add a dependency.

## Verified-good list

- **tzdata is genuinely installed and current.** `tzdata/__init__.py:3` → `__version__ = "2026.5"`; `:6` → `IANA_VERSION = "2026e"`; `tzdata-2026.5.dist-info/METADATA:3` → `Version: 2026.5`; `:8` → `License: Apache-2.0`; `:16` → `Requires-Python: >=2`; `WHEEL` → `Root-Is-Purelib: true`, tags `py2-none-any`/`py3-none-any`. PyPI confirms 2026.5 is the **latest** release (uploaded 2026-10-03, the same day as `uv.lock:818`'s `upload-time`), so the M5 bump-group advice in the prior study needs no action today.
- **The data payload is exactly what the stdlib expects.** `tzdata/zoneinfo/` has 21 region packages (each with an `__init__.py`, as `importlib.resources` requires), 598 TZif data files, plus the auxiliary tables `zone.tab`, `zone1970.tab`, `zonenow.tab`, `iso3166.tab`, `leapseconds`, `tzdata.zi`. The `zones` index has 598 lines and `zoneinfo.available_timezones()` returns exactly **598** — the index and the file tree agree, so the package is not truncated.

- **tzdata survives serious_python's Android zip packaging.** I rebuilt the installed `tzdata` tree into a `ZIP_STORED` archive (mirroring the "pure Python ships in stored zips read via zipimport" model described at `flet_cli/commands/build_base.py:72-76`) and loaded it with an interpreter that has **no** tzdata in site-packages: `tzdata resolved from: …\tzdata.zip\tzdata\__init__.py`; `zoneinfo.ZoneInfo('Africa/Lagos')` → `Africa/Lagos` with the correct `1:00:00` July offset; `available_timezones()` → 598.
