# charset-normalizer 3.5.2 utilization — audit

**Verdict:** IMPROVE
**Confidence:** high
**Scope:** `docs/swarm/BRIEF.md`; `docs/dependency-studies/charset-normalizer.md`; `pyproject.toml`; `uv.lock`; `.github/workflows/app.yml`; `src/screens/views.py`; `src/screens/terminal_view.py`; `src/services/session_service.py`; `src/services/session_manager.py`; `src/services/proot_service.py`; `src/services/update_service.py`; `src/app_controller.py`; `src/core/proot_probe.py`; `src/core/posixdb.py`; `src/components/brand_hero.py`; `.venv/Lib/site-packages/charset_normalizer/`; `.venv/Lib/site-packages/requests/`; `.venv/Lib/site-packages/cookiecutter/`; `.venv/Lib/site-packages/flet_cli/`; `.venv/Lib/site-packages/httpx/`; `.venv/Lib/site-packages/flet_terminal/`; `.venv/Lib/site-packages/proot_distro/`; `.venv/Lib/site-packages/binaryornot/` · **Date:** 2026-10-20

## What it does / how the app uses it

**The app does not use charset-normalizer. Not once, not indirectly, not on device.**

`charset_normalizer` 3.5.2 (`charset_normalizer/version.py:7`) is installed in `.venv/Lib/site-packages/charset_normalizer/` and is reachable in exactly one way: as a transitive dependency of the **dev group** — `flet-cli` (`uv.lock:219-227`) → `cookiecutter` (`uv.lock:173-186`) → `requests` (`uv.lock:732-741`, `:738` `charset-normalizer`) → `charset-normalizer` (`uv.lock:61-65`). `pyproject.toml:9-15` lists the five runtime dependencies (`flet`, `flet-ads`, `httpx`, `flet-terminal`, `proot-distro`) and `pyproject.toml:77-84` the dev group; `uv.lock:586-592` is the runtime closure and `uv.lock:594-601` the dev closure. Neither `httpx` (`uv.lock:298-307`: anyio, certifi, httpcore, idna) nor `proot-distro` (`uv.lock:573-580`: no dependencies at all) pulls a detector. The package is therefore **absent from the APK** and unreachable from `src/`.

Even on the CI build host — where it *is* installed (`.github/workflows/app.yml:49`, `:149` `uv sync --frozen --group dev`, `:159` `uv run flet build apk`) — the detection code never executes: `flet_cli/commands/build_base.py:1893-1905` calls `cookiecutter.main.cookiecutter(...)`, and cookiecutter downloads the template as a streamed ZIP, `requests.get(zip_uri, stream=True, timeout=100)` + `for chunk in r.iter_content(chunk_size=1024)` (`cookiecutter/zipfile.py:54-58`). That path never touches `Response.text` or `Response.apparent_encoding` (`requests/models.py:894-902`, `:1049-1069`) — the only two places in the tree that would call a detector. So charset-normalizer is **present but inert**: it is installed, importable, and never executed.

The app's real text paths do not need it, and the three candidate paths named in the assignment (container logs, distro configs, terminal output, user-imported files) are all closed:

- **Container logs** — the feature does not exist. `grep -rni "\blog\b|syslog|journal|dmesg" src/` returns **zero** hits. The closest thing is upstream's captured stdout/stderr, which is already `str`: `io.StringIO()` + `contextlib.redirect_stdout/redirect_stderr` (`src/services/proot_service.py:87-95`), forwarded line-by-line as `str` (`src/services/proot_service.py:53-70`, `src/app_controller.py:173-177`).
- **Distro configs** — the app never reads a guest file. `grep -rn "etc/|os-release|resolv.conf|apt/sources" src/` returns only pwd/grp shim *field-name literals* (`src/core/posixdb.py:11-12`, `:27`, `:29`, `:33`), never a file read.
- **Terminal output** — byte-transparent end to end: `os.read(master_fd, 4096)` → `self._on_bytes(data)` (`src/services/session_service.py:122-126`) → `deque[bytes]` scrollback (`src/services/session_manager.py:31`, `:38-43`) → `MobileTerminal.send_bytes` (`src/screens/terminal_view.py:98`, `flet_terminal/mobile_terminal.py:245-246`) → `self._channel.send(payload)` raw bytes to the Dart terminal (`flet_terminal/terminal.py:129-140`). There is **no Python-side text decode at all** to replace.
- **User-imported files** — the FilePicker is used for exactly two things, both binary container archives: `save_file(...)` → `.tar.gz` and `pick_files(...)` → an archive to restore (`src/app_controller.py:342-370`). Everything else the app touches is binary too (`src/core/proot_probe.py:97`, `:131`; `src/components/brand_hero.py:28`).

The app's **one** text-file read is `src/screens/views.py:628`. That is the whole surface area, and it is where the real (small) defect lives — see F1.

## Findings

### F1 · P2 · The app's only text-file read is a strict UTF-8 decode with no `errors=` fallback

- **Where:** `src/screens/views.py:628` (`path.read_text(encoding="utf-8")[:6000] if path.is_file() else "(text missing)"`), called from `licenses_view()` (`src/screens/views.py:609-634`), which the Settings row opens at `src/screens/views.py:415-425` (`content=licenses_view()` inside `page.show_dialog(ft.AlertDialog(...))`). File list at `src/screens/views.py:43-51`, directory at `src/screens/views.py:20`.
- **What:** `pathlib.Path.read_text` is `(self, encoding=None, errors=None, newline=None)` (verified: `inspect.signature(pathlib.Path.read_text)` on Python 3.14.7 → `errors=None`), and `errors=None` means the `open()` default, i.e. **strict**. So a single non-UTF-8 byte in any of the seven shipped license texts raises `UnicodeDecodeError` *inside the click handler*, before the dialog is ever shown — the user taps "Open-source licenses" and nothing happens. This is the **only** place in the entire stack that decodes bytes-to-text without a fallback: upstream `proot-distro` uses `errors="replace"` everywhere it decodes (`proot_distro/commands/build.py:153` `raw.decode("utf-8", errors="replace")`; `proot_distro/helpers/dockerfile.py:90` `text.decode("utf-8", errors="replace")`; `proot_distro/commands/login/detach.py:106` `raw.decode(errors="replace")`; `proot_distro/guestfile.py:312` `open(fd, encoding="utf-8", errors="replace")`; `proot_distro/locking.py:259` `os.fdopen(fd, "r", errors="replace")`), and httpx does the same (`httpx/_decoders.py:311-312`, `codecs.getincrementaldecoder(encoding)(errors="replace")`).
- **Evidence:** strict vs. replace on a Latin-1 byte — `STRICT -> UnicodeDecodeError: 'utf-8' codec can't decode byte 0xc9 in position 10: invalid continuation byte`; `REPLACE -> 'Copyright � 2026 caf�'`. Today's files are safe by luck, not by construction: `src/LICENSES/GPL-2.0.txt` is valid UTF-8 (non-ASCII bytes `0xC3 0xA9` = `é` at offsets 131/132, 209/210, 708/709 — "Cédric VINCENT"); the other six are pure ASCII (checked via `git show HEAD:<file>`).
- **Fix / opportunity:** `path.read_text(encoding="utf-8", errors="replace")` — one keyword argument, matches the upstream convention quoted above, and keeps the screen alive. **Do not** reach for charset detection here: these are *our* files, and the house rule is "declare everything, guess nothing" (`docs/dependency-studies/charset-normalizer.md:186-201`).
- **Risk if ignored:** low-severity today (the files are UTF-8), but the failure mode is a silently dead button in the Settings screen, and the trigger is a one-line commit by any future contributor who saves a license text in the editor's local encoding. A `errors="replace"` also degrades gracefully: the user sees `�` where a byte is undecodable instead of getting no dialog at all.

### F2 · P3 · charset-normalizer cannot be adopted by `src/` without breaking the frozen dependency set (and must not be)

- **Where:** `pyproject.toml:9-15` (runtime deps), `pyproject.toml:77-84` (dev group), `uv.lock:586-592` (runtime closure), `uv.lock:594-601` (dev closure), `uv.lock:298-307` (httpx deps — no detector), `uv.lock:573-580` (proot-distro — no deps).
- **What:** there is a chicken-and-egg trap here. `charset-normalizer` is only installed *because* the dev group pulls `flet-cli` → `cookiecutter` → `requests` (`uv.lock:219-227`, `:173-186`, `:732-741`). The runtime closure contains no detector at all, so `import charset_normalizer` from `src/` would work on the CI/dev host and **fail at runtime on the device** where the dev group is absent — an `ImportError` that only manifests on Android. Adding it to `pyproject.toml:9-15` would violate the frozen dependency set (D-003) and grow the APK by ~200 KB for a capability nothing needs.
- **Evidence:** `uv.lock:586-592` — runtime deps are `flet`, `flet-ads`, `flet-terminal`, `httpx`, `proot-distro`; `uv.lock:594-601` — `flet-cli`, `flet-desktop`, `pytest`, `pytest-timeout`, `ruff`. `charset-normalizer` appears in `uv.lock` only at `:61-65` (its own entry) and `:738` (requests' dependency list). `charset_normalizer/__init__.py:26-30` exports `from_bytes, from_fp, from_path, is_binary, detect, CharsetMatch, CharsetMatches` — the package has no runtime-only sub-dependency, but it also has no way into the shipped app.
- **Fix / opportunity:** none in code. This finding exists so the synthesis does **not** propose "use charset-normalizer in `src/` to decode X" — the dependency is unreachable on device, and the correct mechanism for any text path is stdlib `errors="replace"` (F1) or an explicit declared encoding.
- **Risk if ignored:** a "free capability we already ship" recommendation would produce an `ImportError`-on-device crash, or a silent APK-size regression plus a D-003 violation.

### F3 · P3 · Terminal output is the one path where charset detection would be actively harmful, not merely useless

- **Where:** `src/services/session_service.py:113-131` (byte read loop), `src/services/session_manager.py:31`/`:38-43` (`deque[bytes]` scrollback), `src/screens/terminal_view.py:98` (`entry.replay(mt.send_bytes)`), `flet_terminal/mobile_terminal.py:245-246` (`send_bytes`), `flet_terminal/terminal.py:129-140` (`self._channel.send(payload)` — raw bytes to Dart); `.venv/Lib/site-packages/charset_normalizer/api.py:871-882` (`is_binary`), `charset_normalizer/models.py:321-328` (`best()` → `None` when empty), `charset_normalizer/api.py:50-61` (`from_bytes` defaults `threshold=0.2`).
- **What:** a PTY stream is UTF-8 text *interleaved with ANSI escape sequences*, not a homogeneous encoded document. Detection on it fails in three independent ways, measured on the installed 3.5.2 with a realistic 40-line `ls -la` capture:
  1. `is_binary()` returns **`True`** for a normal ANSI terminal capture — the detector classifies interactive shell output as binary, because ESC is not printable ASCII.
  2. `from_bytes(...).best()` returns **`None`** (zero matches) when the capture contains one non-UTF-8 byte — total detection failure, not a wrong guess.
  3. When the capture is clean UTF-8, the best match lands at `chaos == 0.200` — exactly the default `threshold=0.2` abandon point (`api.py:54`) — so it is one noisy byte away from the same total failure.
- **Evidence:** installed 3.5.2, warm run, median of 20 — `ansi+latin1 terminal bytes=998 cn_best=None chaos=None is_binary=True t_cn=0.996ms t_utf8rep=0.001ms`; `ansi+utf8 terminal bytes=1018 cn_best=utf_8 chaos=0.2 is_binary=True t_cn=1.127ms t_utf8rep=0.001ms`; vs. `utf-8 json bytes=880 cn_best=utf_8 chaos=0.0 is_binary=False t_cn=0.253ms t_utf8rep=0.004ms`. (Reproduce: `.venv/Scripts/python.exe -c "from charset_normalizer import from_bytes, is_binary; …"`.)
- **Fix / opportunity:** none — and specifically, do **not** "fix" the terminal path with detection. The path is already correct: bytes go to the Dart terminal unchanged (`flet_terminal/terminal.py:129-140`), and the Dart-side emulator owns decoding. A Python-side decode would be a regression even if it worked.
- **Risk if ignored:** the temptation is the highest here — "the terminal shows mojibake for non-UTF-8 locales, so add a detector." That would replace a working byte-transparent pipeline with a detector that calls ordinary shell output binary.

### F4 · P3 · Detection is never even exercised on the CI host; `docs/dependency-studies/charset-normalizer.md` §6/§8 overstates the coupling

- **Where:** `cookiecutter/zipfile.py:54-58` (`requests.get(zip_uri, stream=True, timeout=100)` → `r.iter_content(chunk_size=1024)` → `f.write(chunk)`), `flet_cli/commands/build_base.py:1893-1905`, `flet_cli/commands/create.py:90`, `requests/models.py:894-902` (`apparent_encoding` → `chardet.detect(self.content)["encoding"]`), `requests/compat.py:37-49` (chardet tried **first**), `binaryornot/helpers.py:11`/`:94` (`import chardet`; `chardet.detect(bytes_to_check)`), `requests-2.34.2.dist-info/METADATA:34` (`Requires-Dist: charset_normalizer<4,>=2`), `docs/dependency-studies/charset-normalizer.md:150-161`.
- **What:** the study says charset-normalizer "decodes … inside cookiecutter's template-zip fetch IF a listing page/registry body needed guessing". Verified against the installed source: cookiecutter's only `requests` call streams bytes into the ZIP file, so `Response.text` / `apparent_encoding` are never touched — the `charset_normalizer` branch of `requests` is unreachable in our tree. Additionally, even if it were reached, `requests/compat.py:37-49` resolves `chardet` first (chardet 5.2.0 is installed *directly* by `flet-cli`, `uv.lock:225`, and again by `binaryornot`, `uv.lock:36`), so `requests/models.py:897-898` calls `chardet.detect(...)` and charset-normalizer is the never-taken second branch — exactly as the study's §1/§5 already noted.
- **Evidence:** `grep -rn "\.text\b|apparent_encoding|iter_content|\.content\b" cookiecutter/ --include=*.py` → only `cookiecutter/zipfile.py:56` (`iter_content`). `grep -rn "charset_normalizer|charset-normalizer" --include=*.py .venv/Lib/site-packages` (excluding the package itself) → `requests/compat.py:40`, `requests/help.py:17`/`:84-87`/`:119` (version banner only) — **no other importer anywhere in the venv**.
- **Fix / opportunity:** tighten the study's §6 sentence to state that the package is installed-but-never-executed on the CI host (it is a *lockfile* consequence of `requests`, not an active capability). No code change; this is a documentation-accuracy correction so the synthesis inherits the right mental model.
- **Risk if ignored:** a downstream agent reads "charset-normalizer is on our CI path" and either (a) tries to rely on it in CI tooling that will silently get `chardet` instead, or (b) proposes moving it into the runtime closure "since CI already has it" — which would be a no-op on device.

## Missed capabilities (dependency audits only)

`charset_normalizer` exposes `from_bytes` / `from_fp` / `from_path` / `is_binary` / `detect` / `CharsetMatch` / `CharsetMatches` (`charset_normalizer/__init__.py:26-30`, `:32-43`); `CharsetMatch` adds `chaos` (`:173`), `coherence` (`:177`), `bom` (`:129`), `languages` (`:137`), `could_be_from_charset` (`:216-222`), `output(encoding)` (`:224-251`). **None of them has a legitimate integration point in this app.** Enumerating them so the synthesis can close the question:

| Capability | API location | Would-be integration point | Verdict |
|---|---|---|---|
| `from_bytes` / `from_path` / `from_fp` — detect an unknown encoding | `charset_normalizer/api.py:50-61` / `:840-868` / `:810-837` | decode guest files / registry text / user files | **Rejected.** No such bytes exist in the app: the runtime text surface is one line (`src/screens/views.py:628`), the file picker only handles tar archives (`src/app_controller.py:342-370`), and the registry/search JSON is decoded by upstream with `json.loads(body)` (`proot_distro/helpers/docker/transport.py:260-282`). Also unreachable on device (F2). |
| `is_binary` — "is this text or binary?" gate | `charset_normalizer/api.py:871-882` | gate before rendering an imported file | **Rejected.** The only imported artifacts are tar archives, and the detector misclassifies ordinary ANSI terminal output as binary (`is_binary=True`, F3). |
| `CharsetMatch.chaos` / `.coherence` — confidence gate before trusting a guess | `charset_normalizer/models.py:173`, `:177` | reject low-confidence detections | **Rejected.** A confidence gate on a guess we have no use for. Note `coherence` was `0.0` on the ANSI capture — the gate would reject valid input. |
| `CharsetMatch.output(encoding="utf_8")` — re-encode to UTF-8 | `charset_normalizer/models.py:224-251` | normalise third-party text to UTF-8 | **Rejected.** The same bytes can be re-encoded with `bytes.decode("utf-8", errors="replace")` in one call and no detection step; the study itself says "prefer explicit UTF-8 … Guessing is for OTHER people's bytes" (`docs/dependency-studies/charset-normalizer.md:186-201`). |
| `detect()` legacy chardet-compatible shim | `charset_normalizer/legacy.py:18` | replace chardet in the CI chain | **Rejected.** chardet is already first in `requests/compat.py:40` and is a *direct* flet-cli dep (`uv.lock:223`); swapping it would change CI behavior for no benefit. |

**Cost of the alternative (the status quo), measured:** strict UTF-8 with `errors="replace"` is **4× to 2400× faster** than detection and is *more* accurate on the app's real inputs. Warm medians on the installed 3.5.2: `utf-8 json (880 B)` → detect 0.253 ms vs. replace-decode 0.004 ms; `utf-8 100 KB` → 0.726 ms vs. 0.171 ms (detection samples only 5×512 B by default, `api.py:52-53`, so its cost is sub-linear in file size but its *confidence* is not); `latin-1 text (22 B)` → 0.829 ms vs. 0.001 ms. Accuracy, same run: on the Latin-1 payload `'café naïve résumé file'` the detector guesses **cp1250** and produces `'café naďve résumé file'` — it decodes `0xEF` as `ď` (U+011F), **wrong**, and reports `could_be_from_charset == ['cp1250', 'iso8859_2']` (`models.py:216-222`); the strict decode at least marks the byte as `�` instead of silently substituting a different letter. On a real syslog line carrying one Latin-1 byte the detector again picked `cp1250` (coincidentally correct for that byte). Import cost for an on-device adoption would be `import charset_normalizer` ≈ **172 ms** cumulative (`python -X importtime`), plus ~4.7 ms on the first `from_bytes` call.

## Verified-good list

- **The app correctly uses strict, declared UTF-8 everywhere it decodes text** — `src/screens/views.py:628` is explicit (`encoding="utf-8"`), never locale-dependent. (The single gap is the missing `errors=` fallback — F1 — not the encoding choice.)
- **The terminal pipeline is byte-transparent and must stay that way.** `src/services/session_service.py:122-126` → `src/services/session_manager.py:38-43` → `flet_terminal/terminal.py:129-140` (`self._channel.send(payload)`, no decode). The app-side encode is explicit UTF-8 (`src/screens/terminal_view.py:107` `e.data.encode("utf-8", "ignore")`, `:126` `command.encode("utf-8")`), matching flet-terminal's own `data.encode("utf-8", errors="ignore")` (`flet_terminal/terminal.py:164`, `:192`) and `data.decode("utf-8", errors="ignore")` (`:179`).
- **The app's only HTTP client is httpx, and httpx does not use charset-normalizer.** `src/services/update_service.py:73-76` is the sole `httpx` use in `src/`; `httpx/_models.py:641-650` decodes with `TextDecoder(encoding=self.encoding or "utf-8")`, `httpx/_models.py:652-672` falls back to `default_encoding` (`"utf-8"`, set at `:529`/`:546`), and `httpx/_decoders.py:311-312` uses `errors="replace"`. `response.json()` (`src/services/update_service.py:80`) goes through `json.loads` on bytes, which handles UTF-8/16/32 natively. No detector anywhere in the request path.
- **The app has no locale-dependent or implicit decoding.** `grep -rn "decode|encoding|read_text|read_bytes|latin" src/` returns exactly three code sites: `src/screens/views.py:628` (text read), `src/screens/terminal_view.py:107`/`:126` (explicit UTF-8 encode), and the binary `read_bytes`/`write_bytes` calls at `src/core/proot_probe.py:97`/`:131` and `src/components/brand_hero.py:28`. No `locale.getpreferredencoding()`, no `sys.stdin`/`sys.stdout` reconfiguration, no `open()` without an explicit encoding.
- **Upstream `proot-distro` — the runtime dependency that actually touches foreign bytes — already implements the "errors=replace" convention**, so the app inherits it rather than needing a detector: `proot_distro/commands/build.py:153`, `proot_distro/helpers/dockerfile.py:90`, `proot_distro/commands/login/detach.py:106`, `proot_distro/guestfile.py:312`, `proot_distro/locking.py:259`.
- **Docker Hub search metadata (non-ASCII descriptions, localized text) is decoded as UTF-8 JSON, not guessed**: `proot_distro/helpers/docker/search.py:142-162` fetches bytes, `proot_distro/helpers/docker/transport.py:260-282` runs `json.loads(body)` (stdlib auto-detects UTF-8/16/32), and the description is then whitespace-collapsed and escaped at `proot_distro/helpers/docker/search.py:124-130`. No charset detector is involved, and the app consumes the result as `dict` (`src/services/proot_service.py:263-269`).
- **The study's headline claim — "host/CI only, never in the APK" — is correct**, and the "no LGPL in the story" claim holds: charset-normalizer is MIT (`charset_normalizer-3.5.2.dist-info/METADATA:7` `License: MIT`), and `requests` resolves chardet first (`requests/compat.py:37-49`), with chardet being the LGPL package that is *directly* required by `flet-cli` (`uv.lock:225`).
- **No `import charset_normalizer` exists anywhere in `src/`.** `grep -rn "charset" src/ --include=*.py` → zero hits; `grep -rn "charset" pyproject.toml` → zero hits.
- **Python 3.14 syntax in the decode-adjacent files is valid.** `except OSError, ValueError:` (`src/services/session_service.py:123`) and `except TypeError, ImportError:` (`src/core/posixdb.py:87`) are unparenthesised multi-exception forms legal under PEP 758 in Python 3.14; confirmed by compiling every file in `src/` with `py_compile` — all 32 modules compile.

## Unverified

- **Whether a non-UTF-8 byte can ever appear in the shipped `src/LICENSES/*.txt`.** Today's files are valid UTF-8 (checked via `git show HEAD:<file>`), but the build copies them from the repo with no encoding gate, and I did not find the copy step (the Flet asset pipeline) to confirm it re-encodes or validates. The F1 fix (`errors="replace"`) removes the dependency on that answer.
- **Whether the Dart side of the terminal decodes the byte stream as UTF-8 or as a configurable charset.** The Python side demonstrably does not decode (`flet_terminal/terminal.py:129-140` sends raw bytes). The Dart terminal widget's decoding policy was not inspected — it lives in the Flutter package, not in `.venv`. This does not affect F3 (the Python-side pipeline is byte-transparent either way), but it does mean "non-UTF-8 guest locales render as mojibake" is a claim about the Dart side that I did not verify.
- **The exact Android on-device latency of `import charset_normalizer`** (I measured 172 ms cumulative import time on this Windows host with `python -X importtime`). On a mid-range ARM device the number will differ; the F2 conclusion does not depend on it.
- **Whether `docs/dependency-studies/charset-normalizer.md` is still current for the `requests`↔`chardet` precedence.** `requests/compat.py:37-49` and `binaryornot/helpers.py:11` confirm chardet-first today, matching the study's §1/§5; but the study's §6 sentence about cookiecutter's zip fetch "needing guessing" is contradicted by `cookiecutter/zipfile.py:54-58` (F4) and should be corrected by the study's owner.
