# arrow 1.4.0 date/time utilization — audit

**Verdict:** MIXED
**Confidence:** high
**Scope:** `docs/swarm/BRIEF.md`; `docs/dependency-studies/arrow.md`; `docs/dependency-studies/{cookiecutter,tzdata,python-dateutil,ruff}.md`; `docs/reference/dep-cookiecutter-stack.md`; `docs/decisions.md` (D-003); `docs/swarm/dependency-tree/uv-tree-inverted.txt`; `pyproject.toml`; `uv.lock`; `version.json`; `src/**` (29 modules, 4174 lines, full read of `app_controller.py`, `core/changelog.py`, `core/state.py`, `core/constants.py`, `services/proot_service.py`, `services/ad_service.py`, `services/session_manager.py`, `services/session_service.py`, `services/update_service.py`, `screens/views.py`, `screens/terminal_view.py`, `components/app_header.py`, `components/update_dialog.py`); `.venv/Lib/site-packages/arrow/{__init__,_version,api,arrow,factory,formatter,parser,locales,util}.py`; `.venv/Lib/site-packages/cookiecutter/extensions.py`; `.venv/Lib/site-packages/proot_distro/{session.py,paths.py,commands/list.py,commands/backup.py}`; `.venv/Lib/site-packages/flet/controls/services/file_picker.py`; `.venv/Lib/site-packages/flet/controls/{page,types}.py`; `.venv/Lib/site-packages/flet_cli/commands/build_base.py`; `.venv/Lib/site-packages/flet_cli/utils/project_dependencies.py`; stdlib `zoneinfo/{_common,_zoneinfo}.py` (CPython 3.14.7) · **Date:** 2026-10-20

## What it does / how the app uses it

**It does not.** `arrow` 1.4.0 is installed in `.venv` but is reachable only through the **dev group**: `flet-cli → cookiecutter → arrow` (`docs/swarm/dependency-tree/uv-tree-inverted.txt:88-90,112`; `uv.lock:174-190` where `cookiecutter` lists `{ name = "arrow" }`). Its only consumer in the entire stack is cookiecutter's Jinja `TimeExtension`, i.e. the `{% now %}` tag in a **build template** (`.venv/Lib/site-packages/cookiecutter/extensions.py:12` `import arrow`; `:128` `d = arrow.now(timezone)`; `:144` `return arrow.now(timezone).strftime(datetime_format)`). The app itself imports neither `arrow` nor `datetime`, `dateutil` or `tzdata` — grep over `src/` for `import arrow|from arrow` → **0**; for `^\s*(import|from)\s+(datetime|dateutil|tzdata|arrow)` → **0**; for `strftime|strptime|isoformat|humanize|\.span(` → **0**.

Consequently the app renders **no timestamps at all**: no changelog dates (`src/core/changelog.py:5-13` is a `version → bullet-list` map, no date key), no container creation/modification time (`src/services/proot_service.py:184-203` builds rows of `name`/`image`/`arch`/`size_bytes` only), no update date (`src/services/update_service.py:84-99` maps eight feed fields, none of them a date; `version.json:1-11` has no date field), no session time in the UI, and no date in a backup file name. The single time-shaped value in the whole app is the epoch float `start_time` that upstream `proot_distro` puts in every session record and the app copies into its plain-dict layer — then drops before rendering.

The prior study `docs/dependency-studies/arrow.md:45-51` asserts the opposite ("Every timestamp the app shows: install-history entries, session logs, report headers — `arrow.now(<device tz>).format(...)` … `shift()` computes retention windows"). There is no install history, no session log, no report header, and no `shift()` in this app. That section is a **HALLUCINATION**, and it is contradicted by the repo's own reference doc, which says the cookiecutter stack is "Build-host only; none ship to Android" (`docs/reference/dep-cookiecutter-stack.md:3`).

## Findings

### F1 · P1 · HALLUCINATION in the prior study: the app formats no timestamp with arrow — it formats no timestamp at all
- **Where:** `docs/dependency-studies/arrow.md:45-51` (the claim); app side: no `import arrow` / `import datetime` anywhere in `src/`; `src/core/changelog.py:5-13`; `src/core/state.py:18-47` (no timestamp field on the observable state); `src/screens/views.py:277-284` (container row text is `image · size · arch`); `src/screens/views.py:460-465` (Settings shows `containers + cache: <size> · N cached image(s)`).
- **What:** the study tells a future reader that arrow is load-bearing for the app's timestamps, that every timestamp goes through `arrow.now(<device tz>).format(...)`, and that `shift()` computes retention windows. None of that exists. The app's only clock usage is `time.monotonic()` for an ad-interval throttle (`src/services/ad_service.py:171,179`).
- **Evidence:** runnable greps over `src/`: `grep -rn "import arrow\|from arrow" --include="*.py" src/ | wc -l` → `0`; `grep -rnE "^\s*(import|from)\s+(datetime|dateutil|tzdata|arrow)" --include="*.py" src/ | wc -l` → `0`; `grep -rnE "strftime|strptime|isoformat|humanize|\.format\(\"YYYY|\.span\(" --include="*.py" src/ | wc -l` → `0`; `grep -rn "^import time" --include="*.py" src/` → `src/services/ad_service.py:7` only. The only `arrow` mention in `src/` is the substring "arrow" inside the word "narrow" (`src/components/update_dialog.py:30`).
- **Fix / opportunity:** correct `docs/dependency-studies/arrow.md:45-51` to state the truth: arrow is a build-host-only transitive dependency of `cookiecutter` (used by its `{% now %}` Jinja tag), the app does not use it, and it is not in the shipped runtime set. Then re-derive the "Better than Termux's proot-distro?" section (`:53-56`) from the actual feature set, not from an assumed one.
- **Risk if ignored:** an engineer trusts the study and adds `import arrow` to app code — which is a guaranteed crash on device (F2) — and, worse, believes the app already has an install-history/session-log/reporting surface that it does not, so the real gaps (F3, F4) are never designed for.

### F2 · P1 · arrow is not in the shipped dependency set: `import arrow` in `src/` is a device-only crash
- **Where:** `pyproject.toml:9-15` (runtime `dependencies` = `flet`, `flet-ads`, `httpx`, `flet-terminal`, `proot-distro`), `pyproject.toml:43-52` (`[tool.flet.android] dependencies = ["flet-proot==5.1.107.98"]`), `pyproject.toml:77-84` (`flet-cli` is in `[dependency-groups] dev`); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2566-2576` (the bundle's site-packages is derived from `project.dependencies` + `tool.flet.<platform>.dependencies`), `:2605-2606` (each is passed as a pip `-r` arg), `:2608-2619` (the `requirements.txt` branch is only taken when the TOML list is empty — and no `requirements.txt` exists in the repo); `.venv/Lib/site-packages/flet_cli/utils/project_dependencies.py:110-133`; `docs/decisions.md:12-13` (D-003: runtime set frozen, "Any addition needs owner sign-off"); `docs/reference/dep-cookiecutter-stack.md:3`; `docs/swarm/dependency-tree/uv-tree-inverted.txt:88-90,112`.
- **What:** `flet build` asks `serious_python` to pip-install exactly the PEP 621 `project.dependencies` into the app's `site-packages`. The dev group is never consulted by that code path, so `flet-cli → cookiecutter → arrow → python-dateutil → tzdata` never reaches the device. The host venv has arrow, so `pytest`/ruff/`flet run` on desktop all pass; only the packaged app breaks.
- **Evidence:** `build_base.py:2566-2570` → `get_project_dependencies(self.get_pyproject("project.dependencies"))`; `:2572-2576` adds `tool.flet.{config_platform}.dependencies`; no reference to dependency-groups or `uv.lock` anywhere in that function. `uv-tree-inverted.txt:88-90`: `six v1.17.0 → python-dateutil → arrow v1.4.0 → cookiecutter v2.7.1`; `:112` `arrow v1.4.0`; `:18-20` `requests → cookiecutter v2.7.1 → flet-cli v1.0.4 → proot-distro-flet v1.0.0 (group: dev)`. `ls requirements.txt` → "No such file or directory".
- **Fix / opportunity:** treat "add arrow to the app" as a **dependency-set decision**, not a code change: it needs owner sign-off under D-003, an `arrow` entry in `project.dependencies` (which would also pull `python-dateutil>=2.7.0` and `tzdata` per `arrow-1.4.0.dist-info/METADATA:25-27`), and a lock bump. Until that decision is made, the only app-legal way to render a date is the stdlib (`datetime` + `zoneinfo`/`timezone`), and the app must not import arrow.
- **Risk if ignored:** a single `import arrow` at module scope in `src/` is a `ModuleNotFoundError` on every Android device at startup — the app fails to launch. Nothing in the host test loop catches it, because the host venv has arrow installed.

### F3 · P2 · The session start time is collected from upstream and then thrown away
- **Where:** `src/services/proot_service.py:393-412` (`active_sessions()`), `:406` (`"start_time": record.get("start_time")`); `src/app_controller.py:385-393` (`list_sessions()`), `:390-392` (the rendered line uses only `pid`, `container`, `kind`); `.venv/Lib/site-packages/proot_distro/session.py:154` (`"start_time": time.time()`), `:320-323` (validated: not a bool, numeric, finite), `:332` (`"start_time": float(start_time)`), `:253` (sessions are sorted by `start_time`); `.venv/Lib/site-packages/arrow/arrow.py:239` (`Arrow.fromtimestamp`), `:1133` (`Arrow.humanize`).
- **What:** upstream already hands the app a validated epoch float for every live session. The app copies it into its plain-data layer and then renders a snackbar without it. "Running sessions" therefore reads `pid 1234 · debian · login` with no indication of age — the user cannot distinguish a session started ten seconds ago from one running for six hours, which is the one fact that decides whether to kill it.
- **Evidence:** `session.py:154` writes `time.time()`; `:321` rejects `bool` and non-`(int, float)`; `:323` rejects non-finite; `:332` coerces to `float`. `app_controller.py:391` → `f"pid {row.get('pid')} · {row.get('container')} · {row.get('kind')}" for row in rows` — `start_time` is not in the f-string and `user`/`command` are dropped too.
- **Fix / opportunity:** render the age. With arrow: `arrow.get(row["start_time"]).humanize()` → `"5 minutes ago"` (`arrow/arrow.py:1133`); with the stdlib (no new dependency): `datetime.fromtimestamp(ts, tz=timezone.utc).astimezone()` plus a 3-line relative formatter, timezone-aware so ruff DTZ stays green. Either way the field must be carried from `src/services/proot_service.py:406` into the rendered string at `src/app_controller.py:391`.
- **Risk if ignored:** users kill live sessions (or keep them) with no information about how long they have been running; the data is paid for and discarded.

### F4 · P2 · Container and cached-image rows drop the creation time that upstream already computes
- **Where:** `src/services/proot_service.py:184-203` (`_container_rows()` — the row dict at `:195-202` carries `name`/`image`/`arch`/`size_bytes` only), `:272-291` (`cached_images()` — the row dict at `:284-289` carries `identifier`/`arch`/`size_bytes` only); `src/screens/views.py:277-284` (row text), `src/screens/views.py:460-465` (Settings shows a count, no per-image list); `.venv/Lib/site-packages/proot_distro/commands/list.py:44` (`_IMAGE_HEADERS = ("IMAGE", "ARCH", "ID", "SIZE", "CREATED")`), `:147` (`:_fmt_created(image, now)`), `:222-225` (`_fmt_created`), `:228-248` (`_created_epoch` — parses the RFC 3339 `created` field with `_TIMESTAMP_RE`, `:49-52`, and falls back to `cached_at`, `:246-248`), `:252-259` (`_AGE_UNITS`), `:262-269` (`_fmt_age`); `.venv/Lib/site-packages/arrow/arrow.py:1133` (`humanize`), `:1105` (`format`), `.venv/Lib/site-packages/arrow/factory.py:85` (`get` — parses ISO/RFC 3339 strings), `.venv/Lib/site-packages/arrow/arrow.py:239` (`fromtimestamp`).
- **What:** upstream ships a *complete* relative-time formatter — six thresholds, pluralization, `"just now"` fallback (`list.py:252-269`) — and a CREATED column, and the app reimplements the same listing without a single time field. So "when did I install this?" and "when did I pull this image?" have no answer anywhere in the UI, and the `clear_cache` action (`src/app_controller.py:231-246`) has no age context to help a user decide what to reclaim. The app's own dict at `proot_service.py:284-289` reads `image.get("image_ref")`, `image.get("arch")`, `image.get("full_path")`/`image.get("path")` — and ignores the `created`/`cached_at` keys the same upstream record carries.
- **Evidence:** `list.py:235` `match = _TIMESTAMP_RE.match(image.get("created") or "")`; `:246-248` `return float(image.get("cached_at") or 0.0)`; `:262-269` `_fmt_age` returns e.g. `"3 weeks ago"`. Upstream's own `list` is the CLI; the app never calls it, and its own re-implementation keeps none of the time fields.
- **Fix / opportunity:** add one field (`created_epoch` or `created`) to the two row dicts and one text line to the container row. With arrow: `arrow.get(created_str).humanize()` handles the RFC 3339 string directly (`factory.py:85`) and `arrow.get(epoch).humanize()` handles the fallback — no hand-rolled regex, no threshold table. Requires the F2 dependency decision; the stdlib alternative is `datetime.fromisoformat` (Python 3.11+ parses RFC 3339 offsets) plus a small formatter, and must be tz-aware to satisfy DTZ.
- **Risk if ignored:** the app cannot tell a fresh install from a stale one, cannot age its cache, and re-implements (rather than reuses) the one thing upstream already solved.

### F5 · P2 · "Backup to a file" raises `ValueError` on Android before the file is ever named
- **Where:** `src/app_controller.py:342-354` (`backup_container`), `:346-348` (`await self.file_picker.save_file(dialog_title=…, file_name=f"{container}.tar.gz")` — no `src_bytes`); `src/screens/views.py:186` (the menu item "Backup to a file"); `.venv/Lib/site-packages/flet/controls/services/file_picker.py:278-286` (`save_file` signature), `:301-303` (`src_bytes`: "Must be provided in web, iOS or Android modes"), `:312-316` (the guard), `:320-331` (the invoke); `.venv/Lib/site-packages/flet/controls/types.py:843-849` (`PagePlatform.is_mobile()` → True for `IOS`/`ANDROID`); `.venv/Lib/site-packages/flet/controls/page.py:595` (`platform: Optional[PagePlatform]`), `:929-964` (`run_task` → the exception is re-raised inside a done-callback, not surfaced in the UI).
- **What:** the Flet 1.0.4 client-side `save_file` refuses to run on mobile without `src_bytes`, raising `ValueError` **before** the picker is invoked. The app's call passes no `src_bytes`, so on every Android device the "Backup to a file" menu item raises, the coroutine dies inside `page.run_task`, and the user sees nothing at all — no picker, no snackbar, no error. The backup path is dead on the app's only shipping platform. (This finding is in the audit because "backups" is one of the timestamp surfaces in scope; the timestamp fix for it is F7.)
- **Evidence:** runnable proof against the installed package: calling `ft.FilePicker.save_file` with a page whose `platform` is `ft.PagePlatform.ANDROID` and no `src_bytes` → `ValueError: "src_bytes" is required when saving a file in web mode,or on mobile (Android & iOS).` (the guard is `file_picker.py:312-316`). `app_controller.py:346-348` passes only `dialog_title` and `file_name`. `page.py:947-961` re-raises the task exception in the done-callback, i.e. it is logged by asyncio, never shown in the UI.
- **Fix / opportunity:** either (a) produce the archive bytes in-process and pass them as `src_bytes` (`bytes` is already the declared type at `file_picker.py:285`) — this requires the backup to be materialized in memory rather than streamed to a path, so it is a design change, not a one-liner; or (b) use a different mobile-safe destination (e.g. write into the app's own storage dir via `storage_paths` and offer the file through a share/open affordance). At minimum, wrap the call in `try/except` and `show_snack` the reason, so a failure is never silent.
- **Risk if ignored:** a headline feature ("Manage containers: rename, back up, restore, copy, reset, remove", `src/core/changelog.py:10`) silently does nothing on the target platform, and the user has no signal that anything went wrong.

### F6 · P2 · Named time zones need `tzdata` shipped — arrow alone is not sufficient on Android
- **Where:** `.venv/Lib/site-packages/arrow/parser.py:928-936` (named zone → `ZoneInfo(tzinfo_string)`; `ZoneInfoNotFoundError` → `ParserError("Could not parse timezone expression …")`), `.venv/Lib/site-packages/arrow/factory.py:333-338` (`arrow.now("Europe/Lisbon")` takes the same path), `.venv/Lib/site-packages/arrow/arrow.py:195-198` (`Arrow.now()` with no argument uses the device's local offset — no tz database needed); stdlib `zoneinfo/_common.py:4-29` (`load_tzdata` reads the **`tzdata` package**; raises `ZoneInfoNotFoundError` when it is absent), `zoneinfo/_zoneinfo.py:74` (the fallback call site); `.venv/Lib/site-packages/tzdata/__init__.py` (2026.5 / IANA 2026e); `arrow-1.4.0.dist-info/METADATA:27` (`Requires-Dist: tzdata; python_version>='3.9'`); `docs/swarm/dependency-tree/uv-tree-inverted.txt:110-112` (`tzdata → arrow → cookiecutter → dev group`).
- **What:** there are two distinct arrow time zones of use. `arrow.now()` (device-local offset) and `arrow.get(epoch)` (UTC) work with **no** tz database at all. A *named* zone ("Europe/Lisbon", "Africa/Lagos") resolves through stdlib `ZoneInfo`, which on Android finds no OS zoneinfo tree and must fall back to the `tzdata` package — which, like arrow itself, is only reachable through the dev group. If arrow is ever added to the runtime set, `tzdata` comes with it (METADATA requires it), so the safe rule is: add `arrow` (not arrow-without-deps), and keep display formatting on the local offset.
- **Evidence:** on this host `zoneinfo.TZPATH` is `()` (Windows) yet `zoneinfo.ZoneInfo("Africa/Lagos")` resolves — proving the resolution came from the installed `tzdata` package (2026.5, IANA 2026e) via `zoneinfo/_common.py:4-29`, not from an OS database. Runtime check of the installed arrow: `arrow.get(1758360000.123)` → `<Arrow [2025-09-20T09:20:00.123000+00:00]>` (UTC); `arrow.now()` → device-local; `arrow.get(ts).to("local").format()` → `2025-09-20 10:20:00+01:00`.
- **Fix / opportunity:** if the F2 dependency decision goes ahead, add plain `arrow` (pulling `python-dateutil` + `tzdata`), and prefer `arrow.now()` / `to("local")` over named zones for display; reserve named zones for an explicit user "timezone" preference, which the app does not have today.
- **Risk if ignored:** if arrow is added without its dependency closure (vendored, `--no-deps`, or a hand-copied wheel), every named-zone render raises `ParserError` at runtime; and any "show the time in New York" feature would be dead on device with an exception rather than a wrong-but-plausible answer.

### F7 · P3 · The backup default file name carries no timestamp and collides on a second backup the same day
- **Where:** `src/app_controller.py:346-348` (`:347` `file_name=f"{container}.tar.gz"`); `.venv/Lib/site-packages/proot_distro/commands/backup.py:471-479` (`os.path.isfile(output_path)` → `crit_error("file '<path>' already exists. Please specify a different name.")` + `sys.exit(1)`); `src/services/proot_service.py:415-423` (`friendly_job_error` surfaces that text to the user).
- **What:** every backup of a given container is pre-filled with the same name. Upstream hard-refuses to overwrite an existing file (by design — it is a no-clobber contract, not a bug), so the second backup of the same container on the same day fails unless the user edits the name in the picker. A date-stamped default (`debian-20261020-140322.tar.gz`) removes the collision and makes the file self-describing, which is exactly what `arrow.now().format("YYYYMMDD-HHmmss")` produces in one call (`.venv/Lib/site-packages/arrow/arrow.py:1105`).
- **Evidence:** `backup.py:476-478` `if os.path.isfile(output_path): crit_error(f"file '{output_path}' already " "exists. Please specify a different name.")`; `app_controller.py:347` builds the same name every time. The stdlib equivalent, if arrow stays out of the runtime set, is `datetime.now().astimezone().strftime("%Y%m%d-%H%M%S")` — `astimezone()` rather than bare `now()` so ruff DTZ005 stays satisfied.
- **Fix / opportunity:** stamp the default name; the file name is also the only place a date would be visible in the user's Downloads folder, so it is the cheapest possible "timestamp surface" in the app.
- **Risk if ignored:** minor friction (the user can rename manually), and a small chance of the user overwriting or losing a previous backup by editing the name carelessly. Upstream's refusal prevents silent clobbering, so this is polish, not data loss. Note this is only reachable once F5 is fixed.

### F8 · P3 · The "dt enforcement" is ruff's flake8-datetimez gate — armed, green, and vacuous; no house UTC-vs-local rule exists
- **Where:** `pyproject.toml:99-105` (`[tool.ruff.lint] select = ["E","F","W","UP","B","Q","C4","PERF","ERA","I","T20","DTZ","RUF","S","TRY","BLE","EM","A","SIM","RET","RSE"]`, `ignore = [...]` — no DTZ entry, so all of DTZ is enforced); `docs/dependency-studies/ruff.md:151` ("DTZ | flake8-datetimez | ✅ … Keep if we touch datetimes"); ruff 0.17.1 rule set: DTZ001 `call-datetime-without-tzinfo`, DTZ002 `call-datetime-today`, DTZ003 `call-datetime-utcnow`, DTZ004 `call-datetime-utcfromtimestamp`, DTZ005 `call-datetime-now-without-tzinfo`, DTZ006 `call-datetime-fromtimestamp`, DTZ007 `call-datetime-strptime-without-zone`.
- **What:** the house "dt enforcement" is the DTZ rule family, and it currently passes on `src/` only because the app never constructs a datetime. The gate is real (it fires on a probe file) but it catches *naive* datetimes only — it cannot catch a datetime that is aware but in the wrong zone, and it says nothing about which zone house style demands. The first contributor to add a timestamp inherits no convention: UTC for stored/comparable values, device-local for display, is the natural split, and it is exactly the split arrow encodes (`arrow.now()` = local, `arrow.get(epoch)` = UTC).
- **Evidence:** `ruff check src/ --select DTZ` → `All checks passed!`. A probe file containing `datetime.now(), datetime.today(), datetime.utcnow()` is rejected with `DTZ005` (`datetime.datetime.now() called without a tz argument`), `DTZ002` (`datetime.datetime.today() used`), `DTZ003` (`datetime.datetime.utcnow() used`). The app's own `time.monotonic()` usage (`src/services/ad_service.py:171,179`) is DTZ-clean because it never touches `datetime`.
- **Fix / opportunity:** write the rule down before the first timestamp lands (one line in `docs/reference/house-ui-design.md` or `docs/decisions.md`): *stored/compared timestamps are UTC-aware; user-facing timestamps are converted to the device's local offset at render time; no naive datetimes.* Then the DTZ gate backs a stated convention instead of an unstated one.
- **Risk if ignored:** the first timestamp feature picks an arbitrary zone convention, DTZ stays green, and the inconsistency surfaces later as "the log says 3am" bugs that no lint rule catches.

## Missed capabilities (dependency audits only)

All of the following are real arrow capabilities that this app does not use. **Every one of them is blocked by F2** (arrow is not in the shipped dependency set) and by D-003 (`docs/decisions.md:12-13`, additions need owner sign-off) — so the honest framing is "what arrow would buy, and what it costs", not "add these imports".

- **`Arrow.humanize()`** · `.venv/Lib/site-packages/arrow/arrow.py:1133` · integration: `src/app_controller.py:391` (session age), `src/screens/views.py:277-284` (container age) · value: replaces upstream's hand-rolled 6-threshold table (`proot_distro/commands/list.py:252-269`) with one call, and adds pluralization + 189 locales for free · cost: one field per row + one call per row; dependency cost: `arrow` in `project.dependencies` + owner sign-off.
- **`Arrow.fromtimestamp()`** · `arrow/arrow.py:239` · integration: `src/services/proot_service.py:406` (`start_time` is already a validated epoch float from `proot_distro/session.py:154`) · value: epoch → tz-aware datetime in one call, no `datetime.fromtimestamp` + `tz` juggling · cost: one call; zero new data plumbing (the value is already in the dict).
- **`Arrow.get(str)`** · `arrow/factory.py:85` (parses ISO 8601 / RFC 3339) · integration: `src/services/proot_service.py:284-289` (the cached-image `created` field, RFC 3339 per `proot_distro/commands/list.py:49-52`) · value: parses the timestamp without the app having to carry its own regex (upstream needs `_TIMESTAMP_RE` at `list.py:49-52` precisely because it has no parser) · cost: one call.
- **`Arrow.format()`** · `arrow/arrow.py:1105` (token format `"YYYY-MM-DD HH:mm:ss ZZ"`) · integration: `src/screens/views.py:277-284` · value: an absolute, unambiguous date in the container row next to the relative form · cost: one call; note the app has no locale layer at all, so only the `en-us` default is meaningful today.
- **`Arrow.to()`** · `arrow/arrow.py:1057` · integration: wherever a UTC-stored stamp is displayed · value: renders in the device's local offset without needing an OS tz database (`to("local")`) — the one conversion that works on Android with no tzdata · cost: one call.
