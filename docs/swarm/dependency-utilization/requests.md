# requests 2.34.2 utilization — audit

**Verdict:** IMPROVE
**Confidence:** high
**Scope:** `docs/dependency-studies/requests.md`; `build_flet_proot_wheel.py`; `src/services/update_service.py`; `src/app_controller.py`; `src/components/update_dialog.py`; `src/core/constants.py`; `src/screens/views.py`; `tests/test_proot_surfaces.py`; `tests/test_imports_vs_deps.py`; `pyproject.toml`; `uv.lock`; `.github/workflows/app.yml`; `.venv/Lib/site-packages/requests/`; `.venv/Lib/site-packages/cookiecutter/`; `.venv/Lib/site-packages/flet_cli/`; `.venv/Lib/site-packages/proot_distro/helpers/download.py`; `.venv/Lib/site-packages/urllib3/util/retry.py` · **Date:** 2026-10-20

## What it does / how the app uses it

**requests is not used by this project at all — it is a build-host transitive dependency, and the one code path that could reach it is never taken by our CI.** The installed tree has exactly one importer: `.venv/Lib/site-packages/cookiecutter/zipfile.py:10` (`import requests`), whose single call site is `.venv/Lib/site-packages/cookiecutter/zipfile.py:54` — `r = requests.get(zip_uri, stream=True, timeout=100)` inside `unzip(..., is_url=True)`. That branch fires only when cookiecutter is handed a **remote** zip. Our CI hands it a **local** one: `flet build` resolves the build template through flet-cli's own stdlib cache (`flet_cli/utils/template_cache.py:38` — `urllib.request.urlopen(url)` + `shutil.copyfileobj`) and then calls `cookiecutter(template=<local .zip path>)` (`flet_cli/commands/build_base.py:1858-1864`, `:1893-1903`). cookiecutter routes that through `repository.determine_repo_dir` → `is_zip_file(template)` true → `unzip(zip_uri=<local path>, is_url=is_repo_url(<local path>))` (`.venv/Lib/site-packages/cookiecutter/repository.py:104-108`); `is_repo_url` matches only `git://`, `ssh://`, `file://`, `http(s)://`, `user@host` (`cookiecutter/repository.py:16-30`). Runtime check: a local cache path → `is_repo_url=False`; the `flet create` release URL → `is_repo_url=True`. So in `flet build apk` (`.github/workflows/app.yml:141`, `:195`) **requests is never imported at runtime** — it is merely installed.

**The dependency is dev-only, provably.** `uv tree --no-dev` (the runtime closure that ships) contains `flet, flet-ads, httpx, flet-terminal, proot-distro` and **no** requests/urllib3/charset-normalizer/cookiecutter/chardet. `uv.lock:184` records `requests` as a dependency of `cookiecutter`, `uv.lock:226` makes `cookiecutter` a dependency of `flet-cli`, and `uv.lock:594-601` places `flet-cli` in the **dev** group only. Independently confirmed at the packaging layer: flet-cli builds the APK requirement list from `project.dependencies` + `tool.flet.<platform>.dependencies` only (`flet_cli/commands/build_base.py:2566-2573`, `flet_cli/utils/project_dependencies.py:110-131`), and a repo-wide grep of `flet_cli` for `dependency-groups` / `dependency_groups` / `dev-dependencies` / `optional-dependencies` returns **nothing** — dev groups are never read by the packager. Our `project.dependencies` are `flet, flet-ads, httpx, flet-terminal, proot-distro` and `tool.flet.android.dependencies` is `flet-proot==5.1.107.98` (`pyproject.toml:9-15`, `:52`). The app-side license list agrees — requests/urllib3/charset-normalizer are absent from the shipped dists tuple (`src/screens/views.py:27-42`).

**Neither audited HTTP path wants requests.** The builder (`build_flet_proot_wheel.py`) is stdlib-only by its own contract ("One self-contained file … **Stdlib only**", `build_flet_proot_wheel.py:4-5`) and fetches six small .debs via `urllib.request.urlopen` (`:196-199`). The app path (`src/services/update_service.py`) is `async` and uses httpx (`:70-80`); requests is **sync-only** (`requests/api.py:69-72` opens a throwaway `Session` and calls `session.request` synchronously), so dropping it into `check_for_update()` would block the Flet session event loop that `page.run_task` schedules onto (`src/app_controller.py:88`).

**Conclusion on the assignment's question: requests is correctly avoided, not underused.** It is not in the app, not in the APK, not in the builder, and not in the app's HTTP path. The one genuine gap this audit exposed is in the builder's own urllib download (F1/F2/F3) — and the fix for it is stdlib, not requests.

## Findings

### F1 · P2 · The builder's pinned .deb download has no retry, so one transient mirror error fails the whole APK/AAB build

- **Where:** `build_flet_proot_wheel.py:196-199` (`_fetch`), `:202-210` (`_fetch_verified`), `:447-463` (`download_sources`); `.github/workflows/app.yml:141` and `:195` (one bare invocation per job, no retry wrapper).
- **What:** `_fetch` performs a **single** `urllib.request.urlopen(req, timeout=TIMEOUT)` and `_fetch_verified` calls it exactly once per package. Any transient failure — a TCP reset, a 502/503 from the `packages.termux.dev` mirror, a DNS blip — aborts the run with a raw traceback. The builder downloads **three** .debs per architecture (`:297` iterates `proot, libtalloc, libandroid-shmem`) and the CI runs it **twice** (apk job and aab job), so a single flaky fetch costs a full CI cycle. `urllib.request` has no retry of its own; the stdlib default opener is `HTTPDefaultErrorProcessor` + `HTTPRedirectHandler` and nothing else (runtime: `build_opener()` handlers = `UnknownHandler, HTTPHandler, HTTPDefaultErrorHandler, HTTPRedirectHandler, FTPHandler, FileHandler, DataHandler, HTTPSHandler, HTTPErrorProcessor`).
- **Evidence:** runtime probe against a local server that answers 503 twice then 200:
  ```
  urllib: FAILED -> HTTPError HTTP Error 503: Service Unavailable
    server hits so far: 1
  requests: status 200 body OK
    server hits total: 3
  ```
  (urllib = the builder's stack, one hit, fails; the same URL through a `Retry`-mounted requests `Session` succeeds after 3 hits). The builder has no `try`/`except` anywhere on the fetch path — `grep` for `try:`/`except` in `build_flet_proot_wheel.py` shows handlers only in `collect_payloads` (`:274`, `:311`), never around `_fetch`.
- **Fix / opportunity:** add a small stdlib retry loop inside `_fetch` (3–5 attempts, short backoff, retry only on `urllib.error.URLError`/`OSError`/`http.client.HTTPException`; never on a 4xx). **Reuse the policy we already ship** rather than a new library: `proot_distro.helpers.download.retry_http(operation, *, what, max_retries=5, retry_delay=5)` (`.venv/Lib/site-packages/proot_distro/helpers/download.py:512-536`) and its classifier `is_retryable_http_error` (`:481-509`) are the house retry semantics. Do **not** import that module from the builder: it is not importable off-Linux — `proot_distro/dirfd.py:73` reads `os.O_DIRECTORY`, which Windows lacks (`AttributeError: module 'os' has no attribute 'O_DIRECTORY'`, reproduced in this venv). Port the ~6-line policy instead, keeping the file stdlib-only as its docstring promises. Note that requests' `HTTPAdapter(max_retries=Retry(total=…, status_forcelist=[…], backoff_factor=…, allowed_methods=[…]))` (`.venv/Lib/site-packages/requests/adapters.py:201-211`; `.venv/Lib/site-packages/urllib3/util/retry.py:43`, `:230-235`) is the *only* ready-made retry in the tree — but adopting it means adding `requests` to a declared dependency group, which D-003 (`docs/decisions.md:12-14`) forbids without owner sign-off, and requests is currently only a *transitive* dev dep of flet-cli, so relying on it would be fragile.
- **Risk if ignored:** a flaky public mirror turns a green pipeline red for no reason. The failure is *not* self-diagnosing: the sha256-mismatch path has a clear message (`:206-209`), but a network failure does not — see F3.

### F2 · P3 · The builder's urllib path follows HTTPS→HTTP redirects and trusts the runner's system CA store

- **Where:** `build_flet_proot_wheel.py:196-199`; `.venv/Lib/site-packages/urllib/request.py` `HTTPRedirectHandler.http_error_302` ("For security reasons we don't allow redirection to anything other than http, https or ftp" — verified in the installed stdlib source); `urllib.request.HTTPSHandler.__init__` (verified: `context=None` → `http.client._create_https_context(http_version)` → `ssl._create_default_https_context()` → the **system** trust store, `verify_mode=CERT_REQUIRED`, `check_hostname=True`).
- **What:** a `Location: http://…` from the Termux pool is followed in cleartext — urllib's default redirect handler has no downgrade rule. TLS verification itself is on and correct, but it anchors to the CI runner's OS CA bundle, not to a pinned bundle. We already ship a hardened downloader that refuses exactly this: `proot_distro.helpers.download.check_redirect` raises `RedirectRefused` for an HTTPS→HTTP hop (`.venv/Lib/site-packages/proot_distro/helpers/download.py:242-289`) and `http_opener` installs that handler (`:373-407`).
- **Evidence:** the integrity of the artifact is nevertheless guaranteed by the sha256 pin (`:204-209`), so a downgrade cannot corrupt the wheel — it can only leak the request path and provoke a pin mismatch. That is why this is P3, not P1: the digest is the real control; the redirect rule is defense in depth.
- **Fix / opportunity:** if F1 is fixed in the same edit, also refuse a scheme downgrade by inspecting `resp.geturl()`/`resp.url` after the fetch and aborting if the final URL is not `https://` (one line, stdlib), mirroring `check_redirect`'s rule.
- **Risk if ignored:** a network-position attacker who can answer with a 302 learns the request path and can force a build failure; they cannot alter the payload.

### F3 · P3 · A 404/5xx from the pool surfaces as a raw traceback, and the builder's `import urllib.error` is dead

- **Where:** `build_flet_proot_wheel.py:18` (`import urllib.error`), `:196-199` (no `except`), `:202-210` (only a sha256 mismatch is converted to a clean `SystemExit`).
- **What:** `import urllib.error` is **never referenced** — an AST scan of the file shows every bound name is used, but `urllib.error` itself is used nowhere (`urllib.request` at `:197-198` is the only use of the `urllib` root). The author imported the error module and then never wired the handling: a 404 from the pool (the exact failure mode already recorded in D-015 item 6 — "Termux removed the old debs from the pool (CI 404)") surfaces as an unhandled `urllib.error.HTTPError` traceback instead of a message naming the package and URL. Ruff does not catch it: `ruff check build_flet_proot_wheel.py` → "All checks passed!" (ruff 0.17.1), because pyflakes treats both `import urllib.error` and `import urllib.request` as bindings of the same root name `urllib`.
- **Evidence:** `grep -n "urllib" build_flet_proot_wheel.py` → only lines 18, 19, 197, 198; `grep -n "try:\|except" build_flet_proot_wheel.py` → no handler on the fetch path.
- **Fix / opportunity:** catch `urllib.error.HTTPError`/`URLError` in `_fetch` and re-raise as `SystemExit(f"[{pkg}] {url}: HTTP {code} — the pinned .deb is gone or the mirror is down; bump _PINNED_SOURCES if the version changed")`, matching the tone of the existing pin-mismatch message (`:206-209`). The `import urllib.error` then earns its place.
- **Risk if ignored:** a CI failure whose cause is a one-line traceback instead of "the pinned .deb 404s" — a small but recurring triage cost on the exact failure that has already bitten this project once (D-015 item 6).

## Missed capabilities (dependency audits only)

requests has real capabilities the project does not use. **None of them should be adopted** — the reasons are architectural, not accidental, and are the substance of this audit's answer.

- **Retry with status-aware backoff** · API: `HTTPAdapter(max_retries=Retry(...))` mounted on a `Session` — `.venv/Lib/site-packages/requests/adapters.py:201-211`, `.venv/Lib/site-packages/urllib3/util/retry.py:230-235` (`total`, `status_forcelist`, `backoff_factor`, `allowed_methods`; `DEFAULT_ALLOWED_METHODS` at `:199-202`, `RETRY_AFTER_STATUS_CODES` at `:205-207`) · Proposed integration point: `build_flet_proot_wheel.py:196` · **Value**: real — this is the one gap (F1). **Cost**: adding `requests` to a declared group requires owner sign-off under D-003 (`docs/decisions.md:12-14`); requests is a *transitive* dev dep of flet-cli, so depending on it directly couples the builder to flet-cli's dependency choices; and the builder is explicitly stdlib-only (`build_flet_proot_wheel.py:4-5`). **Verdict: do not adopt** — port the ~6-line retry policy instead (the shape already exists at `proot_distro/helpers/download.py:512-536`).
- **Async HTTP** · API: none — requests is sync-only (`requests/api.py:69-72`) · Proposed integration point: `src/services/update_service.py:73-76` · **Value**: would be the *only* reason to prefer requests for the app. **Cost**: a sync call inside `async def check_for_update` blocks the Flet session event loop that `page.run_task` schedules onto (`src/app_controller.py:88`; `flet/controls/page.py:929-954`). **Verdict: do not adopt** — httpx is already the house stack (`pyproject.toml:12`) and already ships in the APK; the update-service defects are already owned by `docs/swarm/dependency-utilization/httpx.md` (F1–F7) and are fixed there, not by swapping clients.
- **Connection pooling / `Session` reuse** · API: `Session` (`requests/sessions.py:442-503`) with `mount()` (`:888`) · Proposed integration point: the builder's 6 downloads (3 packages × 2 architectures) · **Value**: negligible — six small files, one host, one run. **Cost**: a dependency. **Verdict: do not adopt.**
- **Streaming downloads** · API: `stream=True` + `Response.iter_content(chunk_size=…)` (`requests/api.py:74`; `.venv/Lib/site-packages/requests/models.py:912-957`, `CONTENT_CHUNK_SIZE = 10*1024` at `:105`) · Proposed integration point: the builder's `_fetch` · **Value**: negligible — the builder needs the .deb **bytes in memory** to parse the `ar` archive (`build_flet_proot_wheel.py:216-245`), and the payloads are small. **Cost**: a dependency for no benefit. **Verdict: do not adopt.** (For scale: cookiecutter's own use of exactly this API, `cookiecutter/zipfile.py:54`, is the pattern requests exists for — a large multi-hundred-MB template zip. Our payloads are Termux .debs, not that.)
- **Checksum verification** · API: **none** — requests has no checksum API; `hashlib` is the only route · Proposed integration point: `build_flet_proot_wheel.py:202-210` · **Value**: n/a — the builder already does the right thing with `hashlib.sha256` (`:204`, `:291`, `:307`, `:426`). **Cost**: n/a. **Verdict: nothing to adopt** — and note this is the axis on which the third stack wins: we already ship `proot_distro.helpers.download.sha256_file` (`.venv/Lib/site-packages/proot_distro/helpers/download.py:539-550`).
- **`REQUESTS_CA_BUNDLE` / `CURL_CA_BUNDLE` override** · API: `Session.merge_environment_settings` (`.venv/Lib/site-packages/requests/sessions.py:831-869`, the env lookup at `:855-860`) · Proposed integration point: the builder's TLS anchor · **Value**: low — the builder runs on ubuntu-latest with a current system store. **Cost**: a dependency. **Verdict: do not adopt.**
- **netrc credentials** · API: `requests.utils.get_netrc_auth` (`.venv/Lib/site-packages/requests/utils.py:231`) · Proposed integration point: n/a — every endpoint we touch is public (Termux apt pool, GitHub releases, `raw.githubusercontent.com`). **Verdict: do not adopt.**

## Verified-good list

- **Installed version confirmed as 2.34.2**: `.venv/Lib/site-packages/requests/__version__.py:8` — `__version__ = "2.34.2"`; license Apache-2.0 (`:12`). Matches `uv.lock:733-734` and the study. No version drift.
- **requests is dev-only, at three independent levels**: (1) `uv tree --no-dev` (the shipping closure) omits it entirely; (2) `uv.lock:184`/`:226`/`:594-601` place it under `dev → flet-cli → cookiecutter → requests`; (3) flet-cli's packager reads only `project.dependencies` + `tool.flet.<platform>.dependencies` (`flet_cli/commands/build_base.py:2566-2573`, `flet_cli/utils/project_dependencies.py:110-131`) and greps zero hits for any dev-group key. **This upgrades the study's "APK-packing claim is UNVERIFIED" (`docs/dependency-studies/requests.md:329-333`) to source-verified at the requirement-list level.** (The final pip resolution inside the Android build remains build-system behavior — see Unverified.)
- **The only importer of requests in the whole installed tree is cookiecutter** — `grep -rn -E "^[[:space:]]*(import requests|from requests)" --include="*.py" .venv/Lib/site-packages/ | grep -v "/requests/"` returns exactly **one** hit: `cookiecutter/zipfile.py:10`. No other installed package touches it.
- **Our CI never reaches the requests branch** — `flet build` resolves the template through flet-cli's stdlib cache (`flet_cli/utils/template_cache.py:38`) and passes cookiecutter a **local** `.zip`; `is_repo_url(<local path>)` is `False` (runtime-verified) so `unzip(..., is_url=True)` is never entered. The remote-zip path exists only in `flet create` (`flet_cli/commands/create.py:118`, `:134`), which our workflow never invokes.
- **The app never imports requests, and a guard test enforces it** — `grep -rn "import requests" src/` → zero hits; `tests/test_proot_surfaces.py:133-148` (`test_dev_only_packages_are_not_imported_from_src`) fails the build if any `src/` file imports `requests` (or cookiecutter/chardet/pytest/ruff/flet_cli/flet_desktop/binaryornot/jinja2). `tests/test_imports_vs_deps.py:46-59` independently enforces that every `src/` import is a declared dependency.
- **The shipped license list matches the shipped closure** — `src/screens/views.py:26-42` lists exactly the runtime dists (proot-distro, flet, flet-ads, flet-terminal, msgpack, anyio, httpx, httpcore, h11, idna, certifi, typing-extensions, oauthlib, repath, six) and correctly omits requests/urllib3/charset-normalizer/cookiecutter/chardet.
- **The builder is self-contained and does not need requests** — `build_flet_proot_wheel.py:4-5` states "Stdlib only"; it imports only stdlib + `hashlib`/`base64`/`struct`/`tarfile`/`zipfile` (`:10-21`); `ruff check build_flet_proot_wheel.py` passes.
- **The builder's integrity control is real** — the sha256 pins live in `_PINNED_SOURCES` (`:34-81`), `_fetch_verified` compares before use (`:202-210`), the payload digests are re-recorded in the wheel manifest (`:291`, `:384`) and the RECORD (`:426-427`). A corrupted or substituted download **cannot** enter a wheel.
- **The builder's TLS is on and correct** — `urlopen` with no `context` uses `ssl._create_default_https_context()` → `verify_mode=CERT_REQUIRED`, `check_hostname=True` (runtime-verified). No `verify=False`, no custom context, no `CERT_NONE` anywhere in the builder.
- **The builder's timeout is bounded** — `TIMEOUT = 120.0` (`:27`) passed to `urlopen` (`:198`); it is a socket timeout, so a dead peer cannot hang the build forever.
- **The builder's user-agent is explicit** — `UA` (`:28`) is set on every request (`:197`); it does not leak a default `python-requests/2.34.2` agent (contrast `requests/utils.py:942` `default_user_agent`).
- **The builder's download is correctly bounded in memory for its purpose** — `resp.read()` on a small .deb is the right shape; the unbounded `read()` path raises `IncompleteRead` when a `Content-Length` body is cut short (verified in the installed `http.client.HTTPResponse.read` source), so a truncated body fails loudly rather than silently.
- **The app's HTTP path is httpx and is already audited** — `src/services/update_service.py:73-76` uses `httpx.AsyncClient(timeout=4.0, follow_redirects=True)`; the constructor matches the installed `httpx/_client.py:1353-1376`; its seven defects (no-op "Check for Updates" button, error reported as "up to date", no size cap, no retry, no client injection, redirect downgrade, no deadline) are **already reported and owned** by `docs/swarm/dependency-utilization/httpx.md` (F1–F7) — not re-opened here.
- **httpx's TLS anchors to certifi, not the Android store** — `httpx/_config.py:31-40` → `ssl.create_default_context(cafile=certifi.where())`; certifi 2026.7.22 is installed and locked (`uv.lock:44-45`). Consistent with `docs/reference/dep-httpx-cluster.md:18`.
- **httpx has no read/status retry** — `AsyncHTTPTransport(retries=N)` is handed to httpcore's connection pool and covers connection establishment only (`httpx/_transports/default.py:291` for the parameter, `:300-311` for the pool construction that receives `retries=retries`); there is no `status_forcelist`/`backoff_factor` equivalent in httpx. This is why "switch the app to requests" is not an answer to the update-service retry gap either.
- **The requests/urllib3/charset-normalizer ceiling pins all hold** — installed `urllib3 2.8.0` (`urllib3<3`), `charset-normalizer 3.5.2` (`<4`), `chardet 5.2.0`; `requests` requires `urllib3>=1.26,<3` and `charset-normalizer>=2,<4` (`requests-2.34.2.dist-info/METADATA:34-37`) — all inside their floors and ceilings, consistent with `docs/reference/dep-cookiecutter-stack.md:19`.
- **The charset detector that actually wins is chardet, and that is benign** — `requests/compat.py:37-49` `_resolve_char_detection()` tries `chardet` first, then `charset_normalizer`; chardet 5.2.0 is installed (via binaryornot), and `requests/__init__.py:80-85` accepts it because `3.0.2 <= 5.2.0 < 8.0.0`. `check_compatibility` (`requests/__init__.py:60-106`) passes for the installed set (no `RequestsDependencyWarning` is emitted — verified at import time). Matches the study's §9 note; behavior note, not a bug.
- **No `verify=False`, no custom SSL context, no bare `except` in the app's HTTP path** — `src/services/update_service.py:73-102` uses httpx defaults (`verify=True`) and a broad `except Exception` that is appropriate for a best-effort check.

## Unverified

- **Live network behavior of any endpoint.** All probes were local or static: the sandbox blocks outbound sockets (`urlopen` to `packages.termux.dev` failed with `URLError: <urlopen error [WinError 10053] An established connection was aborted by the software in your host machine>`). The retry comparison was proven against a local `http.server` on 127.0.0.1, and the redirect-downgrade claim in F2 was proven from the installed stdlib source, not from a live server. The actual failure rate and body sizes of `packages.termux.dev` are unknown; F1's severity rests on the absence of any retry, not on a measured flake rate.
- **The final dependency resolution performed by the Android build** (the pip install of `requirements.txt` inside the Gradle/serious-python pipeline) is build-system behavior. The **requirement list** is now source-verified (see Verified-good), but the observed contents of a built APK were not inspected in this audit — no APK was built.
- **Whether `flet build` is ever run with `--template <remote zip URL>` or `tool.flet.template.url` set** in any environment outside this repo. Our `pyproject.toml` sets neither, and the CI workflow passes no `--template` (`.github/workflows/app.yml:158-161`, `:213-215`), so the requests branch is unreachable here; a maintainer running `flet build --template https://…` locally would reach `cookiecutter/zipfile.py:54` and therefore requests.
- **Whether flet-cli would keep cookiecutter (and therefore requests) as a dependency** in a future release. `flet_cli-1.0.4.dist-info/METADATA:18` requires `cookiecutter>=2.6.0` today. If flet-cli dropped cookiecutter, requests would leave the tree entirely — which is fine for us, since nothing we own imports it.
- **Whether `proot_distro.helpers.download` is importable on the CI runner (ubuntu-latest)** — only the *Windows* failure was reproduced here (`os.O_DIRECTORY`, `proot_distro/dirfd.py:73`). The builder runs on Linux in CI (`app.yml:141`), so the helper *would* import there; the recommendation in F1 deliberately avoids depending on that either way, keeping the builder stdlib-only and locally runnable on Windows.
- **On-device Android behavior of certifi/store and radio timeouts** — no device run was performed; this report verifies the desktop `.venv` source and configuration only.
