## What it does / how the app uses it

`flet-cli` is the host-only build orchestrator (never ships to Android): it resolves the app path and Python release, installs the pinned Flutter 3.44.8 toolchain, renders the version-matched `flet-build-template.zip` through cookiecutter, shells `dart run serious_python:main package`, collects Flutter extension packages, runs `flutter build`, and copies/renames artifacts into `<app>/build/<target>` (`build_base.py:884-954`, `:2514-2873`, `:3218-3386`).

This repo drives two Android targets only. `pyproject.toml` sets `[tool.flet.app] path = "src"`, identity (`org`, `product`, `company`, `build_number`), splash/boot screen, `[tool.flet.android]` (`bundle_id`, `split_per_abi`, `legacy_packaging`, `target_arch`, the `flet-proot` wheel), the `oauthlib` cleanup, `INTERNET`/`ACCESS_NETWORK_STATE`, and the AdMob test application id. `app.yml` runs a `quality` job, creates a placeholder release, then builds APK and AAB on `ubuntu-latest` with env-only keystore signing, a locally built two-arch `flet-proot` wheel set, and post-build inspections.

## Findings

### F1 · P1 · The shipped Python dependency set is unpinned; `flet build` ignores `uv.lock`

- **Where:** `pyproject.toml:9-15` (`flet>=1.0.4`, `flet-ads>=1.0.4`, `flet-terminal>=0.4.0`, `httpx>=0.28.1`, `proot-distro>=5.10.0`); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2566-2574` (reads `project.dependencies`, appends `tool.flet.android.dependencies`), `:2592-2596` (`-r <raw specifier>`), `:2606` (fallback `flet==<cli version>` only when the list is empty); `uv.lock:193-270`; pinned template `build/{{cookiecutter.out_dir}}/pubspec.yaml:13,21`.
- **What:** `flet build` passes the PEP 621 specifiers verbatim to `serious_python`, which pip-installs them into the bundle at build time. No code path in `flet_cli/` reads `uv.lock` (grep: zero hits), so the lock only fixes the host dev environment. The Dart client in the build template is pinned exactly (`flet: 1.0.4`), but the Python side can resolve to a newer family release. `flet-ads 1.0.4` currently pins `flet==1.0.4` (`flet_ads-1.0.4.dist-info/METADATA:14`), which masks the drift today; `flet-terminal 0.4.0` requires `flet` with no version (`flet_terminal-0.4.0.dist-info/METADATA:23`), so the first family release that raises the minimum silently unmasks it.
- **Evidence:** `build_base.py:2572-2574` builds `platform_dependencies` from `tool.flet.{self.config_platform}.dependencies`; `:2595-2596` appends `-r` for each raw string; `:2606` is the only place an exact `flet==` pin is generated. `uv.lock` has `flet 1.0.4`, `flet-ads 1.0.4`, `flet-cli 1.0.4`, `flet-desktop 1.0.4`, `flet-terminal 0.4.0`, but `grep -rn "uv.lock" .venv/Lib/site-packages/flet_cli/` returns nothing. The template's Dart pin is exact: `pubspec.yaml:13` `flet: 1.0.4`.
- **Fix / opportunity:** pin the shipped set exactly (`flet==1.0.4`, `flet-ads==1.0.4`, `flet-cli==1.0.4`, `flet-desktop==1.0.4`, `flet-terminal==0.4.0`, `proot-distro==5.10.0`, `httpx==0.28.1`) and carry the reason in-comment, as `app-ffmpeg.md:6` does. Add a CI assertion after the package step that `build/site-packages/*.dist-info/METADATA` matches the lock (or at least that `flet` is 1.0.4).
- **Risk if ignored:** on the next Flet family release the APK can bundle a newer Python `/flet` against the 1.0.4 Dart client from the template, a wire/constructor mismatch that host tests (which run from the lock) will not catch. This is the exact failure mode `app-ffmpeg.md:6` documents.

### F2 · P1 · The APK "development files" gate never inspects the Python payload

- **Where:** `.github/workflows/app.yml:163-172`; nested-archive proof at `app.yml:275-288`; `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2627-2628`.
- **What:** the APK job runs `unzip -l "$artifact" | grep -qE 'pytest/|ruff/|uvicorn/|starlette/|fastapi/|docs/'`. The Python app is a *stored asset zip* inside the APK (`assets/app/app.zip`), so its members are not APK members and the regex cannot match them. The check therefore passes unconditionally; it is not a gate. It also lacks `set -euo pipefail`, and if `build/apk/*.apk` matches nothing the loop body runs once on a literal path and still exits 0.
- **Evidence:** the AAB job itself demonstrates the nesting: it extracts `base/assets/app/app.zip` before inspecting (`app.yml:280-282`). flet-cli states it explicitly: `build_base.py:2627-2628` — "no app.zip on native; the platform native build copies it into the bundle (Android zips it as a stored asset)". Runnable proof: an APK containing `assets/app/app.zip` with `pytest/...` and `oauthlib/...` members lists as `['AndroidManifest.xml', 'lib/arm64-v8a/libproot.so', 'assets/app/app.zip']` and the workflow regex matches zero members.
- **Fix / opportunity:** mirror the AAB step: `unzip -p "$artifact" assets/app/app.zip > /tmp/app.zip` (fail if absent), then inspect the inner archive; add `set -euo pipefail`; require exactly the expected APK names; assert `oauthlib/` is absent and `flet_proot/` plus `opt/lib` payloads are present.
- **Risk if ignored:** development/test files or the deleted `oauthlib` tree can ship with no signal. The step reads as a compliance gate but proves nothing, which is worse than no step.

### F3 · P1 · The in-app update feed is a 404: `version.json` is gitignored and never published

- **Where:** `version.json:1-10`; `.gitignore:15-19`; `.github/workflows/app.yml` (no step publishes `version.json`); `src/core/constants.py:17`; `src/services/update_service.py:70-85`.
- **What:** the app fetches `https://raw.githubusercontent.com/Nwokike/proot-distro/main/version.json` at startup. The file is explicitly gitignored and is not in `HEAD`, so it never reaches the branch the app reads; the workflow never uploads it to the release either. The local copy is internally consistent (`version 1.0.0`, `build_number 1`, matching `pyproject.toml:5,26`, `src/core/constants.py:11-12`), but it is not reachable by installed apps.
- **Evidence:** `git ls-tree -r HEAD --name-only | grep -c version.json` → `0`; `git ls-files version.json` → empty; `.gitignore:19` → `version.json`; live `curl -s -o /dev/null -w "%{http_code}" https://raw.githubusercontent.com/Nwokike/proot-distro/main/version.json` → `404` (while `main/pyproject.toml` returns `200`). `update_service.py:77-79` returns `None` for any non-200, logged only at debug.
- **Fix / opportunity:** publish the feed deliberately: upload `version.json` to the `app-<run>` release and point `UPDATE_CONFIG_URL` at the release asset, or force-add/commit it to `main` as part of the release ritual and add a post-release CI check that the URL returns 200 and matches `APP_VERSION`/`APP_BUILD_NUMBER`. Update `.gitignore`/runbook so the chosen mechanism is unambiguous.
- **Risk if ignored:** no installed build can ever learn that a newer release exists; the UI always says "up to date". This intersects the separate "Check for Updates" no-op finding, but is independent of it: even a correct click handler would read a 404.

### F4 · P1 · License texts are read through `__file__`, which under the Android app.zip points inside an archive

- **Where:** `src/screens/views.py:20` (`_LICENSES_DIR = Path(__file__).resolve().parent.parent / "LICENSES"`), `:626-628` (`path.is_file()` then `read_text`); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2627-2628` (Android zips the app as a stored asset); same pattern at `src/components/brand_hero.py:21-30`. `extract_packages` is implemented at `build_base.py:2733` and forwarded at `:3027`.
- **What:** the app directory is zipped into `app.zip` and imported by zipimport on Android; `__file__` is then `.../app.zip/screens/views.py`, so `parent.parent / "LICENSES"` resolves to `.../app.zip/LICENSES`, which is not a file. Every license tile falls back to the literal string `"(text missing)"`. The same mechanism makes `brand_hero.app_icon_svg()` find nothing and return `b""`. `--android-extract-packages` cannot fix this: it applies to site-packages only (`build_base.py:2732-2742`), while the app payload is staged separately (`:2627-2628`).
- **Evidence:** runnable zipimport proof with the installed interpreter: a module inside `app.zip` reports `file: ...\app.zip\pkg\mod.py`; `Path(__file__).resolve().parent.parent / "LICENSES"` resolves to `...\app.zip\LICENSES` with `is_file: False`. `src/LICENSES/` exists in `HEAD` and is packaged, so the texts are present but unreachable through `Path`.
- **Fix / opportunity:** app-side (this report is read-only): read the texts through `importlib.resources` from a real package (e.g. make `LICENSES` importable or use `importlib.resources.files("screens").parent`-style access), or copy them into `src/assets/licenses/` and read them through Flet's asset mechanism; keep the repo `LICENSES/` for the source offer. Do not add `extract_packages` hoping to fix it — that knob only extracts site-packages.
- **Risk if ignored:** on device the About → Licenses screen shows `(text missing)` for GPL-2.0/GPL-3.0/Apache/BSD texts, breaking the app's own compliance contract; the brand hero can render without its icon. Cross-scope note: the fix belongs to the app audit, but the trigger is the flet-cli packaging mode this audit covers.

### F5 · P2 · `[tool.flet] icon` is a key with no effect

- **Where:** `pyproject.toml:27-28`; `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2196` (only `tool.flet.icon_background` is read), `:1002-1005`, `:2092`, `:2100-2107` (icon discovery); pinned template `build/cookiecutter.json` (no `icon` key).
- **What:** flet-cli never reads `tool.flet.icon` (grep for `tool.flet.icon` matches only `icon_background`), and the template has no `icon` context key. Icons are discovered from `<app.path>/assets/icon.png` (`build_base.py:2092`: `self.assets_path = self.package_app_path.joinpath("assets")`). The file is currently at `src/assets/icon.png` and therefore *is* used by convention; the key itself is ignored.
- **Evidence:** `grep -rn 'tool\.flet\.icon' .venv/Lib/site-packages/flet_cli/` → only `build_base.py:2196` (`tool.flet.icon_background`). `ls -l src/assets/icon.png` → present (99,177 bytes). The pinned template's `cookiecutter.json` has no `icon` entry.
- **Fix / opportunity:** remove the key (and keep the conventional file), or add a comment that the icon path is fixed at `src/assets/icon.png`; if a custom location is ever required, that is not a supported 1.0.4 key.
- **Risk if ignored:** a future icon move guided by this key is silently ignored and the build keeps the conventional (or default) icon.

### F6 · P2 · HALLUCINATION in the prior studies: `target_sdk_version` / `min_sdk_version` do exist, and neither SDK level is pinned

- **Where:** `docs/dependency-studies/flet-cli.md:362` and `docs/reference/dep-flet-cli.md:12` ("zero reads; do not use"); pinned template `build/{{cookiecutter.out_dir}}/android/app/build.gradle.kts:72-79` and `build/cookiecutter_extensions.py:5-21`.
- **What:** flet-cli Python has zero reads, but the v1.0.4 build template reads both keys through its `get_pyproject` Jinja extension and emits `minSdk = resolvedMinSdk` / `targetSdk = resolvedTargetSdk`, falling back to `flutter.minSdkVersion` / `flutter.targetSdkVersion`. The app sets neither, so both levels are whatever Flutter 3.44.8 defaults to. CI asserts `targetSdkVersion >= 36` after the fact (`app.yml:233-240`) but never pins it; `minSdkVersion` is printed (`app.yml:234-235`) and never asserted, while the native payload wheel is tagged `android_24` (`build_flet_proot_wheel.py:182-185`).
- **Evidence:** the downloaded pinned template (same URL flet-cli uses: `build_base.py:67-70`, `:1830-1859`) contains `{% set min_sdk_version = get_pyproject("tool.flet.android.min_sdk_version") %}` and the `val resolvedMinSdk = ...` / `val resolvedTargetSdk = ...` lines. `build/cookiecutter_extensions.py:5-21` defines the extension reading `cookiecutter.pyproject`. The template zip is v1.0.4 because `template_ref` defaults to `flet.version.flet_version` (`build_base.py:1834-1836`; installed `flet/version.py:19` = `1.0.4`).
- **Fix / opportunity:** add `target_sdk_version = 36` and `min_sdk_version = 24` under `[tool.flet.android]` in `pyproject.toml`; extend the AAB manifest step to assert `minSdkVersion >= 24`. Correct both study files: the keys are not read by flet-cli Python but are first-class template inputs in 1.0.4.
- **Risk if ignored:** a Flutter or flet-cli bump silently changes the SDK levels; an install floor below the payload's `android_24` tag can ship the container engine to devices where it cannot run, and the Play target gate becomes dependent on an upstream default rather than this repo's intent.

### F7 · P2 · No toolchain/cache pinning or reuse in CI

- **Where:** `.github/workflows/app.yml:29-37` (no `FLET_CACHE_DIR`, no `FLET_PYTHON_BUILD_RELEASE_DATE`, no `actions/cache`); `.venv/Lib/site-packages/flet_cli/utils/template_cache.py:15-18`; `utils/python_versions.py:31-34`; `utils/flutter.py:43-55`; `utils/android.py:78-91` (SDK root autodetect).
- **What:** each apk/aab job re-downloads Flutter 3.44.8 to `~/flutter/3.44.8`, auto-installs the Android SDK/JDK, and re-fetches the build template plus the python-build manifest. `FLET_PYTHON_BUILD_RELEASE_DATE` is implicit in flet-cli 1.0.4 (code pin `20260921`), not asserted in the repo; a lock refresh moves it silently. The template fetch has no checksum or revalidation (`template_cache.py:21-48`), so cache reuse is also the only defense against an upstream deletion.
- **Evidence:** `grep -rn "FLET_CACHE_DIR\|FLET_PYTHON_BUILD_RELEASE_DATE" .github/workflows/app.yml` → no hits; `grep -n "actions/cache" app.yml` → no hits. `python_versions.py:31` `PYTHON_BUILD_RELEASE_DATE = "20260921"`; `template_cache.py:15-18` resolves `$FLET_CACHE_DIR` or `~/.flet/cache`; `flutter.py:54-55` returns `~/flutter/<version>`.
- **Fix / opportunity:** set `FLET_PYTHON_BUILD_RELEASE_DATE: "20260921"` and `FLET_CACHE_DIR: ${{ github.workspace }}/.flet-cache`; add `actions/cache` for `~/.flet/cache`, `~/flutter/3.44.8`, `$ANDROID_SDK_ROOT`, and `~/.gradle/caches`, keyed on `hashFiles('uv.lock')` plus the Flet version. A `wheels` job would also avoid rebuilding the payload twice (F12).
- **Risk if ignored:** slow, flaky, network-dependent releases; after a lock bump the bundled Python/manifest can change with no diff in this repo.

### F8 · P2 · The AAB payload inspection is fail-open and never asserts the pruned/payload state

- **Where:** `.github/workflows/app.yml:275-288`.
- **What:** the step does `unzip ... "base/assets/app/app.zip" ... || true` and then `if [ -f ... ]`; if the inner path changes, the extraction fails silently and the whole check is skipped. The `for artifact in build/aab/*.aab` loop does not fail when the glob matches nothing. It also never asserts the things the build claims: that `oauthlib/` is absent after `cleanup.package_files`, or that `flet_proot`/`opt/lib` is present.
- **Evidence:** `|| true` on line 280 plus the guarded `if` on line 281; no `oauthlib` or `flet_proot` reference anywhere in the step (`app.yml:275-288`). `pyproject.toml:62-63` is the only place the diet is declared; `build_base.py:2770-2784` shows the CLI simply forwards the glob and forces `--cleanup-packages`.
- **Fix / opportunity:** drop `|| true`, fail when the inner archive is absent, enumerate AABs with `find` and require exactly one, then grep the inner listing for `oauthlib/` (must be absent), `flet_proot/` and `opt/lib/` (must be present).
- **Risk if ignored:** the declared APK diet and payload are unverified; a packaging-path change disables the gate with no failure.

### F9 · P2 · No signature, package-id, or versionCode verification; the debug-signing fallback is latent

- **Where:** `.github/workflows/app.yml:143-161` (APK), `:197-215` (AAB); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:3056-3091`; pinned template `build/{{cookiecutter.out_dir}}/android/app/build.gradle.kts:102-118`.
- **What:** the template creates the release signing config only when `options.android_signing` is true; that flag is `bool(CLI key store or pyproject key_store or FLET_ANDROID_SIGNING_KEY_STORE)` (`build_base.py:1633-1637`). If the env var disappears or is renamed, the `{% else %}` branch signs the **release** build with the debug keystore, and nothing in CI notices. The workflow also never verifies the output certificate, the application id (`ng.kiri.prootdistro`), or the `versionCode` derived from `--build-number`.
- **Evidence:** `build.gradle.kts:104-118` — `signingConfig = signingConfigs.getByName("release")` inside `{% if cookiecutter.options.android_signing %}`, else `getByName("debug")`; `build_base.py:3063-3091` only exports the env vars when present. `app.yml` has no `apksigner`, `jarsigner`, `package=`, or `versionCode` assertion (grep).
- **Fix / opportunity:** after each build, run `apksigner verify --print-certs build/apk/*.apk` and `jarsigner -verify build/aab/*.aab`, compare the signer SHA-256 to a repo variable, and assert `package="ng.kiri.prootdistro"` plus `android:versionCode="${BUILD_NUMBER}"` in the merged manifest.
- **Risk if ignored:** a secret/renaming mistake can publish debug-signed artifacts or an artifact with the wrong application id/version code; Play rejects the first, and users cannot upgrade over the second.

### F10 · P2 · CI never asserts that both requested ABIs produced artifacts

- **Where:** `pyproject.toml:49`; `.venv/Lib/site-packages/flet_cli/commands/build_base.py:1408-1445`; `commands/build.py:166-179`; `.github/workflows/app.yml:163-181`.
- **What:** the config correctly requests `arm64-v8a` and `x86_64`, and flet-cli maps them to `--target-platform android-arm64,android-x64` and excludes `armeabi-v7a` from jniLibs. `split_per_abi` produces one APK per ABI. The workflow uploads `build/apk/*.apk` without checking the count or names, so a missing ABI (regression, packaging change, or a partially failed wheel) still uploads a green build.
- **Evidence:** runnable calls with the installed package: `excluded_android_abis(["arm64-v8a","x86_64"])` → `['armeabi-v7a']`; `flutter_target_platforms([...])` → `['android-arm64', 'android-x64']`. `build.py:166` appends `--split-per-abi` for apk; `:171-179` appends `--target-platform`. `app.yml:165` is only `ls -lh build/apk/*.apk`; `:181` uploads the glob.
- **Fix / opportunity:** require exactly `proot-distro-flet-arm64-v8a.apk` and `proot-distro-flet-x86_64.apk`, and for each check `unzip -l` contains `lib/<abi>/libproot.so` and `libproot-loader.so`; print per-ABI sizes.
- **Risk if ignored:** a one-ABI release passes CI; x86_64 emulator QA or arm64 devices get no build.

### F11 · P2 · Bundled Python is selected by an open `requires-python`, not pinned

- **Where:** `pyproject.toml:8` (`requires-python = ">=3.14"`); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:923-927`; `utils/python_versions.py:31,139-213`.
- **What:** `resolve_python_version` picks the highest *stable* manifest row matching the specifier. Today that is 3.14.7, and the manifest lists `arm64-v8a`, `x86_64`, `armeabi-v7a` (verified against `manifest-20260921.json`), so the build works. But no `--python-version` is passed, and the manifest date is owned by flet-cli; a routine lock bump can move the selected row to a newer CPython line without a change in this repo.
- **Evidence:** runnable `resolve_python_version(None, ...)` with `project.requires-python = ">=3.14"` → `resolved: 3.14 3.14.7 ... prerelease: False`; `python_versions.py:177-183` selects `max(stable_matching)`; `build_base.py:2558-2561` forwards only the short version.
- **Fix / opportunity:** pass `--python-version 3.14` in both build steps, or narrow `requires-python` to `>=3.14,<3.15`; the exact short version is what `serious_python` consumes (`build_base.py:2558-2561`).
- **Risk if ignored:** a silent interpreter change on a dependency refresh; the `.python-version` wipe (`build_base.py:940-954`) protects against stale bytecode but not against an unintended upgrade.

### F12 · P3 · Both Android jobs rebuild the same wheel set; the fetcher has no retry

- **Where:** `.github/workflows/app.yml:140-141` and `:194-195`; `build_flet_proot_wheel.py:447-463`.
- **What:** the APK and AAB jobs each run the full Termux fetch + wheel assembly, so both depend on `packages.termux.dev` independently. `_fetch` is a single `urlopen` with a 120 s timeout and no retry.
- **Evidence:** identical `uv run python build_flet_proot_wheel.py --out wheels` steps in both jobs; `_fetch` at `build_flet_proot_wheel.py:196-199` has no loop.
- **Fix / opportunity:** build the wheels once in a `wheels` job, upload as an artifact, and download in both Android jobs; add a small retry/backoff in `_fetch` (the sha256 pins make retries safe).
- **Risk if ignored:** duplicate CI time and two independent chances for an upstream/network failure to kill the release.

### F13 · P3 · The release placeholder is never finalized or promoted

- **Where:** `.github/workflows/app.yml:110-128`; `docs/release-runbook.md` section 5 (manual).
- **What:** `prepare-release` creates a prerelease with a fixed placeholder body; no job later replaces the body with `version.json`'s `release_notes`, attaches the update feed, or promotes the release. The runbook makes this manual, so it is a known gap, but it is the same drift `app-ffmpeg.md:21` flags.
- **Evidence:** the placeholder body is a literal string at `app.yml:120-123`; the only later release operations are asset uploads (`:177-181`, `:296-303`).
- **Fix / opportunity:** add a finalize job that reads `version.json` and updates the release body / prerelease flag, or make the runbook step a required checklist item in CI (e.g. fail if the body still equals the placeholder on a tagged release).
- **Risk if ignored:** every release page keeps the automated placeholder text, even after the runbook's manual finalize is forgotten.

### F14 · P2 · No AdMob production-ID guard; the test ID ships on every build

- **Where:** `pyproject.toml:70-75`; `.github/workflows/app.yml:231-268` (presence check only).
- **What:** the AAB manifest step asserts the AdMob `APPLICATION_ID` is present, not that it is the production id. Today the repo intentionally carries Google's public test id, and the comment says M5 swaps it; any tag/release built before that swap ships test ads and does not match the Play data-safety declaration. `app-ffmpeg.md:16` calls for a production-ID guard as a quality gate.
- **Evidence:** `pyproject.toml:75` → `ca-app-pub-3940256099942544~3347511713`; `app.yml:231-232` only records `admob`; `:265-268` only fails when it is empty.
- **Fix / opportunity:** add a guard that fails a tagged/release build when the test id is present, and source the production id from a secret (or a `tool.flet.android.meta_data` override applied only on release).
- **Risk if ignored:** a production upload can show test ads (no revenue) and misdeclare the ads SDK configuration.

## Missed capabilities (dependency audits only)

- **Template-level SDK keys** · `target_sdk_version` / `min_sdk_version` are first-class template inputs in 1.0.4 (pinned template `build.gradle.kts:72-79`, `cookiecutter_extensions.py:5-21`) even though `flet_cli/` Python never reads them · integration: `[tool.flet.android]` · value: deterministic Play target 36 and install floor 24; cost: two lines. This is the correction to the prior study's "do not use".
- **`tool.flet.android.manifest_application`** · arbitrary `<application>` attributes, read directly by the pinned template (`AndroidManifest.xml:13-21`) · integration: a table in `pyproject.toml` · value: e.g. `android:largeHeap` or explicit attributes without patching the template; cost: low. Not needed today.
