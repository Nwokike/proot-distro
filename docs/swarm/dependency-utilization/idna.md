**Verdict:** MIXED
**Confidence:** high
**Scope:** `docs/dependency-studies/idna.md`; `docs/reference/dep-httpx-cluster.md`; `pyproject.toml`; `uv.lock`; `src/core/constants.py`; `src/services/update_service.py`; `src/services/proot_service.py`; `src/screens/views.py`; `src/components/update_dialog.py`; `src/app_controller.py`; `src/core/shared_services.py`; `.venv/Lib/site-packages/idna/`; `.venv/Lib/site-packages/httpx/_urlparse.py`; `.venv/Lib/site-packages/httpx/_urls.py`; `.venv/Lib/site-packages/anyio/_core/_sockets.py`; `.venv/Lib/site-packages/anyio/streams/tls.py`; `.venv/Lib/site-packages/requests/models.py`; `.venv/Lib/site-packages/urllib3/util/url.py`; `.venv/Lib/site-packages/proot_distro/helpers/docker/refs.py`; `.venv/Lib/site-packages/proot_distro/commands/install.py`; `.venv/Lib/site-packages/proot_distro/helpers/download.py`; `.venv/Lib/site-packages/flet/controls/core/markdown.py`; `.venv/Lib/site-packages/flet/controls/services/url_launcher.py`; CPython 3.14.7 stdlib `Lib/urllib/parse.py`, `Lib/encodings/idna.py`, `Lib/ssl.py` · **Date:** 2026-10-20

## What it does / how the app uses it

**The app does not import `idna`, and it does not need to. `idna` is dormant, correctly so.** The only occurrence of the string in `src/` is a license-disclosure entry (`src/screens/views.py:36`); `grep -rni idna src/` returns exactly that one hit. It is a transitive dependency only — absent from the direct dependency list (`pyproject.toml:9-15`: flet, flet-ads, httpx, flet-terminal, proot-distro) and present in the lock as a child of `anyio` (`uv.lock:6-10`) and `httpx` (`uv.lock:299-306`).

The app has exactly three host-bearing surfaces, and **none of them requires direct IDNA handling**:

1. **Update feed host** — a hardcoded ASCII constant, `UPDATE_CONFIG_URL = "https://raw.githubusercontent.com/Nwokike/proot-distro/main/version.json"` (`src/core/constants.py:17`). It is fetched by httpx (`src/services/update_service.py:75-80`). httpx A-label-encodes a non-ASCII host itself (`httpx/_urlparse.py:388-392`), and anyio's socket layer does the same with UTS #46 opt-in (`anyio/_core/_sockets.py:62-68`, used at `:656`). Because the host is ASCII and `check_for_update` is only ever called with its default (`src/app_controller.py:313`; `src/components/update_dialog.py:157`; default at `src/services/update_service.py:70`), the idna path exists but is **never entered**.
2. **OCI registry hosts** — never parsed by the app. `src/services/proot_service.py:212-223` hands the raw image ref to upstream, whose Docker reference grammar is **ASCII-only** (`proot_distro/helpers/docker/refs.py:77-85`, `_DOMAIN_RE` built with `re.ASCII`; enforced at `refs.py:209-216`). Runtime-verified: `parse_reference("münchen.example.com/app:1")`, `("例え.テスト/app:1")`, `("bücher.example/app")` and `("MÜNCHEN.example.com/app")` all raise `InvalidReference: invalid reference format: registry host is not valid`. A non-ASCII registry host cannot reach a socket.
3. **User-entered image refs** — `src/screens/views.py:93-96` strips whitespace and nothing else; there is no app-side host parsing or format validation to make IDNA-aware. Upstream validates (item 2).

The upstream registry/URL transport is stdlib `urllib.request` (`proot_distro/helpers/download.py:44,204-217`), **not** httpx — so idna is not on the registry path either.

The one place the app compares a hostname *itself* is `is_allowed_launch_url()` (`src/services/update_service.py:26-37`), used by `_safe_url` (`:44-47`) for the feed's `github_url`/`playstore_url` (`:97-98`) and re-checked before every launch (`src/components/update_dialog.py:23-26`). The comparison is ASCII-exact against three ASCII literals (`:23,36-37`). **The IDN dimension of that check is sound** (see Verified-good). The *URL-syntax* dimension of that check is not — that is F1 below, and idna is not the tool that fixes it.

## Findings

### F1 · P1 · The launch-URL allow-list approves a host the browser will never visit (backslash before `@`)

- **Where:** `src/services/update_service.py:26-37` (the check), `:44-47` + `:97-98` (the feed's URLs flow through it), `src/components/update_dialog.py:23-26` (the launch), `:134` and `:141` (the two buttons), `:71` and `:92` (release-note links). CPython: `Lib/urllib/parse.py:447`. Not fixed by swapping parsers: `.venv/Lib/site-packages/httpx/_urlparse.py:348-392`.
- **What:** `is_allowed_launch_url` extracts the host with `urllib.parse.urlsplit` and compares `parts.hostname`. `urlsplit` defines the host as everything after the **last** `@` in the netloc (`Lib/urllib/parse.py:447`: `hostname_and_port = netloc.rpartition('@')[2]`) and gives `\` no special meaning. A URL of the form `https://evil.com\@github.com/` therefore reports `hostname == "github.com"` and **passes** the allow-list. WHATWG URL parsing — the algorithm Android's Chrome/WebView implements — converts `\` to `/` inside a special scheme's authority, so the *same string* resolves to host **evil.com**. The app then hands that string to the platform URL launcher.
- **Evidence:**

  | URL | Python `urlsplit().hostname` | WHATWG `URL.host` | `is_allowed_launch_url` | real host |
  |---|---|---|---|---|
  | `https://evil.com\@github.com/` | `github.com` | **`evil.com`** | **True** | **evil.com** |
  | `https://evil.com\\@github.com/` | `github.com` | **`evil.com`** | **True** | **evil.com** |
  | `https://user:pass@evil.com\@github.com/` | `github.com` | **`evil.com`** | **True** | **evil.com** |
  | `https://github.com\@evil.com/` | `evil.com` | `github.com` | False | github.com |
  | `https://github.com/\@evil.com` | `github.com` | `github.com` | True | github.com |
  | `https://évil.com/` | `évil.com` | `xn--vil-9la.com` | False | — |
  | `https://xn--gthub-4va.com/` | `xn--gthub-4va.com` | `xn--gthub-4va.com` | False | — |

  Python side (runtime, `.venv` Python 3.14.7): `urlsplit("https://evil.com\\@github.com/").hostname == "github.com"`; `is_allowed_launch_url("https://evil.com\\@github.com/") is True`.
  WHATWG side (Node's `URL`, the URL Standard reference implementation): `new URL("https://evil.com\\@github.com/").host === "evil.com"`, `href === "https://evil.com/@github.com/"`.
  httpx parses it the same wrong way: `httpx.URL("https://evil.com\\@github.com/").host == "github.com"`, so httpx's parser is **not** a drop-in fix.
- **Fix / opportunity:** normalize the way WHATWG does before splitting — in a special scheme `\` is a path separator, so the authority ends at the first `\` or `/`. Minimal form: reject the URL if `\` appears in the netloc, or replace `\` with `/` in the whole URL before `urlsplit`, then keep the existing ASCII-exact host comparison. **Do not reach for `idna` here:** idna is an IDNA codec and has nothing to say about backslashes; `idna.encode("evil.com\\@github.com")` is not a URL parse. A pure idna-based fix does not exist for this bug.
- **Risk if ignored:** the feed's `github_url`, `playstore_url` and every link in the remote release notes are remote content — the app says so itself (`src/components/update_dialog.py:4-5`: "the notes are remote markdown"), and the allow-list is the only guard. The update check follows redirects with no final-host or final-scheme check (`src/services/update_service.py:75-80`), so a hostile feed — or a network attacker able to steer that redirect — can make the app open an arbitrary https URL in the user's browser while the allow-list reported "github.com". The user sees only a button labelled "Release page" (`src/components/update_dialog.py:138-142`); the effective host is never displayed, so the substitution is invisible.

### F2 · P3 · A user-typed IDN URL image ref would be encoded by the stdlib's IDNA 2003 codec, not by the `idna` we already ship

- **Where:** `src/screens/views.py:93-96` (the image ref is not validated in the app), `src/services/proot_service.py:212-223` (the raw ref is handed to upstream); upstream `proot_distro/commands/install.py:85-87` (`_is_url` accepts **any** string starting with `http://`/`https://`) and `:164-165` (that mode therefore **bypasses** the ASCII reference grammar at `:172-177`); `proot_distro/helpers/download.py:44,204-217` (stdlib `urllib.request`); CPython `Lib/encodings/idna.py:1`, `Lib/ssl.py:443-447`.
- **What:** `https://münchen.example.com/x.tar.gz` typed into the image-ref field is a valid "URL image" for upstream, and it reaches the network with the host A-label-encoded by CPython's `encodings.idna` — **IDNA 2003 over Unicode 3.2 tables** (`Lib/encodings/idna.py:1`: "This module implements the RFCs 3490 (IDNA) and 3491 (Nameprep)"; `Lib/ssl.py:443-447`: `_encode_hostname` → `hostname.encode('idna')` for SNI) — not by `idna` 3.20 (IDNA 2008 over Unicode 18.0.0, `idna/idnadata.py:3`). Runtime-verified divergence: `"faß.de".encode("idna")` → `b'fass.de'` vs `idna.encode("faß.de", uts46=True)` → `b'xn--fa-hia.de'` — **two different hosts**; `"ς.gr"` → `b'xn--4xa.gr'` vs `b'xn--3xa.gr'`. Proof that the stdlib codec is the one applied: `socket.getaddrinfo("a"*64 + ".com", 443)` raises `UnicodeError: 'idna' codec can't encode characters in position 0-63: label too long`, while `socket.getaddrinfo("münchen.example.com", 443)` was accepted by that codec and failed only at DNS (`gaierror`).
- **Fix / opportunity:** none required today — the divergence is confined to a handful of codepoints (ß, ς, ZWJ/ZWNJ) and only affects a user-typed *tarball URL*, an exotic path. If the app ever wanted pinned Unicode-18.0.0 normalization it would A-label the host itself with `idna.encode(host, uts46=True)` before handing the URL upstream. Do not add that speculatively: it would be the first `import idna` in the app for a cosmetic difference.
- **Risk if ignored:** cosmetic only. A host valid under one table set and not the other would resolve differently from the app's other paths; no user-visible symptom today, and the behavior is upstream's, not the app's.

## Missed capabilities (dependency audits only)

The honest answer is **none worth adopting**. Every `idna` capability was checked against a concrete integration point in this app:

- **`idna.encode(host, uts46=True)` as an allow-list canonicalizer** · API: `idna/core.py:732` (the anyio-proven form, `anyio/_core/_sockets.py:62-68`) · Integration point: `src/services/update_service.py:36-37` · Value: would make the host comparison Unicode-18.0.0-deterministic if the allow-list ever gained an IDN entry · Cost: one import + one call per candidate host · **Not needed today** — the allow-list is ASCII-only and the comparison is already exact-match, so every IDN, Punycode and confusable variant is rejected today (runtime-verified, see Verified-good). Listed for completeness only.
- **`idna.decode(host, display=True)` for showing a registry host in the UI** · API: `idna/core.py:819-825` (the `display` flag exists for exactly this) · Integration point: the image-ref line in the container row, `src/screens/views.py:279-281` · Value: would render `münchen.de` instead of `xn--mnchen-3ya.de` without raising on a fake A-label (`ulabel` at `idna/core.py:558` rejects `xn---bbk` with `code="non_canonical_alabel"`, raised at `idna/core.py:606`) · Cost: one call · **Not needed today** — the refs shown there come from upstream's ASCII-only grammar, so they are ASCII by construction.
- **`idna.IDNAError.code` (26 stable codes, `idna/core.py:70-107`) for a friendly "that registry name is not valid" message** · Integration point: `src/services/proot_service.py:415-423` (`friendly_job_error`) · Value: a structured error instead of string matching · Cost: one `except` clause · **Not applicable** — the host is rejected by upstream's ASCII grammar *before any socket work*, so no `idna` exception is ever raised on that path. The right fix for that message is to surface upstream's `InvalidReference`, not to add an idna `except`.
- **The `"idna2008"` stdlib codec** (`idna/codec.py:201-225`, registered at `:225`) · **No integration point** in this app; a stdlib-codec integration would be worse than the direct API.
- **`idna.compat.ToASCII/ToUnicode`** (`idna/compat.py:8,21`) · **Shims; must not be used in new code** (the module's own docstrings point at `idna.encode`/`idna.decode`).

## Verified-good list

- Installed `idna` is **3.20** with **Unicode 18.0.0** tables (runtime: `idna.__version__ == "3.20"`, `idna.unicode_version == "18.0.0"`), matching `docs/dependency-studies/idna.md:16-20` and `uv.lock:314-319`. Every API the study cites was spot-checked against the installed source and the study's line numbers are accurate: `encode` `idna/core.py:732`, `decode` `:799` (with the `display` parameter documented at `:819-825`), `alabel` `:524`, `ulabel` `:558`, `uts46_remap` `:637`, `IDNAError` `:70-107` (`code`/`text`/`codepoint`/`position` at `:90-107`), `_max_input_length` `:14`, `_max_domain_length` `:15`, `codec.search_function` `idna/codec.py:201`, `codecs.register` `:225`, `compat.ToASCII/ToUnicode` `idna/compat.py:8,21`, public re-exports and `__all__` `idna/__init__.py:1-47`. `InvalidCodepointContext` is exported and in `__all__` (`idna/__init__.py:31,45`).
- The app never imports `idna`; the only hit is the license list (`src/screens/views.py:36`), and the dependency is correctly transitive-only (`pyproject.toml:9-15`; root package block `uv.lock:583-592`).
- The update-feed host is a hardcoded ASCII constant (`src/core/constants.py:17`) and `check_for_update` is never called with a custom URL (`src/app_controller.py:313`; `src/components/update_dialog.py:157`; default `src/services/update_service.py:70`), so httpx's `idna.encode` at `httpx/_urlparse.py:390` is unreachable for a non-ASCII host. httpx's display-decode at `httpx/_urls.py:191` fires only for a host starting with `xn--` — impossible here.
- **The IDN dimension of the app's host allow-list is correct.** The comparison is ASCII-exact against three ASCII literals (`src/services/update_service.py:23,36-37`), so no Unicode or Punycode host can satisfy `host == "github.com"` or `host.endswith(".github.com")`. Runtime-verified rejections: `https://évil.com/`, `https://xn--gthub-4va.com/`, `https://gıthub.com/` (dotless i), and a zero-width-joiner host all return `False`. The WHATWG parser agrees on the outcome (it IDNA-encodes `évil.com` to `xn--vil-9la.com`, still not allow-listed).
- `is_allowed_launch_url` fails closed on malformed URLs: `urlsplit` `ValueError` is caught (`src/services/update_service.py:32-33`), which is what Python 3.14 raises for a netloc that NFKC-normalizes into a delimiter.
- The scheme check is exact (`parts.scheme != "https"`, `src/services/update_service.py:34`), so `http:`, `javascript:` and `data:` URLs are rejected before the host is considered; `HTTPS://github.com/` is correctly accepted (`urlsplit` lowercases the scheme).
- The upstream registry/transport path is stdlib `urllib.request` (`proot_distro/helpers/download.py:44,204-217`), so neither httpx nor idna is on it; the `idna`-using branches of httpx/anyio are not exercised by registry traffic.
- The upstream Docker grammar is ASCII-only and enforced before any network call (`proot_distro/helpers/docker/refs.py:77-85,209-216`; `proot_distro/commands/install.py:172-177`), so a non-ASCII registry host is refused with a clear message rather than mangled.
- httpx's own idna use is dormant: `httpx/_urlparse.py:390` and `httpx/_urls.py:191` are reached only for a non-ASCII / `xn--` host; flet has **no** direct `idna` import (grep over `.venv/Lib/site-packages/flet/` → no hits) and imports httpx lazily inside `flet/auth/*` only — the app ships no OAuth flow.
- **The dependency study's call-site table is incomplete but its conclusion still holds.** Two further idna call sites exist, both in the **dev toolchain only**: `requests/models.py:472-478` (`_get_idna_encoded_host` → `idna.encode(host, uts46=True)`) and `urllib3/util/url.py:432-446` (`_idna_encode` → `idna.encode(name.lower(), strict=True, std3_rules=True)`). `requests` reaches the venv through `flet-cli` → `cookiecutter` (`flet_cli-*.dist-info/METADATA`: `Requires-Dist: cookiecutter>=2.6.0`; `uv.lock:174-184` for cookiecutter → requests, `uv.lock:733-739` for requests → idna), and `flet-cli` is in the **dev** group only (`pyproject.toml:77-85`; `uv.lock:594-601`) — so `requests`/`urllib3` are not in the shipped runtime set. `proot_distro` does not import `requests` or `urllib3` (grep → no hits), and neither does flet.

## Unverified

- **On-device (Android) URL resolution.** Flet's `UrlLauncher.launch_url` (`flet/controls/services/url_launcher.py:72`) forwards the string to the Flutter client, which is not in this venv; no device run was performed. The Python-vs-WHATWG divergence in F1 is proven with CPython's `urlsplit` and Node's `URL` (the URL Standard reference implementation), but the exact Android Chrome/WebView/Custom-Tabs behaviour on the Flet launch path was not directly observed. If the Flutter client normalizes the URL before handing it to the platform, F1 would be inert in practice — I could not check that from the Python side.
- **Whether Flet's Markdown renderer preserves a backslash in a link destination.** CommonMark would escape `\＠` to `@` inside a link destination, which would affect the release-notes path of F1. The `github_url`/`playstore_url` JSON path is unaffected — those are plain strings handed straight to `_launch` (`src/components/update_dialog.py:134,141`).
- **Real-world exploitability of F1.** No live request to the update feed was made and no feed content was inspected; the precondition is attacker-controlled feed content (compromised repo, or a network attacker able to steer the update check's redirect — see the httpx audit's F6 on the missing final-host check).
- The IDNA 2003 vs 2008 divergence examples (`faß.de`, `ς.gr`) are from the installed stdlib codec and the installed `idna` 3.20 on CPython 3.14.7; no device run was performed, and the Android build's interpreter was not exercised.
- Whether the Flet Android build strips `requests`/`urllib3` from the packaged APK was not verified from the build output; the conclusion rests on `pyproject.toml:77-85` / `uv.lock:594-601` (dev group) and on the fact that no runtime package imports them.
