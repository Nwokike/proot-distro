## What it does / how the app uses it

`chardet` 5.2.0 is a pure-Python, LGPL-2.1 universal encoding detector: `detect(byte_str, should_rename_legacy=False) -> ResultDict` (`.venv/Lib/site-packages/chardet/__init__.py:30`), `detect_all(byte_str, ignore_threshold=False, should_rename_legacy=False) -> List[ResultDict]` (`__init__.py:53`), and the incremental `UniversalDetector` (`__init__.py:24`, `.venv/Lib/site-packages/chardet/universaldetector.py:56` — `feed` at `:154`, `close` at `:285`, `reset` at `:135`, `.result` at `:108`), with `ResultDict = {encoding, confidence, language}` (`.venv/Lib/site-packages/chardet/resultdict.py:10-13`) and `__version__ = "5.2.0"` (`.venv/Lib/site-packages/chardet/version.py:8-9`).

**The app does not use chardet at all. Plainly: there is not one chardet call, one import, or one reference to it anywhere under `src/`.**

- AST import inventory of all 27 `src/**/*.py` modules: the complete set of top-level imports is stdlib + `flet`, `flet_ads`, `flet_proot`, `flet_terminal`, `httpx`, `proot_distro` — **no `chardet`, no `binaryornot`, no `cookiecutter`, no `charset_normalizer`**. `grep -rn "chardet\|charset\|encoding\|decode" src/` returns exactly two hits: `src/assets/icon.svg:1` (an XML declaration) and `src/screens/views.py:628` (`read_text(encoding="utf-8")`).
- Two repo guards forbid it: `tests/test_proot_surfaces.py:133-148` puts `"chardet"` in the `dev_only` set (`:136`) and asserts no `src/**/*.py` imports any of them (`:146-148`); `tests/test_imports_vs_deps.py:18-32,46-59` requires every `src/` import to be in `project.dependencies` or `tool.flet.<platform>.dependencies` — chardet is in neither.

**chardet is dev-only, reached only through `flet-cli`'s dev group, and it cannot reach the APK.** The chain is closed and mechanical:

```
flet-cli 1.0.4 (dev group)  ──Requires-Dist: chardet<6──▶  chardet 5.2.0
        │  ──Requires-Dist: binaryornot<0.5──▶ binaryornot 0.4.4 ──Requires-Dist: chardet (>=3.0.2)──▶
        └─Requires-Dist: cookiecutter>=2.6.0──▶ cookiecutter 2.7.1 ──Requires-Dist: binaryornot>=0.4.4──▶
```
(`.venv/Lib/site-packages/flet_cli-1.0.4.dist-info/METADATA:18-20`; `binaryornot-0.4.4.dist-info/METADATA:22`; `cookiecutter-2.7.1.dist-info/METADATA:30`; `pyproject.toml:77-84` puts `flet-cli` in the dev group; `uv.lock`/`docs/swarm/dependency-tree/uv-tree-inverted.txt:21-27` agree.)

The **only** source-level importer of chardet in the entire venv is `binaryornot/helpers.py:11` (`import chardet`), used at `:94` (`chardet.detect(bytes_to_check)`) as the second stage of its binary-vs-text probe. `flet_cli` declares chardet but never imports it (`grep -rn "chardet" .venv/Lib/site-packages/flet_cli/ --include=*.py` → 0 hits); `cookiecutter` never imports it (0 hits). The one legitimate exercise is on the **build host**: `flet build` → `flet_cli/commands/build_base.py:1893-1895` (`cookiecutter.main.cookiecutter(...)`) → `cookiecutter/generate.py:15` (`from binaryornot.check import is_binary`) → `:221` (`if is_binary(infile):`) so binary Flutter-template assets are copied instead of being fed to Jinja2. That path is exercised by CI at `app.yml:149,159` and `:203,213` after `uv sync --frozen --group dev` (`:49`). `pygments` has a second, opt-in consumer (`pygments/lexer.py:212-227`, `self.encoding == 'chardet'`) that is off by default and lives in the same dev tree.

**Does the app ever decode external text?** Once, and never with a detector:

| External text | Site | How it is decoded |
|---|---|---|
| Update feed (JSON over https) | `src/services/update_service.py:80` (`response.json()`) | stdlib `json` → `httpx/_models.py:831-832` `jsonlib.loads(self.content)` → **strict UTF-8** |
| License texts (7 shipped `.txt`) | `src/screens/views.py:626-628` | `path.read_text(encoding="utf-8")` → **strict UTF-8** |
| Container output (PTY) | `src/services/session_service.py:122-126` → `src/services/session_manager.py:38-39` → `src/screens/terminal_view.py:98` | **never decoded in Python** — raw bytes to the Dart terminal via `flet_terminal/terminal.py:129-133` (`send_bytes` → DataChannel) |

| Container tar / OCI layers / `.so` payloads | `src/core/proot_probe.py:97`, `src/components/brand_hero.py:28` | `read_bytes()` — bytes copied, never decoded |

## Findings

### F1 · P2 · chardet is entirely unused in `src/`, and the study's on-device plan would fail two repo guards

- **Where:** `docs/dependency-studies/chardet.md:36-42` ("Our-project utilization (M3 import/export) … `chardet.detect` (or `detect_all` when confidence is low) picks the decode codec for guest files with unknown locale encodings … Rule: trust confidence > 0.8, else fall back to UTF-8 with `errors="replace"`"); `tests/test_proot_surfaces.py:133-148` (`:136` = `"chardet"`); `tests/test_imports_vs_deps.py:18-32,46-59`; `pyproject.toml:9-15`.
- **What:** the study proposes a guest-file import/export viewer that decodes guest files with `chardet.detect`. No such feature exists — the only file the user can move is a whole-container tar, handled opaquely by upstream proot (`src/services/proot_service.py:357-372`), and the only in-container access is the shell terminal (`src/screens/terminal_view.py:105-108`). The proposal is also **forbidden twice over**: `tests/test_proot_surfaces.py:136` names `"chardet"` in the `dev_only` set (so importing it from `src/` fails the suite), and `tests/test_imports_vs_deps.py:57` fails any `src/` import not present in `project.dependencies` (`pyproject.toml:9-15`) or `tool.flet.<platform>.dependencies` (`pyproject.toml:52`).
- **Evidence:** AST inventory over all 27 `src/**/*.py` modules returns no `chardet` import; `grep -rn "chardet" src/` → 0 hits (exit 1); `grep -rln "import chardet" .venv/Lib/site-packages/ --include=*.py` → only `binaryornot/helpers.py` (plus chardet's own modules and the `requests` compat shim, which resolves it dynamically).
- **Fix / opportunity:** correct `docs/dependency-studies/chardet.md:36-42` to state the plain truth — **build-host only, transitively via flet-cli → binaryornot/cookiecutter; not an app dependency, and the app has no import/export feature to justify one.** Do not "wire up" a decode pipeline on this package. If a guest-file viewer is ever specced, the codec choice must come from the stdlib (see F6), never from chardet.
- **Risk if ignored:** the synthesis inherits a phantom integration — an app-side `chardet.detect()` call that fails the `dev_only` guard test at CI time and, if that guard were ever weakened, raises `ImportError` on device because chardet is not in the runtime closure (F2).

### F2 · P3 · chardet is provably dev-only — the shipped APK is LGPL-clean

- **Where:** `pyproject.toml:9-15` (runtime), `:52` (`[tool.flet.android] dependencies = ["flet-proot==5.1.107.98"]`), `:77-84` (dev group); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2566-2570` (`get_project_dependencies(self.get_pyproject("project.dependencies"))`), `:2572-2574` (appends `tool.flet.<platform>.dependencies`), `:2605-2606` (each becomes a `-r` requirement for the serious_python package step), `:2621-2625` (`SERIOUS_PYTHON_SITE_PACKAGES = build_dir/"site-packages"`).
- **What:** the APK's Python payload is a **fresh pip install of the declared runtime set only** — flet-cli hands serious_python exactly `project.dependencies` + `tool.flet.<platform>.dependencies` as `-r` requirements, and dev-group packages are never in that list. chardet is a transitive dependency of a *dev-group* package, so it is not in the closure and cannot be installed into `build/site-packages` by this path.
- **Evidence:** transitive closure computed from the **installed** dist metadata (`importlib.metadata` over `.venv/Lib/site-packages/*.dist-info/METADATA`, `Requires-Dist` without extras):
  ```
  RUNTIME closure (pyproject:9-15 + tool.flet.android.dependencies):
  ['anyio','certifi','exceptiongroup','flet','flet-ads','flet-proot','flet-terminal','h11',
   'httpcore','httpx','idna','msgpack','oauthlib','proot-distro','repath','six','typing-extensions']
  chardet in runtime closure?            False
  binaryornot in runtime closure?        False
  cookiecutter in runtime closure?       False
  charset-normalizer in runtime closure? False
  requests in runtime closure?           False
  DEV closure contains chardet?          True
  ```
  Independently: `flet-1.0.4.dist-info/METADATA:14-18` (runtime `Requires-Dist`) names only oauthlib, httpx, repath, msgpack, typing-extensions — **no chardet**; `httpx-0.28.1.dist-info/METADATA:27-30` names anyio, certifi, httpcore, idna — **no detector**; `proot_distro-5.10.0.dist-info/METADATA` has **no** `Requires-Dist` at all.
- **Fix / opportunity:** none required. Record the closure as the standing answer to "does LGPL reach the APK?" — it does not.
- **Risk if ignored:** none for this package; the finding exists so the synthesis does not re-open the question.

### F3 · P3 · The LGPL shipping risk is not zero — no CI gate would notice a regression, and neither gate looks at the site-packages payload

- **Where:** `.github/workflows/app.yml:163-172` (APK prune check), `:275-287` (AAB prune check); `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2621-2625` (site-packages location); `docs/compliance/licensing.md` (HEAD) §0 item 3 and §1d (the dev-only table that already lists chardet as LGPL and build-host-only).
- **What:** today chardet cannot ship (F2), and the compliance reference already says so — §1d's chardet row reads *"Build-host only: `flet-cli` runs on the CI host (`flet build apk`), never bundled into the APK"*, with the guard *"never add cookiecutter-tree packages to runtime deps"*. But that guard is **source-level only**: if a future change added `chardet` to `project.dependencies` (a plausible move for a "detect this file's encoding" feature), **nothing in the build would object**. The APK gate greps for `pytest/|ruff/|uvicorn/|starlette/|fastapi/|docs/` only (`app.yml:168`) — `chardet/` is not in the list, and per the flet-cli audit F2 the APK gate cannot descend into `assets/app/app.zip` at all, so it passes unconditionally. The AAB gate *does* unzip the inner `base/assets/app/app.zip` (`app.yml:280-282`) but greps the same six patterns and, more importantly, inspects the **app payload**, never the Python **site-packages** payload where chardet would live.
- **Evidence:** `app.yml:168` and `app.yml:282` — the literal pattern lists. `docs/compliance/licensing.md` (HEAD) §1d: `chardet` 5.2.0 row, *"LGPL … Build-host only … Guard: never add cookiecutter-tree packages to runtime deps"*. The two working guards that would actually fire are `tests/test_proot_surfaces.py:133-148` and `tests/test_imports_vs_deps.py:46-59` — both are **import** guards, and neither would catch a `pyproject.toml` edit that adds a runtime dependency no `src/` file imports.
- **Fix / opportunity:** (a) add `chardet/|binaryornot/|cookiecutter/|charset_normalizer/|requests/` to both CI prune greps (`app.yml:168`, `app.yml:282`) so the LGPL tree is explicitly asserted absent; (b) add a CI step that lists the **site-packages** payload's `*.dist-info` and compares it against `uv.lock`'s runtime closure — this is the check that actually proves "no LGPL in the APK", and it is the same check the flet-cli audit F1 already recommends for version pinning. No app code changes.
- **Risk if ignored:** a one-line `pyproject.toml` edit could put LGPL code in a Play-distributed APK with no build-time signal — a silent, ship-time compliance defect in a project whose A8 posture is explicitly GPL-hygienic (`docs/decisions.md:56`).

### F4 · P3 · The app's only text decode is strict UTF-8 with no fallback — hardening, and no detector is the right answer

- **Where:** `src/screens/views.py:628` (`body = path.read_text(encoding="utf-8")[:6000] if path.is_file() else "(text missing)"`); `src/screens/views.py:43-51` (`_TEXT_FILES` — 7 fixed `.txt` names); `src/screens/views.py:20` (`_LICENSES_DIR`).
- **What:** `read_text(encoding="utf-8")` has no `errors=` fallback, so a non-UTF-8 license file raises `UnicodeDecodeError` out of `licenses_view()`. Because `licenses_view()` is evaluated as an argument to `page.show_dialog(...)` (`src/screens/views.py:422`), the dialog would never open. The `is_file()` guard covers the missing-file case and all 7 shipped texts are valid UTF-8, so this is **hardening, not a live defect**.
- **Evidence:** `grep -rn "decode(" src/ --include=*.py` → **0 hits**; the only decode-equivalent in `src/` is `views.py:628`. The other file reads are byte-safe: `src/components/brand_hero.py:28` (`candidate.read_bytes()` → `ft.Image(src=bytes)`), `src/core/proot_probe.py:97` (`dst.write_bytes(src.read_bytes())`).
- **Fix / opportunity:** add `errors="replace"` to that one call. **Do not** introduce a detector: the inputs are 7 known-UTF-8 files we ship, and the charset-normalizer study's policy is explicit — *"prefer explicit UTF-8 (`path.read_text(encoding="utf-8")`) for OUR files … Guessing is for OTHER people's bytes"* and *"Don't add direct uses"* (`docs/dependency-studies/charset-normalizer.md` §8).
- **Risk if ignored:** low — a re-encoded or corrupted license file blanks the Licenses dialog instead of showing text. (The license texts are separately reported as unreachable on device by `docs/swarm/dependency-utilization/flet-cli.md` F4 — that is a packaging issue, not an encoding one.)

### F5 · P3 · The app *does* decode external text — the update feed — via strict stdlib JSON, and a non-UTF-8 body fails silently

- **Where:** `src/services/update_service.py:80` (`data = response.json()`), `:100-102` (`except Exception as exc: logger.debug(...); return None`); `.venv/Lib/site-packages/httpx/_models.py:831-832` (`def json(...): return jsonlib.loads(self.content, **kwargs)`), `:652-672` (`encoding` property), `:642-650` (`text` property), `.venv/Lib/site-packages/httpx/_decoders.py:306-317` (`TextDecoder` → `codecs.getincrementaldecoder(encoding)(errors="replace")`).
- **What:** this is the app's only genuine "external text" decode. httpx ships **no** detector (`grep -rn "charset_normalizer\|chardet" .venv/Lib/site-packages/httpx/` → 0 hits): `Response.text` decodes with `self.encoding or "utf-8"` where `default_encoding` is the literal `"utf-8"` (`_models.py:529,648`) and the decoder is **lenient** (`errors="replace"`, `_decoders.py:311`). But `Response.json()` bypasses `.text` entirely and hands **raw bytes** to `json.loads` (`_models.py:832`), and `json.loads` on bytes decodes **strict UTF-8**. A non-UTF-8 byte in the feed therefore raises `UnicodeDecodeError`, which the broad `except Exception` at `update_service.py:100` swallows → `check_for_update` returns `None` → the app reports "no update" and logs only at `debug`. The user sees a silent miss, not an error.
- **Evidence:** runnable, installed interpreter:
  ```
  json.loads on non-UTF8 bytes -> UnicodeDecodeError 'utf-8' codec can't decode byte 0xe9 in position 10: invalid continuation byte
  json.loads on UTF-8 bytes   -> {'a': 'café'}
  ```
  Source: `httpx/_models.py:831-832` (`jsonlib.loads(self.content)`), `:529` (`default_encoding: str | Callable = "utf-8"`), `:648` (`TextDecoder(encoding=self.encoding or "utf-8")`).
- **Fix / opportunity:** this is the one place where a "real decode need" exists today, and the correct tool is the **stdlib**: parse `response.text` (lenient, `errors="replace"` via `httpx/_decoders.py:311`) instead of `response.json()`, or set `response.encoding` before parsing. Do **not** reach for chardet: it is not in the runtime closure (F2), it is LGPL (F3), and the feed is our own GitHub-hosted JSON, which is UTF-8 by construction. Tighten the `except Exception` at `:100-102` so a decode failure is distinguishable from "offline" in the log.
- **Risk if ignored:** a malformed or non-UTF-8 release feed silently disables the update banner — the user is never told the check failed. Low severity, but it is a real "silent failure" surface in a security-adjacent path (a stale app never nags the user to update).

### F6 · P3 · The correct tool for a real decode need is the **stdlib** — charset-normalizer (the MIT alternative) is also dev-only

- **Where:** `docs/dependency-studies/charset-normalizer.md` §6 ("host/CI only, never in the APK") and §8 ("Don't add direct uses … prefer explicit UTF-8 … Guessing is for OTHER people's bytes"); `pyproject.toml:9-15`; `charset_normalizer-3.5.2.dist-info/METADATA:7` (`License: MIT`); `requests-2.34.2.dist-info/METADATA` (`Requires-Dist: charset_normalizer<4,>=2`).
- **What:** the obvious "swap LGPL for permissive MIT" move does not help the app, because **charset-normalizer is not in the runtime closure either** (F2 evidence: `charset-normalizer in runtime closure? False`). It reaches the venv only as `requests → cookiecutter → flet-cli (dev)`. So the app has **no** third-party detector available on device today, and none should be added.
- **Evidence:** runtime-closure computation above; `charset-normalizer` is reachable only through `requests-2.34.2.dist-info/METADATA` → `cookiecutter-2.7.1.dist-info/METADATA` → `flet_cli-1.0.4.dist-info/METADATA` (dev group). The charset-normalizer study itself already says it "never ships in the APK" (§6) and is a "transitive fallback" (§8).
- **Fix / opportunity:** for any future on-device decode need, use the **stdlib** in this order: (1) an explicit encoding when the producer is known — `bytes.decode("utf-8", errors="replace")`; (2) the declared HTTP charset — set `response.encoding` before `.text` (per the study's §8 "declare everything" rule); (3) only if the bytes are genuinely third-party and unknown, `charset_normalizer.from_bytes(b, steps=5).best()` — but note that requires an owner sign-off under D-003 (`docs/decisions.md:12-13`, "the dependency set is frozen") plus a `pyproject.toml` change, and it is a **host-tooling** recommendation in the study, not an on-device one. **Never vendor chardet** (`docs/dependency-studies/chardet.md:5`, `docs/reference/dep-cookiecutter-stack.md:16`).
- **Risk if ignored:** a future feature author reaching for `chardet` (LGPL, absent at runtime) or for `charset-normalizer` (MIT, also absent at runtime) writes code that passes review and crashes on device — or, worse, someone adds the dependency to `pyproject.toml` to make it "just work", quietly putting LGPL in the APK (F3).

## Missed capabilities (dependency audits only)

**None — and that is the finding, not an omission.** The chardet API surface (`detect`, `detect_all`, `UniversalDetector` — all spot-checked above against the installed source) is real, working, and correctly documented in the study, but it has **no consumer in this app**, and the app has no feature that would give it one:

- No file browser, no log viewer, no editor, no text-preview dialog, no download manager in `src/` — the app never opens a user-supplied file for display. `ft.FilePicker` is used exactly twice (`src/app_controller.py:342-369`): `save_file` at `:346` to choose where proot writes a container tar, and `pick_files` at `:360` to choose a container tar to restore. Both paths are opaque to the app.
- Guest content reaches the screen only as PTY bytes (`src/services/session_service.py:122-126` → `src/services/session_manager.py:38-39` → `src/screens/terminal_view.py:98`), and those bytes are never decoded in Python — `flet_terminal/terminal.py:129-133` ships them raw to the Dart terminal emulator, where a UTF-8 assumption is already baked in on the Dart side.
- Every other file path is byte-opaque by construction: container tar / OCI layers are handled by upstream proot (`src/services/proot_service.py:357-372`), `.so` payloads are copied byte-for-byte (`src/core/proot_probe.py:97`), the brand icon is read as bytes (`src/components/brand_hero.py:28`).
- The one text decode that exists (license texts, `src/screens/views.py:628`) reads 7 files we author and ship — "OUR files", which the charset-normalizer study explicitly excludes from the guessing case.

Cost of the status quo: zero. Value of adding detection: zero, and it would import a package the app is forbidden to import (`tests/test_proot_surfaces.py:136`) that is absent from the shipped dependency set (F2). The one place chardet earns its keep is the build host, and it is already earning it: `flet build` → `cookiecutter` → `is_binary(infile)` (`cookiecutter/generate.py:221`) → `chardet.detect` (`binaryornot/helpers.py:94`) keeps binary Flutter-template assets out of the Jinja2 renderer. That path needs no change from us.

- The container-output path performs **no Python-side decode**: `src/screens/terminal_view.py:98` replays raw bytes through `flet_terminal/terminal.py:129-133` (`send_bytes` → DataChannel). The only flet-terminal decode is on the *input* side (`terminal.py:178-180`, UTF-8 `errors="ignore"`).
- The `dev_only` guard test exists, names `chardet` explicitly, and is green in this tree — the repo already forbids exactly the integration the study proposes.
- `requests` resolves **chardet first** in this venv (`requests/compat.py:37-49`; live probe → `chardet`), matching the charset-normalizer study's note — but `requests` is itself dev-only, so this changes nothing on device.
- `docs/compliance/licensing.md` (HEAD) §0 item 3 and §1d already state the correct position: chardet is LGPL, build-host only, never in the APK. This audit confirms it independently.
