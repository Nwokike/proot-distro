# h11 0.16.0 utilization — audit

**Verdict:** IMPROVE
**Confidence:** high
**Scope:** `docs/dependency-studies/h11.md`; `src/services/update_service.py`; `src/app_controller.py`; `src/components/update_dialog.py`; `src/screens/views.py`; `src/services/proot_service.py`; `src/core/constants.py`; `pyproject.toml`; `uv.lock`; `.venv/Lib/site-packages/h11/`; `.venv/Lib/site-packages/httpcore/_async/http11.py`; `.venv/Lib/site-packages/httpcore/_sync/http11.py`; `.venv/Lib/site-packages/httpx/_config.py`; `.venv/Lib/site-packages/proot_distro/helpers/download.py`; `.venv/Lib/site-packages/proot_distro/helpers/docker/{pull,layers,transport,search}.py`; `.venv/Lib/site-packages/proot_distro/commands/install.py` · **Date:** 2026-10-20

**One-line verdict:** h11 is **dormant by design and correctly so** — the app never imports it, and no missed capability in it is worth direct use. The only actionable item is one level up: the app's real download path (OCI/Docker Hub) bypasses the whole httpx→httpcore→**h11** stack, so h11's guarantees never reach the user's actual bytes.

## What it does / how the app uses it

h11 is the HTTP/1.1 wire-protocol state machine underneath `httpcore` (`.venv/Lib/site-packages/httpcore/_async/http11.py:10` `import h11`). It owns framing, keep-alive cycling and protocol-error detection; it owns no sockets, no TLS, no pooling. The dependency chain in the lock is `httpx 0.28.1 → httpcore 1.0.9 → h11 0.16.0` (`uv.lock:291` lists h11 under httpcore's dependencies; `httpcore` requires `h11>=0.16` per the installed `httpcore-1.0.9.dist-info/METADATA`).

**The app never imports h11.** `grep -rn "h11" src/ tests/` returns exactly one hit — the string `"h11"` at `src/screens/views.py:35`, inside the `_PY_DISTS` third-party license tuple rendered by `_py_entries()` (`src/screens/views.py:600-606`). It is a disclosure name, not a usage. There is no `import h11`, no `h11.` attribute access, and no monkeypatching of it anywhere in `src/` or `tests/`.

**The single live h11 path** is the app's only network call: `check_for_update()` → `httpx.AsyncClient` (`src/services/update_service.py:73-76`) → `httpcore._async.http11` → `h11`. It is invoked from the startup background task (`src/app_controller.py:88`, `:309-317`) and from the "Check for Updates" button (`src/components/update_dialog.py:149-161`). Proven live against a local server with an instrumented `h11.Connection`:

```
h11.Connection instantiations: 1  [((), {'our_role': CLIENT, 'max_incomplete_event_size': 102400})]
h11 counters for the app's own check_for_update(): {'init': 1, 'start_next_cycle': 1, 'send': 3, 'next_event': 5}
```

Flet's own httpx use (`flet/auth/authorization_service.py:119,207,248`, `flet/auth/providers/github_oauth_provider.py:43,76`) is OAuth-only and dormant — the app ships no login flow (`pyproject.toml:60-63`). So **every** h11 event in this app comes from one small JSON `GET`.

**HTTP/2 is not in play**, so h11 is the only framing engine on the stack: httpx defaults to `http2=False` (`.venv/Lib/site-packages/httpx/_transports/default.py:142,286`), httpcore then always selects `AsyncHTTP11Connection` (`.venv/Lib/site-packages/httpcore/_async/connection.py:94`), and `h2` is not installed (`importlib.util.find_spec("h2") is None`).

## Findings

### F1 · P2 · The OCI/registry download path — the app's real download — bypasses httpx/httpcore/h11 entirely

- **Where:** `src/services/proot_service.py:212-223` (`install()` → `proot_distro.commands.install.command_install`) → `.venv/Lib/site-packages/proot_distro/commands/install.py:138` → `:320` (`pull_image(...)`) → `.venv/Lib/site-packages/proot_distro/helpers/docker/pull.py:435` → `.venv/Lib/site-packages/proot_distro/helpers/docker/layers.py:82` → `.venv/Lib/site-packages/proot_distro/helpers/docker/transport.py:162-190` → `.venv/Lib/site-packages/proot_distro/helpers/download.py:373-407`. Search hits the same stack: `src/services/proot_service.py:263-269` → `.venv/Lib/site-packages/proot_distro/helpers/docker/search.py:153`.
- **What:** upstream fetches manifests, blobs and auth tokens with **`urllib.request`/`http.client`**, not httpx. `download.py:38-44` imports `http.client`, `urllib.error`, `urllib.parse`, `urllib.request`; `http_opener()` builds a plain `urllib.request.OpenerDirector` (`download.py:396-407`); every fetch goes through `opener(insecure).open(req)` (`pull.py:112`, `layers.py:82`, `search.py:153`, `transport.py:344,538`). **h11 is not in that path at all.** Three consequences, all evidence-backed:
  1. **No h11 framing validation.** Upstream hand-rolls the equivalent instead: `require_complete_body(received, declared, ...)` (`download.py:143`, called at `pull.py:130`, `layers.py:98-101`) checks a truncated body after the fact, whereas h11 would have rejected the framing during `next_event()` (`h11/_connection.py:438`).
  2. **No connection reuse.** urllib does not pool: 3 `opener.open()` calls against one local server produced **3 TCP connections**, versus **1** for 3 requests on a single `httpx.AsyncClient` (both measured in this audit). So a multi-layer pull pays a fresh TLS handshake per manifest/config/blob, and h11's `DONE → start_next_cycle() → IDLE` cycle (`h11/_state.py:356`, `h11/_connection.py:235`, driven at `httpcore/_async/http11.py:245`) is never exercised for the traffic that matters.
  3. **A different TLS trust anchor.** httpx anchors to certifi (`.venv/Lib/site-packages/httpx/_config.py:31,40` → `ssl.create_default_context(cafile=certifi.where())`); upstream's non-insecure opener passes `context=None` to `HTTPSHandler` (`download.py:401`), which resolves to the **platform** trust store. Verified: `urllib.request.HTTPSHandler(context=None)._context` → `verify_mode=2 (CERT_REQUIRED)`, `check_hostname=True`, `load_default_certs()` populated, certifi **not** used.
- **Evidence:** file/line refs above; connection-count experiment: `3 urllib opener.open() calls -> TCP connections: 3` vs `3 httpx calls on ONE AsyncClient -> TCP connections: 1`.
- **Fix / opportunity:** **not an app-code change.** Upstream owns the transport and exposes no injection seam: `transport.opener()` builds the urllib opener itself (`transport.py:162-190`) and the only environment hook is `PD_DOCKER_AUTH` for credentials (`transport.py:355,369,411`), not for the transport. Under BRIEF rule 4 (one upstream importer per service, no monkeypatches, no vendoring, no forks) the app cannot swap it. Route this to the upstream `proot-distro` package as a request ("optionally use httpx/httpcore for registry traffic"), or accept the divergence and record it as a known boundary. **Do not** add a second HTTP stack in `src/` to work around it — that would create exactly the hand-rolled framing the study warns about.
- **Risk if ignored:** the framing guarantees, keep-alive reuse and error attribution that the shipped httpx stack buys never reach the user's actual rootfs download; on Android the pull path trusts the platform CA store rather than the bundled certifi bundle (on-device impact UNVERIFIED — see Unverified).

### F2 · P3 · h11's Local-vs-Remote error attribution is discarded by the app's blanket exception handler

- **Where:** `.venv/Lib/site-packages/h11/_util.py:12,59,80` (`ProtocolError` / `LocalProtocolError` / `RemoteProtocolError`) → translated at `.venv/Lib/site-packages/httpcore/_async/http11.py:144` (`h11.LocalProtocolError → httpcore.LocalProtocolError`) and `:213` (`h11.RemoteProtocolError → httpcore.RemoteProtocolError`) → re-exported by httpx as `httpx.LocalProtocolError` / `httpx.RemoteProtocolError` → collapsed at `src/services/update_service.py:100-102` (`except Exception as exc: logger.debug(...); return None`).
- **What:** h11's headline benefit is *exact error attribution* — "we" broke the protocol vs "the peer" broke it. The app never reads that distinction: every protocol error, timeout, DNS failure and JSON error returns the same `None`, which the dialog renders as **"You're up to date"** (`src/components/update_dialog.py:158-161`). The precise signal is paid for and then thrown away.
- **Evidence:** exception hierarchy and translation sites above; `src/services/update_service.py:100-102` and `src/components/update_dialog.py:158-161` — the `else` branch shows the "up to date" snackbar for *any* `None`, including a failed request.
- **Fix / opportunity:** no h11 work. If the httpx audit's F2 (tri-state result) is implemented, branch on the exception type: `httpx.RemoteProtocolError` = the mirror/host sent garbage (retry, or try another mirror); `httpx.LocalProtocolError` = our own request is malformed (a bug in the app, do not retry); `httpx.TimeoutException`/`NetworkError` = transport. That is precisely the "Local vs Remote" signal the dependency exists to produce, and it needs no new dependency.
- **Risk if ignored:** no new user-visible break today (the httpx audit already owns the "failure reported as up to date" defect). The cost is that a capability the app already ships and pays for is not used, so protocol bugs stay indistinguishable from "the network was busy".

### F3 · P3 · Two prior-study details are wrong for this stack — correct them before they are re-used

- **Where:** `docs/dependency-studies/h11.md:118` and `:132` (the study itself); `.venv/Lib/site-packages/httpcore/_async/http11.py:45,62`; `.venv/Lib/site-packages/h11/_version.py:16`.
- **What:**
  1. **Event-size cap.** The study says h11's cap is 16 KB and that "the knob lives in httpcore's constructor path" (`docs/dependency-studies/h11.md:118`), and lists `_version.py:23` for the version constant (`:132`). In fact httpcore **always overrides** h11's default: `MAX_INCOMPLETE_EVENT_SIZE = 100 * 1024` (`httpcore/_async/http11.py:45`) is passed as `max_incomplete_event_size=self.MAX_INCOMPLETE_EVENT_SIZE` (`:62`) — identical in the sync backend (`httpcore/_sync/http11.py:45,62`). The installed value is therefore **100 KB, not 16 KB** (h11's own default `DEFAULT_MAX_INCOMPLETE_EVENT_SIZE` is 16384 at `h11/_connection.py:170`). Confirmed by the live instrumentation above: `max_incomplete_event_size: 102400`.
  2. **Version line.** `__version__ = "0.16.0"` is at `h11/_version.py:16`, not `:23`.
  Everything else spot-checked against the installed source matched the study exactly: `_connection.py:51,55,84,93,151,167,207,218,225,232,235,255,260,272,320,342,354,364,410,438,504,508,514,517,544,577,602`; `_events.py:32,41,82,129,137,168,176,206,218,247,260,299,316,337,358`; `_util.py:12,59,80`; `_state.py:134-184,249,250,263,267,271,275,299,316,356`; `_readers.py:122,148`; `_writers.py:62,84,101,116`; `_receivebuffer.py:47,147`; `__init__.py:35` (`PRODUCT_ID`).
- **Evidence:** the `102400` value is taken straight from the instrumented `h11.Connection` construction; `h11/_version.py` is a 16-line file whose last line is the assignment.
- **Fix / opportunity:** amend `docs/dependency-studies/h11.md:118,132` (documentation only, outside this agent's write scope). The 16 KB figure is not load-bearing for the app (no app path sends large headers) but it would mislead anyone reasoning about registry responses: a 32 KB manifest header block is *accepted* by our stack and *rejected* by stock h11.
- **Risk if ignored:** a future decision about the OCI path (F1) could be made against the wrong cap.

## Missed capabilities (dependency audits only)

**Direct h11 use: nothing in h11 is worth calling directly.** The study's own verdict (`docs/dependency-studies/h11.md:115`) — "never touch h11 directly in app code" — holds against the installed source: h11 has no sockets, no TLS, no pooling, no timeouts (`h11/_connection.py:151-205` wires only a reader/writer over bytes the caller supplies). Every legitimate direct use it lists is diagnostic:

- **Protocol debugging / fuzzing** (`h11/_connection.py:364` `receive_data`, `:438` `next_event`, `:207-232` state properties) · Integration: a `tests/`-only script that replays captured bytes and asserts `friendly_job_error` (`src/services/proot_service.py:415-423`) handles `RemoteProtocolError` · **Value: low.** The OCI path never produces h11 exceptions (F1) — upstream raises `urllib.error.URLError`/`OSError`/`http.client.HTTPException` (`proot_distro/helpers/download.py:85`) — so such a test would exercise a code path the app does not have. Cost: a test-only dependency on an internal of a transitive package, for a scenario that cannot occur. **Not worth it.**
- **`max_incomplete_event_size` tuning** (`h11/_connection.py:170`) · **Value: none.** httpcore hard-sets 100 KB (F3) and the app cannot pass a different value without replacing the transport. **Not worth it.**
- **`send_with_data_passthrough`** (`h11/_connection.py:544`) · server-side `sendfile` optimization; httpcore never calls it (grep: absent from `httpcore/_async/http11.py` and `_sync/http11.py`). **N/A.**

**What the app is not using from the layer that h11 provides, indirectly:**

- **Connection reuse / keep-alive** · API: `httpx.AsyncClient` is shareable between tasks (`.venv/Lib/site-packages/httpx/_client.py:1311-1313`), `httpcore` pool + `h11.Connection.start_next_cycle()` (`httpcore/_async/http11.py:245`) · Integration: one client owned by the app instead of one per call (`src/services/update_service.py:75`) · Value: 3 requests on one client = **1** TCP connection (measured) instead of 3; removes a TLS handshake per check. **Already reported as F5 in the httpx audit — do not re-open.** h11 itself needs no change.
- **h11's Local/Remote error split** · API: `h11.LocalProtocolError` / `h11.RemoteProtocolError` (`h11/_util.py:59,80`) → `httpx.LocalProtocolError` / `httpx.RemoteProtocolError` · Integration: branch in `check_for_update`'s error handling (`src/services/update_service.py:100-102`) · Value: retry the mirror vs fix our request. Cost: 3 lines. **F2 above.**

## Verified-good list

- **h11 is correctly dormant.** No `import h11` in `src/` or `tests/`; the single `"h11"` token in app code is the license-list entry `src/screens/views.py:35`. Nothing to remove, nothing to add. This is the desired end state, not an oversight.
- **The transitive chain is intact and satisfied.** `uv.lock:277-291` pins h11 0.16.0 and lists it under httpcore 1.0.9's dependencies; the installed httpcore requires `h11>=0.16` — 0.16.0 is the exact minimum. The installed package is 0.16.0 (`h11/_version.py:16`; `h11.__version__` → `0.16.0`).
- **h11 ships inside the APK.** `flet build` resolves the project dependencies only (`tests/test_imports_vs_deps.py:1-5`: "`flet build` resolves ONLY the project dependencies"), i.e. `httpx` → `httpcore` → `h11`. h11 is pure-Python — 11 `.py` files plus `py.typed` in `.venv/Lib/site-packages/h11/`, with **no** `Requires-Dist` at all (`h11-0.16.0.dist-info/METADATA` has only `Requires-Python: >=3.8`) — so it adds no native packaging risk.
- **The license screen discloses h11 correctly.** `importlib.metadata.metadata("h11")` → `Version: 0.16.0`, `License-Expression: None`, `License: 'MIT'`; `_dist_license()` (`src/screens/views.py:565-572`) falls back to the `License` field, so the screen renders "h11 0.16.0 (MIT)". The MIT text ships in `src/LICENSES/MIT.txt` (`_TEXT_FILES`, `src/screens/views.py:43-51`); the loader degrades to "(text missing)" if the file is absent (`src/screens/views.py:628`), so a missing text cannot crash the screen.
- **The app's only HTTP call is well-formed for h11.** `httpx` sets `Host:`, `Content-Length` and the target itself, so h11's `Request` validation (`h11/_events.py:112-122`: missing/duplicate `Host` → `LocalProtocolError`, illegal method/target characters → `LocalProtocolError`) can never fire from app code. The update check is a plain `GET` with no body — `h11.Request` is built at `httpcore/_async/http11.py:145` and `h11.EndOfMessage()` at `:161`.
- **h11's state machine completes its cycle correctly on the live path.** `start_next_cycle()` is called on every response (`httpcore/_async/http11.py:239-245`) and the instrumentation shows it firing once per request; the `DONE → IDLE` reset is not left dangling. A `LocalProtocolError` would surface as `httpx.LocalProtocolError` and be contained by the blanket handler.
- **The installed h11 API matches the study's anti-hallucination notes.** `Connection` has no `receive` and no `receive_failed` (`getattr(h11.Connection, "receive", None)` → `None`; `"receive_failed"` → `None`); the receive path is `receive_data` + `next_event`. `h11.Connection.__init__` signature is `(self, our_role, max_incomplete_event_size: int = 16384)`; `our_role` outside `CLIENT`/`SERVER` raises `ValueError` (`h11/_connection.py:174-175`).
- **No HTTP/2 shadow path.** `h2` is not installed and httpx's `http2` defaults to `False` (`httpx/_transports/default.py:142,286`); `httpcore` therefore always instantiates `AsyncHTTP11Connection` (`httpcore/_async/connection.py:94`) — h11 frames 100% of the httpx traffic.
- **The one host-side HTTP client is out of app scope.** `build_flet_proot_wheel.py:18-19,197-198` uses `urllib.request.urlopen` — a CI-time wheel builder, not shipped in the APK (`pyproject.toml:113-115` documents it as a host-side CLI).

## Unverified

- **On-device Android behavior.** No device run was performed. Specifically unverified: whether the Android platform CA store (used by the upstream urllib path, F1) contains the roots that Docker Hub / registry-1.docker.io present, and whether upstream's urllib path behaves differently on Android's BoringSSL. The trust-anchor *difference* is proven at the source level; its runtime consequence is not.
- **Upstream `proot_distro` runtime behavior.** The installed package cannot be imported on this desktop Windows venv (`proot_distro/dirfd.py:73` uses `os.O_DIRECTORY`, absent on Windows), so all upstream claims in F1 are source-level citations, not executed traces. The urllib-vs-httpx connection-count contrast was measured with the same stdlib/httpx calls upstream issues, not with upstream's own code.
- **Live feed behavior.** No request to `raw.githubusercontent.com/Nwokike/proot-distro/main/version.json` was made; the live instrumentation used a local `http.server` on 127.0.0.1 and called the app's own `check_for_update()` with that URL. The h11 call chain, the counter values and the `max_incomplete_event_size=102400` value are all from the real installed packages.
- **The `LICENSES/` working-tree state.** `git status` shows `LICENSES/*.txt` and `src/LICENSES/*.txt` deleted in the working tree (pre-existing, not caused by this audit). The screen degrades gracefully (`src/screens/views.py:628`), but whether the MIT text for h11 is present in a release build was not verified.
- **`docs/roadmap.md` and other deleted docs.** `git status` also shows `docs/roadmap.md` deleted, so the study's roadmap cross-references (e.g. "M3 downloads") could not be checked against the current plan. No roadmap claim is made in this report.
