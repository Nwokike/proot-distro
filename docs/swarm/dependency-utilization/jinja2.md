## What it does / how the app uses it

**The app does not use jinja2 at all, and it should not start.** jinja2 3.1.6 is installed in `.venv` but is reachable only through the **dev group**:

- `pyproject.toml:9-15` — the runtime dependency set is `flet`, `flet-ads`, `httpx`, `flet-terminal`, `proot-distro`. No jinja2.
- `pyproject.toml:77-84` — the dev group is `flet-cli`, `flet-desktop`, `pytest`, `pytest-timeout`, `ruff`. jinja2 is not listed anywhere in `pyproject.toml`.
- `uv.lock:226` — `flet-cli` → `cookiecutter`; `uv.lock:181` — `cookiecutter` → `jinja2`; `uv.lock:332-337` — `jinja2` 3.1.6 → `markupsafe` 3.0.4. Confirmed by the resolved tree: `docs/swarm/dependency-tree/uv-tree.txt:23-35` puts jinja2 at depth 4 under `flet-cli (group: dev)` → `cookiecutter` → `jinja2`; the runtime closure (`uv-tree.txt:3-22`) contains no jinja2 edge.
- `.venv/Lib/site-packages/flet_cli/commands/build_base.py:2566-2577` — the packager computes the on-device dependency set from `project.dependencies` + `tool.flet.<platform>.dependencies` only. The dev group is never consulted, so the dev tree **structurally cannot reach the device**.
- `tests/test_proot_surfaces.py:133-148` — the repo already asserts this: any `src/` file importing `jinja2` (among `chardet`, `cookiecutter`, `pytest`, `ruff`, `flet_cli`, `flet_desktop`, `binaryornot`, `jinja2`, `requests`) fails the suite. True today: `grep -rn "jinja" src/` → **0 hits**.
- `docs/reference/dep-cookiecutter-stack.md:3` already states the truth ("Build-host only; none ship to Android"), and `docs/roadmap.md:136` lists jinja2 in the "dev stack … dev-only" line.

Where jinja2 actually runs: cookiecutter renders the flet build template. `.venv/Lib/site-packages/cookiecutter/environment.py:7` (`from jinja2 import Environment, StrictUndefined`), `:30-37` (the five built-in extensions), `:59-71` (`StrictEnvironment` → `undefined=StrictUndefined`, fail-closed); `.venv/Lib/site-packages/cookiecutter/generate.py:16` (`from jinja2 import Environment, FileSystemLoader`); `hooks.py:14`, `prompt.py:15`, `find.py:13`, `utils.py:104` (`_jinja2_env_vars`). That is the whole of its exercise: the **build host**, during `flet build apk|aab` (`.github/workflows/app.yml:159,213`).

**No HTML is generated anywhere in this repo.** `grep -rn -i "<html\|<!DOCTYPE\|<div\|<p>\|<br" --include="*.py" src/ build_flet_proot_wheel.py` → 0 hits; `grep -rn -i html .github/workflows/app.yml` → 0 hits. The only markdown the app produces is a 5-bullet changelog string (`src/core/changelog.py:5-13`) rendered by Flet's own `ft.Markdown` control (`src/components/update_dialog.py:67,88`; class at `.venv/Lib/site-packages/flet/controls/core/markdown.py:928`, `MarkdownExtensionSet` at `:28`).

## Findings

### F1 · P1 · The in-app license texts are truncated to 6000 characters — 5 of 7, including both GPL texts (GPL-3.0 shows 17% of its text)
- **Where:** `src/screens/views.py:628` — `body = path.read_text(encoding="utf-8")[:6000] if path.is_file() else "(text missing)"`; the tiles are built at `src/screens/views.py:625-634`; the screen's own promise is at `src/screens/views.py:639-640` ("Full texts below"). House contract: `docs/compliance/licensing.md:691` (checklist A2) requires "§3.3 wording, per-component entries, **scrollable full texts**, source-offer link".
- **What:** every license text is cut at 6000 characters. Measured against the tracked texts (`git show HEAD:LICENSES/<name>.txt`): GPL-3.0 35 147 chars → **6000 shown (17.1%)**; GPL-2.0 19 103 → 6000 (31.4%); MPL-2.0 16 726 → 6000 (35.9%); PSF-2.0 13 936 → 6000 (43.1%); Apache-2.0 11 357 → 6000 (52.8%). Only BSD-3-Clause (1 529) and MIT (1 071) fit. The screen therefore shows a **partial GPL-2.0 and GPL-3.0** while the user-facing text claims "Full texts below". A truncated GPL text is not the license: GPL-2.0 §4(a) requires a copy of the License to accompany the program, and the compliance plan lists the GPL texts as the reason the screen exists (`docs/compliance/licensing.md:690`).
- **Evidence:** char counts computed from the tracked blobs: `GPL-3.0 35147 / shown 6000 / 17.1%`, `GPL-2.0 19103 / 6000 / 31.4%`, `MPL-2.0 16726 / 6000 / 35.9%`, `PSF-2.0 13936 / 6000 / 43.1%`, `Apache-2.0 11357 / 6000 / 52.8%`, `BSD-3-Clause 1529 / 100%`, `MIT 1071 / 100%`. The guard test does not catch it: `tests/test_ui_reactive.py:200-207` only asserts the body is not the placeholder and contains "GNU GENERAL PUBLIC LICENSE" — a string that appears in the first line of the GPL texts, i.e. inside the truncated prefix. `tests/test_ui_reactive.py:194` checks `st_size > 500` on the *file*, not on the rendered string.
- **Fix / opportunity:** drop the `[:6000]` slice and render the whole text; the screen is already a scrollable `ft.Column` (`src/screens/views.py:692`), so a 35 KB `ft.Text` costs nothing but scrollback. If a hard cap is wanted for memory, make it a *page* (load the file on tile expansion) rather than a silent truncation, and never present a truncated text as the license. One-line change at `src/screens/views.py:628`.
- **Risk if ignored:** shipping truncated GPL-2.0/GPL-3.0 in the distributed APK is a license-compliance defect (the exact obligation the screen was built to satisfy), and the app asserts the opposite of what it does.

### F2 · P2 · The licenses screen fails open, and in this working tree the texts really are missing (the guard test fails today)
- **Where:** `src/screens/views.py:628` (the `else "(text missing)"` branch); the files live at `src/LICENSES/*.txt` (`src/screens/views.py:20`); the presence guard is `tests/test_ui_reactive.py:175-197`.
- **What:** a missing license file is rendered as the literal string "(text missing)" inside a legal-text tile — the app looks shipped while carrying no license. The current working tree is exactly that state: `git status --short` shows ` D src/LICENSES/Apache-2.0.txt` … ` D src/LICENSES/PSF-2.0.txt` (7 files), ` D LICENSES/*.txt` (7), plus ` D THIRD-PARTY-SOURCES.md`, ` D check_elf_alignment.py`, ` D generate_third_party_sources.py`, ` D docs/compliance/*.md`, ` D docs/roadmap*.md`, ` D docs/release-runbook.md`, ` D docs/testing-findings.md` — all **uncommitted**; `HEAD` (9027359) still tracks them (`git ls-files` lists every one).
- **Evidence:** `uv run pytest tests/test_ui_reactive.py -k licenses` →
  `FAILED tests/test_ui_reactive.py::test_licenses_view_carries_real_text` — `AssertionError: assert '(text missing)' not in 'This app in…ext missing)'` (7 placeholders). Same deletions would make the CI wheel build abort: `build_flet_proot_wheel.py:330-334` (`_license_text` → `SystemExit("missing vendored license text")`) is reached from `build_flet_proot_wheel.py:396-398`, i.e. from the "Build native payload wheel set" step at `.github/workflows/app.yml:141` and `:195`.
- **Fix / opportunity:** the workspace state itself is a local artifact (a fresh CI checkout is unaffected) — restore with `git checkout -- LICENSES src/LICENSES THIRD-PARTY-SOURCES.md check_elf_alignment.py generate_third_party_sources.py docs/`. In the app, do not render a legal text as a placeholder: raise (or show an explicit "text unavailable — see the repository's LICENSES/ directory" line) instead of silently substituting. The screen is a plain function called from a dialog handler (`src/screens/views.py:609-611`), so an exception is a legitimate failure mode.
- **Risk if ignored:** a release built from a tree where the notices files are absent ships an app whose license screen reads "(text missing)" — the worst possible presentation of a compliance obligation, and CI would not stop the wheel build unless `src/LICENSES` were also missing.

### F3 · P2 · The dependency study claims first-class in-project jinja2 use that does not exist
- **Where:** `docs/dependency-studies/jinja2.md:52-59` — "**Our-project utilization — first-class (M3/M5 distro configs + profiles)** … Jinja2 renders our distro/profile configs: per-distro install manifests, default shell profiles, MOTD/login scripts with `{{ arch }}`, `{{ image_ref }}`, `{% now %}` stamps — always with `StrictUndefined` … Use `DictLoader` for inline templates in tests, `FileSystemLoader` for a `templates/` dir …".
- **What:** none of that exists. The repo has **no template files and no template directory** (`find . -type d -name "template*" -not -path "./.venv/*" -not -path "./.git/*"` → 0 hits), `src/` imports no templating library (`grep -rn "jinja" src/` → 0), and `src/` writes **no** files at all — the only writes in the app are the proot probe's temp files (`src/core/proot_probe.py:45,47,97,129,131`). The claim comes from the M3 **plan** (`docs/roadmap.md:86`, "Certified catalog: YAML manifests (pyyaml …); names via `slugify`; timestamps via arrow/dateutil/tzdata; optional Jinja2 profile templates with `StrictUndefined`"), which shipped as "DONE 2026-10-19" without the catalog, the YAML manifests, `slugify`, `arrow` or any template landing. The same plan line is what `docs/dependency-studies/arrow.md` already had to be corrected for (`docs/swarm/dependency-utilization/arrow.md:9`).
- **Evidence:** `grep -rn "jinja" src/` → exit 1 (0 hits). `grep -rn "jinja\|cookiecutter" .venv/Lib/site-packages/proot_distro/` → 0 files. The installed proot-distro ships no template machinery, and the app consumes it through its documented contract only.
- **Fix / opportunity:** rewrite `docs/dependency-studies/jinja2.md:52-59` to state the truth — jinja2 is a **build-host-only transitive dependency of cookiecutter**; the app ships no templates; if the certified-catalog feature (M3 plan, `docs/roadmap.md:86`) is ever revived, jinja2 would be used **at build/codegen time on the host** (where it already exists) and the rendered artifacts shipped, never as an app runtime dependency. This is a documentation fix only; the swarm's synthesis should not treat the "first-class" claim as a pending integration.
- **Risk if ignored:** every future audit (and the owner) inherits a false picture of the app's dependency surface; a later milestone could "rediscover" jinja2 as an app dependency and break the A4 licensing boundary enforced by `tests/test_proot_surfaces.py:133-148`.

### F4 · P3 · Study error: `select_autoescape` **is** a top-level export in 3.1.6 — the study says the opposite
- **Where:** `docs/dependency-studies/jinja2.md:15-16` — "`select_autoescape` lives in `jinja2.utils`, not top-level — the similarly named top-level import fails; verified."
- **What:** it is defined in `jinja2/utils.py:581` **and** re-exported at top level: `.venv/Lib/site-packages/jinja2/__init__.py:36` — `from .utils import select_autoescape as select_autoescape`. The "similarly named top-level import fails" claim is false.
- **Evidence:** `python -c "from jinja2 import select_autoescape; print(select_autoescape)"` → `<function select_autoescape at 0x…>` (exit 0). `python -c "import jinja2; print(jinja2.select_autoescape)"` → same function.
- **Fix / opportunity:** correct `docs/dependency-studies/jinja2.md:15-16` to "defined in `jinja2/utils.py:581`, re-exported at top level (`jinja2/__init__.py:36`)". Also correct the filter count in the same file (`:22-27` says "**~60** `do_*` built-ins"): introspection of the installed module gives **48** distinct `do_*` filter functions — `jinja2/filters.py` has 52 `def do_` lines, the difference being `async def` variants and overload stubs (`filters.py:1386,1390,1393` for `do_reverse`; `:1507,1517,1527` for `do_map`).
- **Risk if ignored:** a future reader copies the "top-level import fails" note and writes `from jinja2.utils import select_autoescape` or, worse, concludes the helper is unavailable and hand-rolls an escaping helper.

### F5 · P3 · The changelog fallback returns the **oldest** entry while its docstring promises the newest
- **Where:** `src/core/changelog.py:16-18` — `"""The changelog entry for a version, falling back to the newest one."""` / `return CHANGELOG.get(version) or next(iter(CHANGELOG.values()), "")`.
- **What:** `next(iter(...))` returns the **first-inserted** value of the dict literal, i.e. the *oldest* release once the dict has more than one entry. The docstring is wrong about the behaviour it implements. Today it is masked: `CHANGELOG` has a single key (`src/core/changelog.py:6`, "1.0.0"), which `src/core/constants.py:11` (`APP_VERSION = "1.0.0"`) matches, and `tests/test_version_sync.py:30-31` only asserts the current version is present — the unknown-version path is untested.
- **Evidence:** run against the installed tree — `notes_for('1.0.0')` → the 1.0.0 bullets; `notes_for('9.9.9')` → the same; after inserting `CHANGELOG['1.1.0'] = 'NEWEST ENTRY'`, `notes_for('9.9.9')` still returns the **1.0.0** bullets, not the newest one. The fallback is what the "You're up to date" dialog shows (`src/components/update_dialog.py:89` → `notes_for(APP_VERSION)`; dialog at `:83-100`).
- **Fix / opportunity:** either make the code match the docstring (`max(CHANGELOG.items(), key=…)` on a version key) or fix the docstring to say "the oldest entry". One line, `src/core/changelog.py:18`. This is the only changelog-rendering defect found; the rest of that path is sound (Flet's own `ft.Markdown` renders it, `src/components/update_dialog.py:88-93`).
- **Risk if ignored:** after the second release, an app with no changelog entry shows the first release's "What's New" notes under an "You're up to date" dialog — a small, visible inaccuracy in the one screen that tells users what is new.

### F6 · P3 · The host tools duplicate the pin set and the second copy has already drifted — but jinja2 is **not** the fix
- **Where:** `build_flet_proot_wheel.py:34-81` (`_PINNED_SOURCES`, proot **5.1.107.98** at `:40`, sha256 at `:44`) vs `docs/requests/mobile-forge-recipe-flet-proot/build.sh:32-56` (proot **5.1.107.96** at `:35`, sha256 `8199dca0…` at `:37`). The recipe also points at files that do not exist: `build.sh:11` references `tools/build_flet_proot_wheel.py` and `:31` references `tools/flet_proot_sources.json` — the script is at the repo root and there is no `tools/` directory.
- **What:** this is the "duplicated pin set" defect already filed by the cookiecutter audit (`docs/swarm/dependency-utilization/cookiecutter.md` F3, "The payload pin set is duplicated and has already drifted"). It is recorded here **only to close the jinja2 angle**: a Jinja template would not fix it. The duplication is in *data* (versions, sha256s, URLs), and the correct fix is one machine-readable pin file read by both the wheel builder and the recipe — a template engine cannot deduplicate a data table, it can only move the text around. A Jinja-rendered `build.sh` would add a second representation plus a jinja2 dependency to a script that declares itself stdlib-only (`build_flet_proot_wheel.py:5`).
- **Evidence:** `git show HEAD:docs/requests/mobile-forge-recipe-flet-proot/build.sh` lines 11, 31, 35, 37 vs `build_flet_proot_wheel.py:5,40,44`; `ls tools` → "No such file or directory"; `git ls-files | grep tools/` → 0 entries. The recipe is explicitly **not submitted** (`build.sh:4-8`: "Status: prepared, NOT submitted"), so the drift is not currently user-visible.
- **Fix / opportunity:** one shared pin file (JSON) consumed by both — not a cookiecutter template and not a Jinja template. Out of scope for this audit except to prevent a templating proposal.
- **Risk if ignored:** the forge recipe would ship 5.1.107.96 artifacts (or fail on a 404 pool) while the app ships 5.1.107.98 — two different native payloads under one product name.

The repo's own guard `tests/test_proot_surfaces.py:133-148` is green.
- **cookiecutter's use of jinja2 is strict and correct.** `cookiecutter/environment.py:59-71` (`undefined=StrictUndefined` → missing keys fail closed), `:30-37` (five extensions), `generate.py:16` (`Environment, FileSystemLoader`), `hooks.py:14`, `prompt.py:15`, `find.py:13`, `utils.py:104`. Only the fallback direction is wrong (F5).
- **The app writes no template-able files.** `grep -rn "write_text\|write_bytes\|mkdir" src/` returns only the proot probe's temp files (`src/core/proot_probe.py:45,47,77,97,129,131`).
