## What it does / how the app uses it

`src/services/proot_service.py` is the sole `proot_distro` importer (`tests/test_proot_surfaces.py:34-41`; repo-wide grep finds only docstring mentions elsewhere). Its `bootstrap()` installs the `pwd`/`grp` shims and the XDG/Termux env contract **before** every lazy import (`proot_service.py:32-41`). In-process `command_*` calls go through `_run_command` (`proot_service.py:73-102`), which redirects stdout/stderr, optionally tees stderr lines to the UI, and catches `SystemExit` + `Exception`; namespaces are hand-built `SimpleNamespace`s (`:108-169`) whose fields were re-verified against every `args.*`/`getattr(args,…)` read in the upstream handlers.

The app uses install (`install.py:138`), remove/remove-image (`remove.py:108`), reset (`reset.py:44`), rename (`rename.py:50`), backup (`backup.py:451`), restore (`restore.py:441`), copy (`copy.py:63`), kill (`kill.py:88`), Docker Hub search (`docker/search.py:191`), cached-image enumeration (`docker/cache.py:845`), container enumeration/origin (`paths.py:257,380`), `busy_locks` (`locking.py:346`), and the read-only session registry (`session.py:210`). Sessions are spawned as a PTY child from the argv printed by `proot-distro login <c> --get-proot-cmd` (`session_service.py:39-69,95-134`); `command_login` itself is never invoked in-process and `command_run` is never used. The probe stages the native payload and sets `PD_PROOT_BIN`/`PROOT_LOADER`/`LD_LIBRARY_PATH`/`PROOT_TMP_DIR` before any proot call (`proot_probe.py:65-136`), and `AppController.init` runs it first (`app_controller.py:47-51`).

## Findings

### F1 · P1 · `get_proot_cmd` cannot complete: two independent guaranteed exceptions

- **Where:** `src/services/proot_service.py:312-345` (call at `:334`), `src/services/session_service.py:39-41`, `src/app_controller.py:403-410` (`asyncio.to_thread` at `:406`); upstream `.venv/Lib/site-packages/proot_distro/cli.py:258` and `.venv/Lib/site-packages/proot_distro/commands/login/__init__.py:624`.
- **What:** `get_proot_cmd` calls `cli.main()` in-process. (a) `main()`'s first statement installs a SIGQUIT handler: `signal.signal(signal.SIGQUIT, …)` (`cli.py:258`). `SessionManager.open` runs in a `ThreadPoolExecutor` worker (`app_controller.py:406`), and `signal.signal` is main-thread-only → `ValueError: signal only works in main thread of the main interpreter`. (b) Even on the main thread it would still fail: `get_proot_cmd` replaces `sys.stdout` with `io.StringIO()` (`proot_service.py:328,331`), but `--get-proot-cmd` prints through `sys.stdout.buffer` (`login/__init__.py:624-625`); `StringIO` has no `.buffer` → `AttributeError`. (`_print_command` is at `login/__init__.py:603`.)
- **Evidence:** runnable proof of the thread restriction with the installed interpreter:
  `python -c "import asyncio,signal; f=lambda: signal.signal(signal.SIGINT, lambda *a: None); print(asyncio.run(asyncio.to_thread(f)))"` → `ValueError: signal only works in main thread of the main interpreter` (main-thread call returns `None`). Proof of (b): `python -c "import io; io.StringIO().buffer"` → `AttributeError: '_io.StringIO' object has no attribute 'buffer'`. The code path is unconditional: `login/__init__.py:531-552` enters the `show_cmd` branch, warns, prints, and `sys.exit(0)` — the `warn`/print happen before any exec.
- **Fix / opportunity:** stop calling `cli.main()`. Build the namespace with the public parser and call the public handler directly, which touches neither `sys.argv` nor signals: `parser.build_parser().parse_args(["login", container, "--get-proot-cmd"])` + `command_login(ns)` inside the existing `SystemExit` wrapper; also give the capture object a `.buffer` (e.g. a `TextIOWrapper(BytesIO())`, or a small class whose `.buffer` is a `BytesIO` that `getvalue()` decodes), because upstream writes bytes. If `cli.main` must stay, it has to run on the main thread **and** still needs the `.buffer` proxy. Add a non-mocked test.
- **Risk if ignored:** every "open shell" fails — the terminal feature is 100% unusable, and the user sees either `signal only works in main thread…` or `'_io.StringIO' object has no attribute 'buffer'` in the session error line. This is the app's flagship flow.

### F2 · P1 · Generic-mode login argv silently drops the proven Android proot extensions

- **Where:** `src/core/storage_paths.py:36-53`, `.venv/Lib/site-packages/proot_distro/constants.py:55-68`, `.venv/Lib/site-packages/proot_distro/commands/login/proot_cmd.py:130-158` (guard at `:137-138`); app's own contract `docs/reference/dep-proot-distro.md:18` and D-016 §3 (`docs/decisions.md:81-85`).
- **What:** the env contract sets `TERMUX__PREFIX`/`TERMUX__HOME` but deliberately not `TERMUX_VERSION`/`TERMUX_APP__APP_VERSION_NAME`, and `TERMUX_PREFIX` (the one `_detect_termux` probes) does not exist, so `IS_TERMUX=False`. `_add_proot_extensions` returns immediately in that mode (`proot_cmd.py:137-138`), so the printed login argv contains **none** of `--kill-on-exit`, `--link2symlink`, `-L`, `--sysvipc`, or the fake `--kernel-release`. The device-proven session argv (D-016 §3) explicitly required `--link2symlink`, `-L`, `--sysvipc`, `--kill-on-exit`, `--kernel-release`, `PROOT_L2S_DIR`; the reference note already records that generic mode skips them.
- **Evidence:** `proot_cmd.py:137-138` — `if not IS_TERMUX: return` before every `args.append` at `:139-158`. `constants.py:55-68` — indicators are android platform/build.prop, `TERMUX_VERSION` env (unset), and `os.access(TERMUX_PREFIX)` (path does not exist). `session_service.py:39-69` parses the printed line verbatim; it never adds generic-mode extensions. `docs/decisions.md:84-85` records the spike's required flags.
- **Fix / opportunity:** after `shlex.split`, insert the generic-mode extensions immediately after `argv[0]` in `session_service.session_argv` (proot accepts flags in any order): `--kill-on-exit`, `--link2symlink`, `-L`, `--sysvipc`, and `--kernel-release=…` if desired. Do **not** flip `IS_TERMUX` by setting `TERMUX_VERSION`: that relocates `RUNTIME_DIR` from XDG to `$PREFIX/var/lib/proot-distro` and orphans every installed container (`constants.py:75-86`). Add the flags to the golden test.
- **Risk if ignored:** guest `dpkg`/`apt` loses the hardlink/lstat handling the spike needed (the documented apt-upgrade failure class), guest processes can survive `ProotSession.stop()` (no `--kill-on-exit`), and the fake kernel release is absent. Device verification required, but the omission itself is proven.

### F3 · P1 · Live shell output is never shown after the terminal mounts

- **Where:** `src/services/session_manager.py:38-43,69-70`; `src/screens/terminal_view.py:96-98,105-106`; flet observable semantics `.venv/Lib/site-packages/flet/components/observable.py:95-141` (auto-wraps only `list`/`dict`, `:227,342`).
- **What:** `SessionManager`'s output callback is `entry.feed(data)`, which only does `self.scrollback.append(data)`. The terminal widget receives bytes only from `entry.replay(mt.send_bytes)`, called once from `mt.on_mount`. A `deque.append` is invisible to `@ft.observable` (it notifies on attribute assignment; a `deque` is not wrapped into an observable list), and `TerminalView` subscribes to `state`, not to the entry. So bytes printed by the shell after mount are never forwarded to `mt.send_bytes`; they appear only after leaving and re-entering the screen (which remounts and replays the whole buffer).
- **Evidence:** `session_manager.py:69-70` — `def _on_bytes(data): entry.feed(data)`; `session_manager.py:38-39` — `feed` is one `self.scrollback.append(data)`; `terminal_view.py:96-98` — `_on_mount` is the only `send_bytes` consumer. `ProotSession.start` starts the reader thread at `session_service.py:113-134` and calls `_on_bytes` at `:126`.
- **Fix / opportunity:** keep `feed()` for replay, but also push each chunk to the widget on the UI thread. `SessionEntry` can hold a sink (`entry.sink = mt.send_bytes` set in `terminal_view`) and `feed()` can call `entry.page.loop.call_soon_threadsafe(sink, data)` (the install path already uses `call_soon_threadsafe`, `app_controller.py:171-177`); `mt.clear_pending()` before replay still works on mount. This preserves the D-017 "process and scrollback live on the entry" rule.
- **Risk if ignored:** the shell looks dead: the first prompt may render, but every subsequent prompt, command echo, and command output is invisible until the user leaves and reopens the container.

### F4 · P1 · Backup is impossible on Android at the file-picker boundary

- **Where:** `src/app_controller.py:342-354` (`save_file` at `:346-348`); `.venv/Lib/site-packages/flet/controls/services/file_picker.py:312-316`; upstream `.venv/Lib/site-packages/proot_distro/commands/backup.py:451-481`.
- **What:** on mobile, `FilePicker.save_file` raises `ValueError('"src_bytes" is required …')` unless `src_bytes` is supplied. `backup_container` calls `save_file(dialog_title=…, file_name=…)` with no `src_bytes`, and does not catch the exception, so "Backup to a file" always fails on device before proot-distro runs. Even if the picker returned a path, upstream refuses an existing file (`backup.py:476-479`), so a SAF-created empty target would be rejected.
- **Evidence:** `file_picker.py:312-316` is an unconditional guard on `self.page.platform.is_mobile()`; `Platform.is_mobile` exists (`flet/controls/types.py:843-851`). `backup.py:472-479` — `isdir`/`isfile` checks then `crit_error(... already exists ...)` + `sys.exit(1)`.
- **Fix / opportunity:** write the archive into app storage first (`proot_service.backup_container(container, str(storage_paths.support_root() / "backups" / f"{container}.tar.gz"))`), read the bytes, then `save_file(file_name=…, src_bytes=bytes)`. This also enables compression choice (see missed capabilities) because the app owns the temp filename. Delete the temp after the picker returns.
- **Risk if ignored:** the backup action in every container menu fails on Android; restore has its own path risk (F11), so the snapshot feature has no working half on device.

### F5 · P2 · Install diagnostics never reach `Outcome.output`; pull-limit detection is dead

- **Where:** `src/services/proot_service.py:87-94,415-444`; upstream `.venv/Lib/site-packages/proot_distro/message.py:187-229` and `commands/install.py:380-393`.
- **What:** when `on_line` is supplied, `_run_command` nests `redirect_stderr(buf)` **and** `redirect_stderr(_LineTee(on_line))`. The inner redirection replaces the outer one, so stderr lines go only to the tee and are **not** captured in `buf` — contrary to the docstring's "as well as captured for the final report". All upstream diagnostics are stderr (`msg`/`log_*`/`crit_error`, `message.py:187-229`), and install failures print only there before `sys.exit(1)` (`install.py:380-393`). Therefore an install `Outcome` is `(False, "proot-distro exited 1", "")`; `friendly_job_error` returns that bare string, and `is_pull_limit` (`proot_service.py:441-444`) can never see `429`/`rate limit`, so `PULL_LIMIT_COPY` is unreachable.
- **Evidence:** `proot_service.py:89-94` (nested `redirect_stderr`); `message.py:207` — `print(*args, file=sys.stderr)`; `install.py:385-393` — `log_error(...)` then `sys.exit(1)` with nothing on stdout.
- **Fix / opportunity:** make `_LineTee` a two-sink tee (`self._buf.write(data)` **and** `on_line(line)`), or capture into `buf` and have the UI read incrementally from it. Then `Outcome.output` keeps the real error tail and `is_pull_limit` works.
- **Risk if ignored:** users get "proot-distro exited 1" instead of the actual cause (bad reference, network, auth, rate limit), and the specially written Docker Hub limit message never appears.

### F6 · P2 · Session list/kill read a registry the app never populates

- **Where:** `src/services/proot_service.py:393-412`; `src/app_controller.py:385-399`; upstream `.venv/Lib/site-packages/proot_distro/session.py:115-140,210` and `commands/kill.py:88-115`.
- **What:** upstream's registry is written only by the process that immediately `execvpe`s proot (`register_session` must run in the exec'ing process so `os.getpid()` is the proot PID — `session.py:115-140`). The app spawns proot with `subprocess.Popen` (`session_service.py:101-109`) and never registers, so `active_sessions()` is always empty. The "Running sessions" menu therefore always snacks "no running sessions" even with four live shells. If `kill_session(pid)` is ever called, upstream finds no match and returns cleanly (`kill.py:109-111`), which `_run_command` reports as success — the UI would say "stopped session N" while nothing was signalled.
- **Evidence:** `proot_service.py:393-412` returns `session.active_sessions()`; `app_controller.py:385-393` renders it; `kill.py:109-111` — `if not selected: log_info(...); return` (no exit, so `Outcome.ok=True`).
- **Fix / opportunity:** enumerate the app's own `SessionManager.entries` (`session_manager.py:46-61`) — expose `(container, session.pid, alive)` from `ProotSession` (`_process.pid`) — and stop via `ProotSession.stop()`/`os.killpg` (each session is started with `start_new_session=True`, `session_service.py:107`). Keep upstream's `active_sessions`/`command_kill` only for foreign sessions; do not try to fake `register_session`.
- **Risk if ignored:** a session-management screen that always claims there are no sessions, and a "stop" path that can report success without stopping anything.

### F8 · P2 · Storage total undercounts and cached-image sizes are always zero

- **Where:** `src/services/proot_service.py:272-298`; `src/screens/views.py:462`; upstream `.venv/Lib/site-packages/proot_distro/helpers/docker/cache.py:683,689-714`; `constants.py:78-86`.
- **What:** the settings row says "containers + cache" but `storage_bytes()` walks only `xdg_data_home()/proot-distro` (containers, locks, sessions). Layer and manifest caches live under `XDG_CACHE_HOME/proot-distro` (`constants.py:82-86`) and are never counted. Separately, `cached_images()` tries `image.get("full_path") or image.get("path")` and then `Path(path).is_dir()`; upstream's `path` is the manifest **JSON file** (`cache.py:683`), so `is_dir()` is always false and `size_bytes` is always 0 — even though the record already carries `"size"` (sum of present layer blobs, `cache.py:689-696,710`) and `"missing"`.
- **Evidence:** `cache.py:683` — `path = os.path.join(MANIFEST_CACHE_DIR, name)`; `cache.py:698-714` — record keys `path, name, key, image_ref, repo, arch, image_id, layers, size, missing, created, cached_at` (no `full_path`, no `id`). `proot_service.py:282` — `Path(path).is_dir()`; `:286` — `image.get("id")`.
- **Fix / opportunity:** sum both roots (`xdg_data_home()` and `xdg_cache_home()`); return `image.get("size", 0)` from `cached_images()` (and optionally `missing`), keeping the host-side walk only as a fallback.
- **Risk if ignored:** the storage figure can be orders of magnitude low after several installs; the cache screen cannot show per-image weight.

### F9 · P2 · The token field accepts a bare Docker Hub token, which upstream hard-rejects

- **Where:** `src/screens/views.py:496-502`; `src/app_controller.py:248-258`; `src/services/proot_service.py:426-430`; upstream `.venv/Lib/site-packages/proot_distro/helpers/docker/transport.py:404-419`.

### F10 · P2 · `busy_locks()` converts "cannot tell" into "nothing held"

- **Where:** `src/services/proot_service.py:301-309`; upstream `.venv/Lib/site-packages/proot_distro/locking.py:346-368,388-397`.
- **What:** upstream deliberately raises `LockStateUnknown` when a lock directory cannot be read, because an empty list must mean "nothing is held". The facade catches `Exception` and returns `[]`, so an unreadable/chmod-ed lock tree looks free and the install guard in `app_controller.py:164-166` lets a second install start. Upstream's container lock then makes one of them fail with a lock error instead of the app showing "install already running".
- **Evidence:** `locking.py:346-368` docstring ("An empty list has to mean 'nothing is held' … Raises `LockStateUnknown`"); `proot_service.py:304-309` — `except Exception: return []`.
- **Fix / opportunity:** catch `locking.LockStateUnknown` specifically and surface a distinct "lock state unknown" note (fail closed: do not start the install), while returning `[]` only for a genuinely absent lock directory.
- **Risk if ignored:** concurrent installs/resets race on the cache and one fails with a confusing error; the concurrency guard silently disappears exactly when the state is suspicious.

## Verified-good list

- **Sole-importer rule holds.** `src/services/proot_service.py` is the only `src/` module importing `proot_distro`; `app_controller.py:48` and `proot_probe.py:66` are comments. Enforced by `tests/test_proot_surfaces.py:34-41`.
- **Env contract before first import.** Every facade entry point calls `bootstrap()` first (`proot_service.py:81,186,265,274,303,319,395`), and `AppController.init` runs `proot_probe.bootstrap_env` before any of them (`app_controller.py:47-51`). `PD_FORCE_NO_COLORS=1` is set pre-import (`storage_paths.py:52`), so captured stage lines contain no ANSI (`message.py:107-113`).
- **Storage paths match upstream exactly.** `containers_dir()` = `$XDG_DATA_HOME/proot-distro/containers` (`storage_paths.py:31-33`) vs `constants.py:85,89`; cache root `$XDG_CACHE_HOME/proot-distro` (`storage_paths.py:26-28`) vs `constants.py:82-86`. Lazy import + `_BOOTSTRAPPED` makes the contract idempotent.
- **No `command_login` and no `command_run` in-process.** No exec path is reachable: grep finds neither handler; sessions are a `Popen` of the printed argv (`session_service.py:101-109`).
- **All hand-built namespaces match upstream reads, field-for-field.** install `image_ref/custom_container_name/override_arch/allow_insecure` (`install.py:140-183`); remove `target/image/override_arch/verbose` (`remove.py:110-179`); reset `container_name` (`reset.py:46`); rename `orig_name/new_name` (`rename.py:52-53`); backup `container_name/output/compression/verbose` (`backup.py:453-456`); restore `archive/verbose` (`restore.py:458-459`); copy `source/destination/verbose/move/recursive` (`copy.py:65-69`); kill `target/all/signal` (`kill.py:90-92`). Extra fields (`quiet`, `verbose` on reset) are harmless.
- **`kill` with `signal=None` is correct.** `command_kill` falls back to `SIGTERM` when `signal_name` is falsy (`kill.py:94`), so `_ns_kill(..., signal=None)` does not fail.
- **`SystemExit` and `RuntimeError` are handled.** `_run_command` maps `SystemExit` codes to `Outcome` and catches `Exception` (`proot_service.py:96-102`); `get_proot_cmd` catches `SystemExit` and restores `sys.argv`/stdout/stderr in a `finally` (`:335-344`). Upstream's `RuntimeError` (network/bad ref) therefore cannot escape as an unhandled crash.
- **Upstream session read is read-only and correctly shaped.** `active_sessions()` reads `pid/container/kind/user/command/start_time` (`proot_service.py:399-408`) exactly as upstream writes them (`session.py:155-168`); the app never calls `register_session`, which is the right call given its PID-identity requirement.
- **Search integration matches upstream's normalized shape.** `search_images` returns dicts with `name/description/stars/pulls/official/automated` (`search.py:127-139`); the UI reads exactly those keys (`views.py:137-146`).
- **`busy_locks` tuple handling is correct.** `for _path, hint in locking.busy_locks()` matches `(lock_path, hint)` (`locking.py:346-350`); only the exception path is wrong (F10).
- **`PD_DOCKER_AUTH` is read at call time**, not import time (`transport.py:411`), so setting/clearing it from Settings takes effect without a restart.
- **Python 3.14-only tuple-except syntax is valid here.** `session_service.py:123` (`except OSError, ValueError:`) and `posixdb.py:87` (`except ValueError, ImportError:`) are PEP 758 syntax, accepted by Python 3.14 (`ast.parse` on the venv interpreter returns OK; `requires-python = ">=3.14"` in `pyproject.toml:8`). Not a syntax error on this floor — do not flag as P0.
- **Import-time `os.umask(0o022)`** (`constants.py:40`) is an upstream side effect on the whole process. On Android the app data dir is private, so no exposure; noted so it is not mistaken for app code.
